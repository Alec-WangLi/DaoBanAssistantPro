- **v0.9.19**（测试版 · v0.9.18 自己改出来的两处）：两条都是**上一版的手尾**，也都属于「单测照不出来、屏幕上看一眼就现形」那一类。
  **① 全 app 的弹窗按钮跑到左边**（用户原话「怎么好多按钮都跑到左边去了？……好像是你改错了某一处地方」——**判断完全正确**）。根因是 v0.9.18 为了让小窗（200×400）下「删除 / 取消 / 保存」三颗按钮不横向溢出，把 `GlassDialog` 的动作行从 `Row(mainAxisAlignment: end)` 换成了 `Wrap(alignment: WrapAlignment.end)`：**两者宽度行为不同** —— `Row` 默认 `mainAxisSize.max` 会把整行撑满、`end` 才有富余可对齐；`Wrap` 收缩到**内容宽度**，外层 Column 又是 `crossAxisAlignment.start`，于是整块被贴到左边，`WrapAlignment.end` 在「自己就是内容那么宽」时不起任何作用。**一处改错 = 二十来个弹窗一起靠左**（版本更新的「知道了」、删除确认、时段弹层、重复待办面板……全走同一个件）。修法是外面套一层 `Align(alignment: Alignment.centerRight)`（撑满宽度、高度仍收缩），`Wrap` 原样保留 —— 靠右回来了，窄窗折行也没丢。
  **② 编辑排班页底部那条「蒙板」**：那块板子就是 `Scaffold.bottomNavigationBar` 本身 —— 它**不是浮在正文上的**，正文到它的上沿被**硬切**（探针实测：卡片正好在距屏底 80 处齐刷刷断掉，下面一整片平色）。修法是 `extendBody: true`（与首页导航胶囊同一套写法：正文铺到屏幕底、按钮条自己不画任何底色），再用 `core/layout.dart` 的 `kFloatingSaveInset = 92` 给正文补足底部留白，并给胶囊补一层与 `GlassButton` primary 同款的投影（正文从它底下穿过去时，没有投影的实心胶囊看着像贴上去的）。
  **两个只有量过才知道的数**：按钮 **48 高**、按钮条 **80 高**、**顶边距屏底 64** —— 420×900 与 200×400 两档完全一致（所以「小屏按钮更矮、留白可以同步收」这个假设是错的）。旧的 `isShort ? 56 : 100` 分档是按「正文到按钮条上沿就被切掉」的老结构算的，`extendBody` 之后 **56 那一档就不够了**（最后一行正好塞在胶囊底下，反向验证过：退回去小窗那条用例立刻红，344 vs 328）。
  **⚠️ 这条常量与上面两个不同，必须叠系统栏**：按钮条包在 `SafeArea` 里、会跟着手势条 / 三键导航一起上移，所以调用点写 `MediaQuery.paddingOf(context).bottom + kFloatingSaveInset`。本仓的测试视口都没有系统栏，这类错只能靠算式堵 —— 别「为了统一」把它也改成裸常量。
  **工装**：`02_editor_*` 五档全部重出（浅色那张现在能看到「中班」那张卡从胶囊下面穿过去），`33_span_editor` 的浅色 / 小窗两张用来核「按钮回到右边」与「窄窗仍折行」。测试 531 → **536**，工装 254 条不变。

- **v0.9.18**（测试版 · 三条真机反馈）：v0.9.17 真机试用后的三条，逐条都在「先查清再改」上花了功夫。
  **① 「小组件只能显示 3 个月？重启才正常」** —— 两个问题分开答：**能翻的范围**确实只有 ±1 个月，但那不是架构限制（数据是 App 上次运行时算好的，窗口就是一段日期区间）→ 放宽到 **±3 个月**（最坏 231 天，上限 112 → 240，**协议版本仍不动**）。**「重启才正常」不是特性**：数据只能由 Dart 算，装完更新到「App 第一次运行」之间**没有任何触发点**让卡片重画（`BootReceiver` 收了 `MY_PACKAGE_REPLACED` 也只重排闹钟），所以卡片上挂的是升级前那一次的渲染字节 → 一句话进更新日志与使用帮助（**装完新版先打开一次 App**），外加一条兜底：`HomeShell` 挂 `WidgetsBindingObserver`，**回到前台也推一次快照**（推失败本来是 fire-and-forget、只留日志，切回 App 就是一次重试）。
  **② 待办列表最后一行的删除键被「新建」按钮挡住** —— 探针实测：FAB 顶边在**距屏底 148**，而留白 96 时最后一颗删除键的最低点在距底 115 → **压住 33px**。修法是两个**量出来的**常量（`core/layout.dart` 的 `kNavCapsuleInset = 96` / `kFloatingActionInset = 160`）＋待办列表、闹钟页最下面那段列表各补一次。**闹钟页有同一处**（底部按钮条同样 56 高、顶边同样在距底 148，而那两个分区原来底部留白是 0，只有 short/narrow 才补一截 156）。护栏是**几何 + 命中测试**（滑到底后断言删除键的底边在按钮顶边之上、且它中心真的打得中）—— 这类「被盖住」单测照不出来。**第一版用例不具鉴别力**：夹具视口 1200 高、12 条待办根本滚不动，把留白改回 96 照样绿；改成 24 条才照出来（两条都反向验证过）。
  **③ 「添加时段」弹层字体偏小** —— 真跑偏了：三个标签用的是 `rowSecondary`（13/**w400**），而**打开它的那一行**（同一页时间线）是 `rowPrimary`（14/w500），编辑器的「行内标签」契约又是 `labelSecondary`（13/w600）—— 本仓那条用例的注释写着「掉到 w400 的 rowSecondary 正是要钉住的」。按用户拍板对齐到 `rowPrimary`，并补一条钉字号的用例。
  **屏单一补上就抓出两个小窗布局 bug**（这个弹层此前**从没进过屏单**）：`33_span_editor` 在 200×400 下先是 `ListTile` 的 trailing 吃掉整行（框架**直接抛断言**），接着日期那行横向溢出 23px → 把「排班 / 从 / 到」三行统一走时间线那套**手搓 flex Row**（`_labelValueRow`，文件内共一份），最后 `GlassDialog` 的 actions **`Row` → `Wrap`**（三个按钮在约 112dp 的弹层内宽里排不下就折行；正常宽度下与 `Row` 一样）。**这三处都不是这一轮引入的，是"没有屏单 = 没有眼睛"的又一次记账。**
  **工装**：`33_span_editor`（新屏，含小窗那一档）；`05_todos` / `06_alarm` 因留白变化重出。测试 527 → **531**，工装 246 → **254**。

- **v0.9.17**（测试版 · 月历小组件连月 + 翻月）：v0.9.15 真机反馈的第二条，用户原话「咱们桌面小组件里，最大的那个显示月历的小组件，能不能把上个月和下个月都连起来显示？同时支持切换上下月呢？」。spec 在 `docs/superpowers/specs/2026-09-30-widget-month-navigation-design.md`，计划在 `docs/superpowers/plans/2026-09-30-widget-month-navigation.md`（5 个任务）。
  **四个决策**（2026-09-30 拍板）：① 相邻月那几格**日数字变灰、班次胶囊照画**；② 标题行 `‹ 月份 ›`，**点中间那行文字回今天**；③ 能翻的范围 = 快照覆盖到的月份（上月 / 本月 / 下月），到头那侧箭头变灰；④ 翻走之后**跨天跨月不把你拽回来**（锚点存绝对值）。
  **快照窗口从「本月 + 下月」扩到「上月 + 本月 + 下月」**（整周对齐，最坏 105 天；上限 68 → 112）。**协议版本仍是 2**：只改范围、字段没动，旧读新忽略多出来的天、新读旧相邻月挖空，两边都能降级 —— 升版本会把桌面上所有小组件立刻打成占位态。
  **「能不能翻」与「画不画得出来」是同一条判据**：`WidgetRenderer.monthCovered`（该月 42 格全在快照窗口里）。箭头灰不灰、接收端吞不吞这枚点击，用的都是它；`displayedMonth`（锚点 ?? 今天，锚点画不出来就当没设）**也是渲染端与接收端共用一处** —— 两边各读一次盘上的锚点就会出现「箭头作用在你没看见的那个月」。
  **两条只有翻过代码才看得见的约束**：① **箭头变灰也不能不设点击** —— `RemoteViews` 的 `reapply` 只重放新的动作串，**没有任何办法撤掉上一次设过的点击**（与 v0.9.9 那条 `removeAllViews` 同源），所以越界一律由**接收端**吞掉；② 锚点**不能在删卡后留着**（`ShiftWidgetBase.onDeleted` 里清）—— 系统会复用 `widgetId`，留着就是「新卡片一上来停在上一张卡翻到的月份」。
  **这一轮改了 Kotlin**（`WidgetRenderer` / `WidgetRefreshReceiver` / `WidgetStore` / `ShiftWidgetBase` + 月历布局），但**依然没有测试目标**：验收靠「Dart 扫源码的护栏（箭头 id、action 常量的引用关系、requestCode 基数与展开式、锚点清理）+ 真机」两头兜。
  **计划之外的两处修正**（账本里都有 ruling）：窗口终点原写成「下月最后一天所在周的周日」盖不住下月自己的 42 格（下月是 2 月时排到 3/8，而那个周日是 3/1）→ 改成「下月 1 日所在周的周一 + 41 天」；护栏原打算比对「两边各写的 action 字面量」，而实现是发送端引用接收端那个 `const val`，改成钉「它确实是引用、不是手抄」。

- **v0.9.16**（测试版 · 法定班次改回「一张纯日历」）：v0.9.15 真机反馈两条里的第一条，也是**上一版做过头了**的一处。
  **用户原话**：「这个法定班次……确实不应该显示上班嘛，它本质上可能就想当个日历看吧。」
  **根因是一次判据与显示的混用**：v0.9.14 的「整月没排班」那句指路用 `shiftOn == null` 判，而空白表天天返回 null；v0.9.15 我没有把判据修正，而是**给空白表合成了一个「上班 / 休息」班次**让它「画得出东西」—— 那是拿显示去迁就判据，用户一眼就看出来了（「不应该显示上班」）。
  这一版把两者分开：**判据改用新的 `ScheduleChain.hasScheduleOn(day)`**（= `scheduleOn(day) != null`，「这天有没有**班表在管**」），**显示上什么都不写**（格子 / 小窗信息卡 / 桌面小组件都只画日期与农历，法定节假日照旧标红、调休照旧打「班」）。`domain/day_display.dart` 与那两个合成色号（白班蓝 / 休班灰）一并删净；`shiftOn` 从头到尾都是真值，没动过。
  **信息卡那一支顺手改对了**：原先是三支（真班次 / 空白表写两个字 / 没有班表），现在两支 —— 空白表**什么都不写**，而「这段时间没有排班」那句只在 `daySchedule == null` 时出现（原样删中间那支的话，空白表会掉进「没有排班」那支，正是要修掉的那句话）。`info_card_metrics` 那一行的高度也**从一次性算好的常量改成逐日算**（空白表按 0）：不改的话卡片底下白留约 16dp，而用户对「卡片底下那截空白」是**报过一次的**（v0.9.7 整轮的起因）。
  **验收**：新增/改写的用例各钉一边 —— 日历「整月一天胶囊都不画，但也不说『没有排班』」、小窗「不写上班，也不说没有排班」、快照「hasSchedule 为真但逐日 hasShift 为假」、信息卡「空白表那套班次行不占高度（比真排班至少矮 12dp）」，外加 `schedule_chain_test` 那条**把三个 getter 的分工摆在一起**的用例。三条护栏都反向验证过：判据退回 `shiftOn == null` → 日历那条立刻红（v0.9.14 的老毛病复现）；那一行留回高度 → 信息卡那条红。

- **v0.9.15**（测试版 · v0.9.14 真机反馈的收口）：五条反馈一次收齐，外加两条跑全套测试时逮到的既有缺陷。
  **⚠️ 其中 ⑤ 的**做法**已被 v0.9.16 推翻**（给空白表合成「上班 / 休息」班次 —— 那是拿显示去迁就判据，用户第二天就指出「确实不应该显示上班」）。下面这段是当时的记录，**看结论时把 ⑤ 换成 v0.9.16 那条**：判据用 `hasScheduleOn`、显示上什么都不写。
  **① 更新说明里混进了 markdown**：`_changelogZh/_changelogEn` 的 v0.9.14 与 v0.9.11 条目里有五处 `**...**`，而更新日志是纯文本渲染的（`showAppInfoDialog` 里就是一个 `Text`）—— 用户看到的是星号本身。**这是 v0.7.1/v0.7.2 犯过的同一个错**，当时只手工清掉、没留护栏，所以它又长回来了。这回除了清掉，还在 `changelog_window_test.dart` 里补了一条「不许出现 markdown 标记」的用例（`**` / 反引号 / 行首 `#` / `[文字](链接)`，且报出**命中哪一行**）。
  **② 排班管理页分成两节**（用户原话「有点乱，应该分成两个功能区……现在它们连在一起」）：加一个页面级小节标题（`_sectionHeading`，与「我的」页/闹钟页那两处同形），「排班时段」在上、「排班表」在下。**原本时间线那张卡片的标题在卡里面、排班表那一节没有标题**，一节有一节没有正是「连在一起」的来源。
  **③ 一个时段都没有时改说「全部日子」**（用户原话「它说『其余时间 五班三倒』，那其实是默认一直都是五班三倒吗？」）：「其余」得有「这一段」才有意义。`L10n.allDates` + 两版说明（有兜底班表 / 没有 —— 后者的下一步是「挑一套」而不只是「加一段」）；`scheduleRoleLabel` 多一档 `hasPeriods == false` → 「正在使用」，并把列表副标题尾巴上那个「· 当前」只在**有段时**才挂（否则是同一件事说两遍）。日历那个只读总览弹层用的是同一套说法，一起改。
  **④ 时段弹层的两颗钮**：「取消」**点不动**，是真 bug —— `onPressed: () => dialogCloser(ctx)` 套了一层箭头函数，等于把闭包造出来又扔掉（`dialogCloser` **返回**闭包，惯用法是 `onPressed: dialogCloser(ctx)`）；Dart 允许「返回函数的函数」赋给 `void Function()`，所以它编译得过、不报错、也不关窗。全仓只剩两处（时段弹层、其余时间选择层），都修了，并补了「点取消必须关窗」的用例。三颗钮原先还紧挨着（`GlassDialog` 的 actions 是个光秃秃的 `Row`，间隔得各调用点自己给，全仓其余弹窗都写了 `SizedBox(width: 8)`，就这一处漏了），按**几何**补了一条用例。
  **⑤ 法定班次（跟随法定节假日）不再被当成「没有排班」**（用户原话「日历界面一直弹窗提示这段时间没有排班，但其实我们是按照法定节假日上班的」）：根因是 `_monthHasNoShift` 的判据用了 `shiftOn == null`，而空白表**天天**返回 null。新增**一处**实现 `domain/day_display.dart` 的 `displayShiftOn`（空白表 → 合成一个「上班 / 休息」班次，色号借内置模板的**白班蓝**与**休班灰**，不另造），日历格子 / 小窗信息卡 / 本月统计 / 桌面小组件快照四处理解同一处；**`shiftOn` 保持真值不动**，所以闹钟链与按天改班的闸门一个字都没改；**Kotlin 侧一个字都没改**（快照字段形状不变，原生本来就只认 `hasShift/shiftAbbr/color`）。同源的另外两处一并修：桌面小组件的 `hasSchedule` 从 `hasCycle`（「有没有班次可挑」）换成新的 `hasAnySchedule`（「用户到底排没排班」），只有一套法定班次时不再写「还没有排班」；信息卡那一支给真班次的闸门加了 `!isBlank`（合成班次不能去写时间与闹钟）。
  **顺手逮到的两条既有缺陷**（跑全套测试时撞上的，都不在反馈里）：① 上一条：`recurring_dialog_test` 那条「把每周三改成每周五」**在周三、周四必红** —— 编辑重复待办时把系列的 `startDate` 改写成「当前这一次」的日期，于是「最近的那个周五」早于新起点、被 `occurrenceOnOrBefore` 的那道 `daysBetween(start, 候选) >= 0` 闸门（本来是给生成器用的）判掉，静默不对齐。**这份仓库在 v0.9.14 是带着一条红用例发出去的**（只有周三/周四跑才会现形）。② 无（另一条就是它自己的两个面）。
  **工装**：新增 `32_calendar_blank_schedule`（空白表那种班表**从没进过屏单** —— 它此前只由 `calendar_screen_test` 的 `blank: true` 造出来过，单测问得出「有没有指路」，问不出「整张日历被盖住好不好看」），并给 `seedBlankSchedule` 造了「只留一套法定班次」的库；`30_management_timeline` / `03_management`（含下滚那张）/ `05_todos` 全部重出比对。

- **v0.9.14**（测试版 · 排班时段重做）：v0.9.12 真机试用后用户报的**第一件事**，也是五条反馈里最后落地的一条。用户原话：「我给两个新排班表 2 跟 3 设的生效时间都是 9 月 1 号到 9 月 30 号，最终日历给出的是排班表 3。感觉有点乱。同时日历界面的切换排班按钮相当于没用了，你切换什么班表呢？」
  **根因不是 bug，是按钮的语义和模型的语义打架**：解析规则「起点最晚的赢」是为了**永远不报错**（重叠也有确定答案），代价是结果不可预测；而「切换排班」改的 `isCurrent` 只是**没被时段覆盖时的兜底**，时段盖满之后它什么也改不动 —— 用户以为它在管全局，它其实只在管「剩下的」。

  **实施途中发现模型装不下一个形状，重新拍了板**：旧规则能表达「外段被内段截断之后还要接着用」（`B[7/1,∞)` + `C[9/1,9/30]` → 10/1 起又归 B），而「一套方案只有一对起止」表达不了 —— 于是**段独立成表**（`ScheduleSpanRows`），一套方案可以出现在**多段**上。迁移因此是**无损**的（「按边界切 → 逐区间重放旧规则 → 合并相邻同胜者」），用户升级后**一天都不变**。

  **生成器** `advanceRecurringTodos({required DateTime today})`：没有未完成的行 → 新建；有过期的 → **就地顺延**（只改日期，行 id 不变）；日期**晚于或等于** occurrence → **不动**（用户手工把这一次挪到周五之后不许被拽回来）；停用 → 不动；`skipThrough` 之前 → 不补。跑在三个时点：App 启动（`home_shell` 那个「三个流到齐」的闸，**在重排提醒之前**）、回到前台（`ScheduleScreen` 因此变成 `StatefulWidget` 挂 `WidgetsBindingObserver`）、进页面。

  **⑤ 日历文字 = 主因是系统字号，不是窄屏**。用户以为是「窄的手机」，量下来要靠宽度截断得窄到 ~245dp（那是小窗）。真正的原因有两层：① 农历那一行是格子里**唯一没有自己 `FittedBox`** 的一行（日期有、胶囊有），它是 `maxLines:1 + ellipsis`，而整格外面那层 `FittedBox` **救不了它** —— 外层给的约束是固定的 `contentW` 宽，省略号先烘进结果，之后再缩也变不回来（「缩小不能取消省略」）；2 字的「廿一」放得下、3 字的「财神节」放不下，正是这条线上发生的事。② 周标题行是固定 26dp 的带子，字高随系统字号长到约 30dp 就**压进第一行格子里**。改法：给农历、周标题、以及「窄到画不出胶囊」时那句纯文字各补一层 `FittedBox(scaleDown)`，与日期行同一个写法。**有意不按系统字号长高 `_weekdayH`**：那个常量同时被 `_buildGrid` 六处命中测试算式用，改成逐帧算的值漏一处就是「系统字号调大点哪一格都不对」；而且换来的高度换不成更大的字（格子里的字按格子高度缩放）。由此定下一条规则写进注释：**网格是定尺的点阵、字一律归一到格子里；真正按系统字号长的是底栏信息卡**（`info_card_metrics.dart` 用 `textScaler` 实测）。另加 `LunarInfo.cellLabel`（≤3 字 + 省略号）：长节日名（「全民国防教育日」7 字，来自 `getOtherFestivals()`）交给 `FittedBox` 会缩到 0.46 倍约 6px —— **完整但没人看得见，比截断更糟**；信息卡仍用完整的 `shortLabel`。**加这一屏立刻抓出第二处真 bug**：信息卡第一行「日期 + 今天 + N 项待办」在 1.8× 下横向溢出 76px、把待办徽章整个挤出卡片 —— 日期那串改成 `Flexible + FittedBox(scaleDown)`（三个元素都要紧，谁也丢不得；紧凑卡那一支仍走省略号，那边窄到 200dp 缩下去就没法看了）。**已量过的不修项**：班次行尾的 `闹钟…` 在 1.8× 仍会省略 —— 那是 `Flexible + ellipsis` 的**有意降级**（先丢最不重要的那段），改成整体缩放会把「窄窗下长班次名」一起拖下水。**工装**：`VisualApp` / `pumpScreen` / `renderScreen` 加了 `textScale`（默认 1.0），新增 `20_calendar_large_font`（1.8×）—— 此前每一屏都只在 1.0× 出图，「系统字号放大后文字被截」在图上**结构性地看不见**，这一轮的截断就是这么漏掉的。测试 366 → 371（小组件护栏 1、铃声 2、农历格标签 2），工装 195 → 196，全套 + 工装全绿。

- **v0.9.6**（测试版 · 自定义闹钟的默认值与日期）：起头是用户真机反馈「自定义闹钟的时候，默认选项改成一次性 —— 现在老是选每天，很多时候我们的闹钟就是想一次性用完就自动删掉」。改 `alarm_screen.dart` 的 `_showAlarmDialog`：新建时 `repeatType` 默认从 1（每天）改成 0（一次性），编辑既有闹钟照旧读存下来的值。**但只改那一个默认值会造出一类排不出去的闹钟**：新建时时间默认此刻、日期默认今天，两个默认叠在一起，触发时刻在按下「添加」之前就已经过去了 —— 而一次性闹钟的排定判据是 `fire.isAfter(now)`（`reschedule`），过去的那一刻**直接不排**，`deleteExpiredOnceAlarms` 还会在下一次进闹钟页时把它删掉，用户看到的是「加了一条、它自己没了」。所以日期改由新的纯函数 `nextOnceDate`（`alarm_service.dart`，与 `hasPendingShiftAlarm` 同一处）取「该钟点的下一次出现」：今天这个点还没到就是今天、过了就顺延一天，用户手选了更晚的日期则听用户的；返回 `dateOnly`（UTC 零点），与库里 `onceDate` 那一列同形。**关键实现细节：日期是「派生」不是「回写」** —— 最初写成「改钟点时把 `onceDate` 就地改写成结果」，那样默认值一顺延到明天，用户再把钟点往前调回今天，就再也回不到今天了（默认值被当成了用户的选择）；现在 `onceDate` 只存用户选的那天，显示与落库都走 `onceDateAt(hour, minute)`。另给 `CustomAlarms.repeatType` 的列注写明「那个 `withDefault(1)` 是建表时的、与界面无关」，免得下次有人把两个默认值当成一处去改。测试：`once_alarm_date_test.dart` 十条纯函数边界（正好等于此刻、差一分钟没过、月末跨月、年末跨年、手选过去/将来的日期、返回 UTC 零点）；`alarm_screen_test.dart` 三条界面用例（默认一次性 → 日期行直接就在、什么都不动直接「添加」存下来的是将来那一刻、编辑「每天」的闹钟不被默认值盖成一次性）。**同轮里用户提了但决定不做的**：日历底栏信息卡「按选中那天定高」。它是 v0.6.6/0.6.10 那套「按本月最满的一天定高」的直接反面 —— 竖屏 `Column[顶栏, Expanded(网格), 信息卡]` 把卡片和网格绑在同一块空间上，卡片高度一动六个格子就一起动。实测（400dp 宽 = 用户机型宽度、六班组、2026-09）：有节假日的月份卡片 241dp、普通日子内容只要 156~175dp，底下空 32dp（农历描述短的更空到 51dp）；没有节假日的月份（2026-11）卡片 209dp、空 0~19dp。空白几乎全来自**法定节假日徽章自占一行（+32dp）**——那是 v0.6.7「徽章与农历并排会挤掉农历」之后的定法，而高度按月取最大，于是整月每一天都为这一行留着位置。按天定高能把这空白全消掉，代价是点日期时网格跟着伸缩（长按拖选一段日子时选中日连续变化，抖得最明显）—— 用户明确不要这个抖动，**定为不做**。另记一条不动网格的中间方案，将来想捡可以捡：把徽章从「自占一行」挪回日期行，节假日那天高出的部分从 32dp 缩到约 8dp、卡片整体矮约 24dp，点日期一格都不动（重新挤的概率小，但要真机看图）。
