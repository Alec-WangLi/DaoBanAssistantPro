- **v0.11.26**（测试版 · 今日卡贴齐 App：竖条通高 + 「其他班组」胶囊）：用户 v0.11.25 真机测完说周视图与月视图「基本上可以了」，只剩今日卡两处没跟 App 对应上。**这一轮按用户要求走了完整流程**：brainstorming 磨需求 → 写 spec/plan → **交给最强模型（opus，新上下文）审一遍** → 用户确认后由快模型按计划执行（`executing-plans`，台账在 `.superpowers/sdd/`，跑完删）。
  **① 竖条通高。** App 的信息卡那条是 `Positioned(left: 0, top/bottom: spaceLg, width: 6)` —— 6dp 宽、通到内容底、圆头；桌面原来只是日期行里一根 **4dp × 24dp**。改法：`widget_today_card.xml` 的根从「垂直 LinearLayout + 四周 22dp」换成**横向** LinearLayout（左内边距 0、其余 22dp），两个子层 =「通高竖条 + 内容列（`weight=1`、`marginStart 14dp`）」；日期行那根短条与它 10dp 的缩进一并删掉。竖条位图 `WidgetChip.bar(color, 6dp, 200dp)`（200dp 是「够长的常量」，`fitXY` 拉到真实内容高）。
  **⚠️⚠️ 本轮最值钱的一条：审核抓出的致命前提错误。** 我第一版设计写的是「FrameLayout + `match_parent` 高的竖条会被二次测量拿到内容列的高」——**这是错的**。`FrameLayout.onMeasure` 对每个子层**只量一次**，`match_parent` 高的子层会按它自己那张 200dp 位图解析成**固定 200dp**，与内容脱钩（内容 168dp 时竖条多出 32dp），而且卡片的根会被撑到 `max(200, 内容) + 44` —— 把卡片尺寸改了，而那一版非目标里明写着不许动尺寸。**横向 LinearLayout 才有二次测量那一步**（`measureHorizontal` 量完 `wrap_content` 的邻列后把 `match_parent` 高的子层重设为 EXACTLY 那个高度），所以根必须是它。这一条是**在写代码之前**被审核挡下来的 —— 前两轮「先出对照图/先量再改」那套自检照不出它，因为它是纯 Android 度量模型的推理。**教训：把「某个框架 API 有某个行为」写进设计之前，先想清楚它的代价 —— 那正是审一次能省一整轮构建的地方。**
  **② 「其他班组」胶囊。** App 是「8dp 实心色点 + 组名简称」外面套 14% 淡染 + 45% 描边的胶囊、几颗紧挨左排（`Wrap(spacing: spaceSm=8)`）；桌面原来是「14dp 淡色圆环 + 8dp 圆点 + 裸文字」还摊在四个等宽槽里。改成 `wrap_content` 槽位 + `marginStart 8dp` + `WidgetChip.tintedChip` 按文字宽现量（新增 `crewChipWidthPx` = `measureText + 26dp`），标签那 6dp 右边距交给槽位。
  **数字（真机 · Redmi K90 Pro Max · 3×）**：竖条 **6.00dp × 191.33dp**，顶 = 内容首行墨迹顶 − 3.00dp、底 = 内容末行墨迹底 + 2.67dp（即与内容盒同高），**卡片高 265.7dp 与改动前一致**；三颗胶囊 **77.3 / 77.3 / 65.3dp**、间距 8.3dp、末颗距内容列右缘 **8.0dp**。
  **⚠️ 内边距 6dp 而不是 App 的 8dp**：真机量出**桌面卡宽 341.7dp、App 的信息卡 368dp**（内容列 299.7 vs 332）。同样三个班组，App 那套要 **303.3dp** 而桌面只有 299.7dp —— 第一次真机跑出来最后一颗被 `LinearLayout` 挤成「四班…」。每颗省 2dp×2 让出 12dp 之后三颗完整。
  **⚠️ 反向验证抓到护栏自己是假的**：`today.contains('crewChipWidthPx')` 被我**注释里**那个词喂饱了 —— 把调用换成写死的 `dpToPx(context, 60)` 照样绿。改成先 `_stripComments` 再断言。**扫源码的 `contains` 断言必须先剥注释**（`widget_font_scale_guard_test.dart` 一直这么做，这条漏了）。
  **⚠️ 一条交付时才说清楚的**：用户当初拍板「4 个班组时接受省略」时，听的是「最后一个打省略号」；真机上那个机制的**第三种形态是「整颗看不见」**（溢出多时最后一颗被挤到 0 宽）。**4 个「其他班组」那一档没在真机验过** —— 验它必须把用户真实的班组数从 4 改成 5，那是改动用户的数据，不做。已写进 spec §3.3 并在交付说明里如实讲给用户。

- **v0.11.25**（测试版 · 周条今天那块玻璃长高 + 今日卡「其他班组」那行跟上字号）：用户 v0.11.24 真机测完提的两条，**两条都先在真机上量清楚再动手**。
  **① 周条「今天」那块，块里的字贴边。** 用户原话：「它上边的周几和下边的班次，离遮罩的边缘太近了，跟之前一样的问题，要留点空隙。要么你就把这个遮罩上下拉长，反正它还有空间。」
  量下来（Redmi K90 Pro Max · 3×）：卡片 76.33dp、块 **59.0dp**，块离卡上下沿各 **8.67dp** —— 那正是卡自己的 8dp 纵向内边距 + 块自己的 2dp 外边距，**不是多余的空白**；真正挤的是块**里面**：周几离块上沿 **3.67dp**、下夜胶囊离下沿 **5.33dp**，而左右有 6.67dp。
  也就是说「拉长遮罩」这条路能走，但空间**全在那 8dp 内边距里**（块本身已经顶到它那一格的两端了）。改法：`widget_week_strip.xml` 的纵向内边距 8 → **3dp**、`widget_strip_cell.xml` 里块的纵向外边距 2 → **0**；`stripCellPx` 的高度算式跟着从 `hDp - 20` 改成 `hDp - 6`（块是 `fitXY` 拉伸的，这个数不跟着改圆角就被拉成椭圆）。**横向一个数没动**（仍是 8dp + 2dp）。
  **真机复测**：块 59.0 → **72.67dp**，块内上留白 3.67 → **10.67dp**、下留白 5.33 → **12.00dp**；逐像素比过 —— 周条去掉今天那一列**最大差 0**、今日卡上半（日期 / 农历 / 班次 / 时间）与「本月统计」那一行**全是 0**。
  **② 今日卡「其他班组」那一行小了一档。** 用户原话：「『其他班组』那里的字体有点小，是因为没位置了还是什么？如果可以的话，可以整体再放大一些。」——**不是没位置**：卡内上下各还剩约 13dp 富余（这张卡一直「只缩不放」）。是**写小了一档**：那一行 11dp，而 App 同一行 12（`microText` / `microLabel`）、这张卡自己的「本月统计」也是 12 —— App 里「其他班组 / 色块 / 本月统计」本来同一档，是搬到桌面时这行掉了一级。用户拍板：**只放大这一行**，不动整张卡。
  改法与结果：`widget_today_card.xml` 的标签、`widget_crew_chip.xml` 的文字、`WidgetRenderer` 里那处 `applyScale` 三处 11 → **12dp**；真机墨迹高度 10.0 → **11.0dp**，与 App 那一行量到的 11.0dp 一致；卡上其余各行**位置与高度一个像素没变**（「本月统计」还在原来那一行）。那行「小圆点 + 裸文字」的形态**有意不跟 App 的淡染胶囊**：桌面这行是四个等分槽位，套上胶囊按文字宽撑开就放不下（三个班组时每槽 82.7dp 够、四个班组时只剩 62dp）。
  **⚠️ 本轮最值钱的一条是踩出来的（见「关键决策与坑」）**：改完重装、重开 App、重推快照，块**纹丝不动** —— 只有 `widget_strip_cell.xml` 那 2dp 外边距生效了。原因是 **`RemoteViews` 只在宿主建立视图时 inflate 一次外层布局**，之后每次更新都是 `reapply` 到已有的视图树上；而每格那份**子** RemoteViews 因为每次都 `removeAllViews` + `addView`，才会重新 inflate。**外层布局的改动不重启桌面就看不到。** 当时为此白跑一轮、还顺着错误的现场下了两个错结论（先怀疑 aapt2 把 `paddingVertical` 丢了、据此改了写法），后来 `aapt2 dump resources` 拿到混淆后的文件名、`aapt2 dump xmltree --file res/Bb.xml <apk>` 一看，属性好好地在 APK 里。
  **护栏两条，都逐条反向验证过**：`widget_cell_block_guard_test.dart` 的「周条：布局让掉多少，`stripCellPx` 就得减掉多少」（把高度算式改回 `hDp - 20` 立刻红，报 `Expected: <6.0> Actual: <20.0>`；它解析时**先剥 XML 注释**，否则注释里那句反例 `android:padding="8dp"` 会把「不许用合并写法」那条断言自己打红 —— 第一次跑就是这么红的）；`widget_today_card_guard_test.dart` 的「『其他班组』那一行与 App 同一档字号」（把 Kotlin 改回 `11f`、或把 `widget_crew_chip.xml` 改回 11dp，各自打红一次）。**单测 1090 → 1092**；`flutter analyze` 0/0。

- **v0.11.23**（测试版 · 光谱接缝 + 桌面小组件再贴齐）：用户 v0.11.22 真机测完之后提的三条，
  **全部先用 adb 在真机上量，再动手**（一次性证据留在 `work/adb-shots/`，跑完即弃）。
  **① 那圈光谱的接缝（新问题）。** 沿透镜轮廓按角度采一圈色相：别的地方每 5° 只变
  0~11°，**唯独正右方那一步跳 62°** —— 与用户「右边两个颜色的交界处像是被一刀切了」
  位置完全对上。**成因在算式里**：`spectralSweep()` 走的是 `base.hue + hueLag + 300 * t`，
  绕 300° **没回到起点**，而 `SweepGradient` 的 `t = 0` 正是 **+x（正右方）** ——
  `t=1` 与 `t=0` 落在同一个屏幕方位上却差 60°，中间没有角度可以插值。改成 **360°**
  走满一圈，两端同色。`floor` / `span` / 亮峰锚点（225°，光从左上来）一个字没动。
  这是**唯一一处实现**（`liquid_lens.dart` 四个 painter 共用），所以底栏 / 分段器 /
  开关 / 日历那枚块 / 拖选水带一起好 —— 用户说的「类似的还有其他共用了这个动态光晕的
  地方」正是它。真机复测：接缝处那一步 **9.3°**。
  ⚠️ **顺手改掉一条面积阈值**：`彩边是「光晕」不是「等宽的带」` 断言带色相的像素面积
  ≥ 700，改成 360° 之后实测 **668**（掉的是接缝附近那一小片 —— 那里的色相现在正好
  等于主色，被「偏离 > 25° 才算」筛掉了）。**基线是当场重量过的**：把 `_paintHalo`
  临时短路再跑，只有 **15**，所以 600 仍然有 668:15 的鉴别力。
  **② 桌面小组件不再跟系统字号（用户报的那条，比描述更糟）。** font_scale=2.0 真机实测：
  今日卡的时间行**下半截被切**、「其他班组」整行不见、「1 项待办」徽章右半截出界；
  周条七列的「周四/周五」挤成一团。根因是**卡片尺寸编译期定死（`resizeMode="none"`）
  而字号写 `sp`** —— 尺寸不动、字在长，装不下就切。改法两件：9 张会渲染真数据的布局
  26 处 `textSize` 全部 `sp` → **`dp`**（`widget_preview_*` 是静态缩略图，豁免），
  渲染侧一律 `setTextViewTextSize(..., COMPLEX_UNIT_DIP, …)`；再按**真实尺寸**算系数
  缩放（月历格用行槽高、今日卡用卡内可用高），基准取 App 那一份（`cellDateSm` 13 /
  `cellShift` 12 / `tinyLabel` 11、`_cellDesignH` 55）。真机验：font_scale 1.0 与 2.0
  两张截图逐像素比，只有 ~1px 的整体位移（亚像素抗锯齿差），内容一个像素没变。
  **③ 月历周标题改单字。** 用户：「月视图跟 App 里的界面差别挺大，主要是外观方面」，
  第一条就是周标题 —— App 是「一 二 三 四 五 六 日」，桌面是「周一 周二 …」，宽度差一倍。

  那一列与今日卡读的是 `days[].weekday`，两处仍是「周一」（它不是网格、两个字更好读）。
  **④ 月历「今天」改回半透明块（推翻 v0.11.9 的一处决定）。** 用户点名：「问题就出在
  这格子的外观跟 App 里的差别太多了，尤其是那个半透明块」。当初做诚实的理由**前提已经
  没了** —— 同一轮把面板底换成了不透明页面色、格子换回白卡，块其实压在白卡上、与 App

  **机制（在 `flutter test` 里量出来的，不是推的）**：`MaterialApp` 每次 build 都会**命令式**发一次 `SystemChrome.setSystemUIOverlayStyle`（`material/app.dart` 的 `_themeBuilder`，值按主题深浅取）—— 所以 tab 那四页一直是对的；而 `AppBar` 会往树上挂一层 `AnnotatedRegion<SystemUiOverlayStyle>`，值是**由 AppBar 的底色推出来的**，而我们三个带 AppBar 的页面底色是 `Colors.transparent`（亮度 0）→ 被判成「深色背景」→ 推出**白图标**。`RenderView._updateSystemChrome` 每合成一帧都拿「最上面那层声明」覆盖掉 `MaterialApp` 那一发，于是**一进排班管理就变白**；退回来时那层声明随路由离开树，而它**一份都没找到就直接早退**（`MaterialApp` 那一发只在它自己 rebuild 时才发，pop 不会让它 rebuild）→ 白图标留在屏幕上。**「返回后也不恢复」就是这么来的**，也是它「与谁家的 ROM 无关、只与深浅档有关」的证据。
  **两条腿的修法，缺一不可**：① `AppBarTheme` 补 `systemOverlayStyle`（不补的话 AppBar 那层会盖住根部那层）；② `app.dart` 的 `builder` 里挂一层**常驻**的 `AnnotatedRegion` —— 任何一页的声明离开树，下一帧立刻被它顶回来，「返回后不恢复」从此结构上不可能。判据收进 `core/theme/app_theme.dart` 的 `statusBarStyleFor()` **一处**（只带状态栏那几位、**不碰导航栏**，照 Flutter 自己 `_systemOverlayStyleForBrightness` 的理由 —— 免得在 Android 14 及以下把导航栏涂黑）。响铃页是**恒深**的（`bgDark` + `isDark: true` 写死），单独给它一层白图标，顺带修掉一条既有缺陷（浅色档下它一直是深图标压在深色底上）。`values/styles.xml` / `values-night/styles.xml` 各补一条 `windowLightStatusBar`，只管**首帧之前**那一小段窗口。新用例 `status_bar_style_test.dart` 四条，判据落在**真正发给系统的平台通道调用**上（不是「树上有没有一个 AnnotatedRegion」—— 后者对「AppBar 那层盖住根部那层」完全无感）；**三条护栏逐条反向验证过**：去掉 AppBarTheme 那条 → 第 1 条报 `Actual: 'Brightness.light'`；去掉根部那层 → **只有**「响铃页退回来」那条红；把响铃页那层改成浅色 → 那条的进去断言红。⚠️ **写用例踩到的一条**：`SystemChrome.setSystemUIOverlayStyle` 对「与上一发相同」的样式会**静默丢掉**，而那个「上一发」是**静态**字段、**跨用例不清** —— 同一文件里第二条用例会一发都收不到、断言变成句空话（第一次写就撞上 `Actual: <null>`），所以开头先推一发哨兵再冲掉。单测 904 → **908**。
