- **v0.13.26（测试版 · 滑块跟手：抓取偏移按按下点算）**
  **① 现场**：2026-11-25 用户真机 —— 快速滑动底栏时透镜落后手指一大截、老是乱跳，只有手一直压在滑块上才跟得住。上一版按「滑动不该提起」修是误判，本次已恢复原样。
  **② 根因**：`dragStart` 用「拖动被识别那一刻」的坐标算抓取偏移，而 Flutter 要等手指走过识别阈值（约 18dp）才发 `onHorizontalDragStart` —— 这段位移被**永久**吃掉。用例量到透镜中心落后 1.11 格。
  **③ 修法**：`press()` 按**按下点**算好偏移存进 `_pressGrabOffset`，`dragStart()` 直接用；没有按下记录的拖动才退回旧算法。
  **④ 恢复**：升程目标恢复 `_dragging || _heldLongEnough`，删掉上一版为此加的 2 条用例（同期下调 `EXPECTED_TESTS`）。
  **⑤ 数字**：新增 1 条「快速滑动不落后」用例；单测 1428 → **1427**；`flutter analyze` 0 issue；版本 `0.13.25+212` → **`0.13.26+213`**。

- **v0.13.22（测试版 · 闹钟取证与自愈：启动快照 / 退出原因 / 巡检不被推后）**
  **① 现场**：2026-11-25 一加 PLK110（Android 16）用户报「早上 10:00 的班次闹钟没响」，是 11-24 16:00 之后的第二次。诊断包能证明排定侧完全正确 —— 按他的排班复算，08:00:03「排 206 / 撤 79」、08:18:46「排 206 / 撤 0」、10:06:05「排 205 / 撤 1」三个数字与「下一跳」里的 id **逐条命中**（撤的 79 条 = 每天换号的相位差：7×6 夜→休 + 7×3 中→休 + 8×2 白→中）；10:00 那条（id=61）两次 `setAlarmClock` 都成功、没有取消记录、清单里活到 10:06。而那一刻连 `AlarmReceiver.onReceive` 都没有 —— **进程在整个时间窗里一次都没起来**，不是「响了没听见」。
  **② 诊断包拍不到关键状态**：`reschedule` 一跑就把清单里过期的那条当陈旧记录撤掉，实测进程起来 **约 180ms** 就发生 —— 之后导出的 `alarms.json` / `alerts` 全是「改过之后」的。新增 `AlarmScheduler.startupSnapshot`：在 `MainActivity.onCreate` 里、**`super.onCreate` 之前**（引擎起来之前）写「系统下一跳（`AlarmManager.nextAlarmClock`）/ 清单最早（+是否已过期）」。读法：两边**是同一时刻**（哪怕已过期）＝记录还在、**投递被拦**；系统更晚或「无」、而清单那条已过期＝**记录被删**。`nextAlarmClock` 是全系统的，所以只有「比我们更晚」这一侧是确定判据。
  **③ 分清强行停止与冻结**：`AlarmScheduler.lastExitDigest` 用 `getHistoricalProcessExitReasons(packageName, 0, 1)`（API 30+ 加 guard）记一行：`REASON_USER_REQUESTED(10)`＝强行停止 / 一键清理（**会撤掉本包全部闹钟**）、`REASON_FREEZER(14)`＝系统冻结器。常量值写死（好几个 `REASON_*` 是 API 31 的字段，引用会被 `NewApi` 拦）。
  **④ 巡检不会按时跑（真 bug）**：`AlarmScheduler.reconcile` 收尾无条件 `ensureScheduled()`＝`now + 6h`，于是 03:12 排的 09:12 被 08:00/08:18 两次重排挤到 14:18 —— 10:00 丢的那条**没有任何自愈机会**，用户越常开 App 巡检越不会跑。现在 `AlarmWatchdog` 记住「已排到几点」（`alarm_watchdog` prefs），`scheduleAhead` **只往前挪、不往后推**；`nextTarget` ＝ `min(now+6h, 最早那条闹钟 - 1h)`，下限 `now+10min`（防「巡检自己排到 T-1h 之后又排 T-10min」的自激）。`BootReceiver` 走新的 `forceScheduled`（重启后 AlarmManager 已清空，落盘的时刻不作数）。
  **⑤ 一加 / OPPO 入口**：`ColorOS / OxygenOS` 的「自启动管理」页（`com.coloros.safecenter` / `com.oplus.safecenter` 四个组件 + 耗电管理两个兜底）解析进 `colorOsStartupPage`，抽了共用的 `resolveFirst`；「我的 → 权限 → 后台与开机」在非小米 / 非三星机型上多一行「自启动 / 后台运行（一加 · OPPO）」，打不开落回应用信息页。
  **⑥ 文案**：诊断包 `README.txt` 的三分法重写为「先看启动快照那两行 → 再看撤 N 条」。旧第 2 条（清单有、日志无 onReceive）在导出时**永远不成立**，因为导出必须先开 App、开 App 第一件事就是重排。帮助页「闹钟偶尔有一两次不响」同步改写并补一加一档。
  **⑦ 数字**：新增 `app/test/alarm_evidence_guard_test.dart` 6 条（取证在 `super.onCreate` 之前 / 快照读 `nextAlarmClock` / 退出原因两档 / 巡检不推后且提前 1 小时 / ColorOS 入口 / README 教法），单测 1408 → **1414**；`flutter analyze` 0 issue；版本 `0.13.21+208` → **`0.13.22+209`**。

- **v0.13.11（测试版 · 修 HarmonyOS 3.0 冷启动闪退）**
  用户 2026-11-11 反馈：荣耀 10（COL-AL10）与畅享 20 Pro（DVC-AN20）装上 v0.13.10 后**一开就闪退**，v0.13.9 正常。

  **修法**：① 门槛逐条按 `api-versions.xml` 校准 —— `areEffectsSupported` / `areAllEffectsSupported` / `areAllPrimitivesSupported` / `startComposition` / `VibrationEffect.Composition` 都是 30（v0.13.10 把原语门槛写成了 31，反而漏掉了 API 30 这一段），`PRIMITIVE_THUD` 31，`createPredefined` 29；② 低于门槛一律不调，`logCapabilities` 在 API 30 以下只记「未知」；③ **所有 `catch` 从 `Exception` 改成 `Throwable`**（`play` 入口也整段兜住），缺 API 的 `Error` 从此不会再冒到主线程；④ 顺手补上 Android 8 / 9 的路径：那两版没有 `createPredefined`，原来点一下就会抛同样的 `NoSuchMethodError`，现在改发 20ms 单次。
  **验证边界**：本机是 API 34，复现不了「API 29 上崩」；两台真机由反馈用户装 v0.13.11 验。单测 1294 不变（没动 Dart）。

- **v0.13.5（测试版 · 修导入后重启）**
  真机验证 v0.13.4 的导出/导入时发现：点「立即重启」后 `Process.killProcess` 把进程杀掉，新 Activity 还没建起来，系统不会替我们拉起。Android 14+ 还会把「进程已死 + PendingIntent 拉起 Activity」判成后台启动并 `BAL_BLOCK`（logcat 原文 `Background activity launch blocked`），AlarmManager 也救不回来。最终做法：**不杀进程**，用 `FLAG_ACTIVITY_NEW_TASK | FLAG_ACTIVITY_CLEAR_TASK` 从当前前台 Activity 启一个新任务 —— 旧 Activity 销毁、旧 FlutterEngine 释放，新 Activity 建新引擎、Dart `main()` 再跑一遍，导入的库在打开数据库之前完成替换。整个过程都在前台，不受后台启动限制。
  同时，恢复 prefs 后把 `lastSeenVersion` 写成当前版本、`onboarded` 置 true —— 否则备份里的旧版本号会让导入后第一眼弹出「版本更新」。
