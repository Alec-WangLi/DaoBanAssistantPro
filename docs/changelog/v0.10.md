- **v0.10.22**（测试版 · **动画与流畅性第二轮：真正的瓶颈在光栅线程**）：起点是真机测完 v0.10.21 之后的一句「功耗应该是降低了，但页面流畅性感觉好像还是没有变化。比如在编辑排班界面滑动时，能感觉到页面不知道是掉帧还是抽帧，反正看着卡卡的」。**这一轮的第一件事是在真机上把「卡在哪」量清楚**，而不是继续猜。
  **① 量出来的结论把上一轮的方向直接推翻了。** 探针（`app/tool/probe/`，跑完即删）量到：屏幕**全程 120Hz ⇒ 帧预算只有 8.33ms**（不是 16.67）；**build（UI 线程）p50 只有 0.52ms**；而 **raster（光栅线程）p50 4.19ms、p90 13.10ms、13.4% 的帧掉拍**。**上一轮优化的是 UI 线程（436 → 42 个 widget/帧）—— 那里已经没剩什么可优化，而 GPU 那一侧一个字节都没碰过。**这就是「功耗降了、流畅没变」的全部原因：省下的是 CPU，掉的是 GPU 的帧。**教训**：优化之前先量「哪一侧」，不要拿一个已经很好的指标当成功。
  **② 贵的是 `BackdropFilter` 那条渲染通道本身，不是滤镜算什么。** 同一段滑动，把整条 `BackdropFilter` 摘掉（**填充配方一个字节不动**）raster p90 **13.10 → 2.37ms**、掉拍 13.4% → ~3%；而**只留模糊（σ 仍 18）是 7.92、只留饱和度矩阵是 8.21** —— 所以「把 σ 调小」「简化那个 compose」都不解决问题。于是把 `GlassPanel` 上**被捆在一起的两件事拆开**：`enableBlur` → `translucentFill`（用哪支填充）+ 新的 `blurBackdrop`（挂不挂那条通道），**`GlassTile` 恒为 `blurBackdrop: false`**。全仓扫下来仍开着模糊的调用点**只有 8 处、全是 `GlassTile`**（日历 2 + 编辑排班 6），所以一处收口；`GlassBlur`（按钮 / 提示条 / 液态轨道 / 导航胶囊）与液态透镜一律不动。**踩过的一个坑**：第一版探针把 `glassBlurDisabled.value` 写在 `app.main()` **之后**，被 `main()` 里的 `recomputeGlassTiers()` 覆盖回去 —— 白量一轮，还差点得出「模糊不是原因」的错误结论。**教训**：任何「开关到底生效没有」的实验，都要有一条**落在采集窗口里**的日志自证（`CFG ...`）。
  **③ 观感是量出来的，不是推出来的。** 同机同包连渲两遍**噪声本底为 0**（逐字节相同），再比去掉模糊前后的两张图：全 app 除响铃时钟假差异外**最大差异 16/255、占比 ≤0.07%**，差异形状是卡片内部一片弥散的极淡色偏（背景那层「真实饱和度」没了）与 1px 描边抗锯齿；放大 12/20 倍才看得清，并排出图看不出区别。**所以这一条不是取舍，是白捡的。**
  **④ 顺带收掉上一轮明确留下的六项**：`appSettingsProvider` 收窄成 `select`（**拨一下触觉开关不再把整个 App 重建一遍**；「我的」页是例外 —— 五个开关都画在它身上）；`L10n` 的 `DateFormat` 按 (模式, 语言) 缓存；光晕暂停判据从「手指按着」改成「**这一帧有没有东西在产出**」（判据落在 `_publishFrame` 被没被调上，一个条件同时覆盖「飞行 / 拖动有位移 / 带子淌 / 换月」四件事），帧末用 `addPostFrameCallback` 放行而不是 `Timer`；`WidgetService.push` 加 in-flight 守卫（`finally` 放开闸门，且 `resetPushCache` 要连它一起清）；`AlarmStore` 内存镜像（**只镜像「读」这一半，写仍然写穿** —— 合并落盘那一版被最终审查否掉了，见下）；**响铃 15 分钟没人管自己停**；小组件刷新默认退非精确。
  **⑤ 两处量到之后决定不做的**：**切 tab 保活** —— 切一页重建的 UI 线程代价最多 **2.4ms**（预算 8.33ms），保活省的就这一点，却要四页的 widget 树与数据流常驻内存；真正贵的是切过去之后那几帧的光栅，保活解决不了。**把改动扩到液态档的分段器 / 开关** —— 归因把它指出来了（剩下 ~1.0ms p50 / ~3.8ms p90 全在它们身上），但**掉帧已经落到地板**（3.2% vs 地板 2.8%，而地板 p90 只有 2.15ms ⇒ 剩下的掉拍不是 raster 造成的），再往下走只买到余量、买不到流畅度，而 `LiquidTrack` 同时是**底部导航胶囊**的载体、动它就碰仓库里「底栏逐像素不变」那条硬验收（为它付过四轮代价）—— **交用户拍板**。
  **⑦ 最终审查（全新上下文、最贵那一档模型，审整个分支 9 个提交）抓出四处** + 五处小项，一轮修完：
  **① 桌面小组件在换主色 / 换主题档时不再重推**（**真回归**，且正是 v0.10.21 修过的同一类）：`home_shell` 推快照的那个 `listenManual` 被收窄成了 `select((s) => s.language)`，而快照里**带着** `themeMode` / `accent`（原生渲染端拿它们决定今日高亮、胶囊配色与深色判定）—— 于是换主色、换主题档之后桌面那张卡停在旧配色上。**教训**：`select` 收窄要按**那个消费者真正用到的东西**收，而不是按「这一页长什么样」收；这一处是**推送触发器**、不是重建触发器，而规格里那张收窄表把它当成后者了。已加用例 `home_shell_nav_test.dart` 的「换主色：必须重推快照」（反向验证过：改回只 select 语言立刻红）。
  **②③ `AlarmStore` 的延迟落盘有两个真问题，整条撤掉、改回写穿**：**竞态** —— 延迟那一发跑在主线程 `Handler` 上、**不在任何锁里**，而 `clear` / `clearEntries` / `clearQuiets` 是从**后台线程**调的（`cancelAllNativeAlarms` / `cancelTodoReminders` 都是 `Thread{…}.start()`），两边一起动镜像与同一个 prefs 键 ⇒ 丢更新、或者**把刚清掉的清单写回去**（症状是「重启后冒出幽灵闹钟」）；**丢失窗口比账本里写的宽** —— `reschedule` 开头就是 `clear()`（同步把键删掉），那一刻盘上是空的，而新的那批要等静默期才落。**这一条最终选择用「简单」换「17ms」**：写穿实测 60 次 put / 64 次落盘 / **18ms**，而延迟版是 1ms —— 但在一个「重启不该丢闹钟」的 app 里，为了 17ms（总耗时 600ms 的 3%）引入跨线程共享状态划不来。**内存镜像保留**（那一半没有副作用）。写穿版真机复验：30 条 → 重装触发 `MY_PACKAGE_REPLACED` → `BootReceiver` 读回 **30 条**。
  **④「换月也进光晕暂停判据」第一版是句空话**：`AnimatedSwitcher` 整个转场用的是**同一个** `_MonthPane` 实例，子树不重建，所以 `_buildGrid` 里那处 `_publishFrame` **只在 `setState` 那一帧跑一次**，不是每帧 —— 而我原来的注释写成了「换月那个每帧重建整页的 AnimatedSwitcher」。那条用例也**没有鉴别力**：换月动画（`durMed` 220ms）比光晕一步（`durSlow` 340ms）还短，即使完全不暂停也看不出差别。**修法**：加一个 `_MonthRollWatcher`（`AnimatedBuilder` 跟着转场的 `animation` 每帧回调一次），换月于是成了一个正经的运动源；用例的判据落到「本来该走一步、却没走」那一刻（推 384ms —— 不暂停的话 340ms 就该走了），**反向验证过：把那个回调掐掉，光晕在换月里走了 0.013、当场红**。
  **⑤ 另外三处小项**：`WakeLock` 的 10 分钟超时**短于**自停的 15 分钟（「仅震动」那档没有音频在放，锁一掉 CPU 可能睡下去，`postDelayed` 要等下次有人唤醒才跑 ⇒ 一直震）→ 改成 `autoStopMs + 60s`；两处注释写反 / 没写（手动关闭那条路其实**也会**走到 `_onRingingChanged` 里那一次 `popUntil`；`_ringingUp` 带来的「第二个闹钟不叠层」是一处行为变化，补上说明）；`expect(layers, lessThanOrEqualTo(0))` → `0`。
  **⑥ 另一处量出来的既有开销，记录在案**：`cancelAllNativeAlarms` 盲扫 ~1600 个 AlarmManager 取消（`for (id in 0..600)` / `10000..11000` / `99990..100000`），占掉一次重排约 **600ms**。不在本轮范围内。
  **数字**：测试 807 → **824**，工装 349；四个 tab 的 raster p90 全部落进 2.7ms（日历 10.36 → **2.26**、闹钟 9.77 → **2.27**、待办 6.48 → **2.50**、我的 3.45 → **2.66**），超预算的帧从 1~14.5% 降到 0~1.4%；编辑排班页 raster p90 13.10 → **5.98ms**、掉拍 13.4% → **3.2%**（未达 spec 的 ≤4ms，原因见 ⑤）。

- **v0.10.20**（测试版 · **动画与流畅性第一轮**）：起头是真机测完 v0.10.19 之后的一句「所有动画、所有界面动画的流畅性，以及功耗，有没有优化空间」。规格 `docs/superpowers/specs/2026-10-10-smoothness-first-pass-design.md`，计划 `docs/superpowers/plans/2026-10-10-smoothness-first-pass.md`（11 个任务，原生执行）。**这一轮的全部依据是四个一次性探针量出来的数字**（`app/tool/probe/`，跑完即删）—— 先说结论：**最大的三处都不在「液态玻璃画得贵」上**，而在「每帧顺带做了多少别的事」上。共享液态件（底栏 / 分段器 / 开关 / 透镜 / 水带）本身写得克制，**不每帧重建整页**（`_onLensChanged` 那三处都有「值真变了才 setState」的护栏）；每屏的 `BackdropFilter` 也只有 1~2 层。
  **① 液态档把每帧动画状态放进了整页的 `State`（最大的一处）**：实测「点一个日期起飞行」时一帧重建 **436** 个 widget，而标准档同一个动作只有 **6** 个 —— 差别就在 `_flightPos` / `_vx / _vy` / `_rangeTipPos` 住在 `_CalendarScreenState` 里，每帧 `setState` 把顶栏 + 42 格 + 信息卡全带上。修法是**两个 `FrameNotifier`**（`_lensCenter` 挤压场中心、`_blockFrame` 那枚块的位置/速度/速度是否活的）**只从一个 `_publishFrame` 出去**，读的那两层各建在**自己那一小块**上。**Task 6 与 Task 7 有意拆开**：6 只把 42 格那条路换成 `LensWarpScope`（等价换路、**画面逐像素不变**，238 张一张不差），7 才是收益落地（436 → 42）；合在一起的话，出图一旦有差异就分不清是搬运错了还是外置错了。
  **② 规格里有一个前提是错的，被用例当场抓住**：规格与计划都写「`ValueListenableBuilder` 自己在 build 时读 `.value`，所以帧内静默写照样这一帧生效」——**Flutter 3.47 不是这样**：它把值 `late T value;` 缓存在 State 里、只靠 listener 刷新，静默写它**看不到**。为此新增 **`FrameBuilder`**（`core/frame_notifier.dart`，同 API 但每次 build **现读**），`LensWarpScope` 与块那一层都走它。**这条是 TDD 抓的**：`lens_warp_scope_test` 的「静默写…下一次 build 读到的就是新值」当场红。
  **③ 实施中自己造的两个 bug，也都是用例抓的**：把 `sized`（透镜那棵树）建在 `FrameBuilder` **外面**再传进去 ⇒ 同一个 widget 实例不会被重建，透镜被**冻在第一帧的速度**上（`滑行中：彩边亮起来`当场红）；两条新护栏第一版把 `debugProfilePaintsEnabled` 的还原写在 `addTearDown` 里 ⇒ 框架自检跑在 tearDown **之前**，报「测试改了渲染调试变量」（工装 `tearDownVisual` 的注释里早写着这条，我没有先读它）。
  **④ 光晕：从「整页的祖先」改成「页面旁边的兄弟层」**（`CustomPaint(painter:, child: 整页)` → `Stack[RepaintBoundary(CustomPaint), child]`），一次 tick 重绘的绘制节点 **139 → 1**。**为什么不给 child 加 `RepaintBoundary`**：那会把「边界外的动静、边界里的模糊跟不跟得上」变成一条依赖引擎行为的假设，跟不上就是**玻璃里的模糊被冻住**；兄弟层不依赖它。**这条量过**（一次性探针借工装取像走真光栅）：光晕走一步后，卡片**外**变了 559 点、卡片**里**变了 237 点、最大差都是 3 —— 跟着动。另加 `pauseWhen`：**有东西在动时把光晕停住**（`_t` 不推进 ⇒ 恢复时不跳），拿掉「拖动时每 340ms 一次固定掉帧」——**这是这一轮唯一一处改变可观察行为的地方**，已与用户逐条确认。
  **⑤ 另外四件「白付」**：`lunarOf` 加按天缓存（22~41µs/次 × 42 格/次重建）；排闹钟的**逐条日志收成一条汇总**（一次 `rescheduleAll` 99 次跨端里 46 次是它）；小组件快照**按内容去重 + 五个触发合并成一处 340ms 尾去抖**（指纹取**输入**而不是 JSON —— 里面带 `genAtMs`，直接比 JSON 永不命中；**失败不许记成已推**，否则「装完新版先打开一次 App」那条兜底重试永远不再试）；启动去掉 `tz.initializeTimeZones`（`latest_all` 全量 IANA 库、21ms、跑在首帧前，而全仓从来没有一处 `zonedSchedule` / `TZDateTime`）。
  **⑥ 三条数字护栏 + 一条键护栏**（都要求**先看着它红一次**）：`calendar_frame_budget_test`（一帧重建 ≤ 80 液态 / ≤ 20 标准档，反向验证 498 > 80）、`glow_layer_test`（光晕那一帧绘制节点 ≤ 8，反向验证 139 > 8）、`alarm_reschedule_budget_test`（跨端 ≤ 55，反向验证 99 > 55）、`widget_push_dedup_test`（同一份只发一次 + 失败要重试）、`startup_path_guard_test`（扫源码：首帧前不许再有 `initializeTimeZones`，带两条自证）。
  **⑦ 一处「计划的设计会引入静默 bug」，就地收窄**：规格让「本月统计 / 有没有班表在管 / 有没有调过班 / 有没有未完成待办」四样共用一个按月缓存，但 **`chain.cacheKey` 不含按天改班的覆盖**（`_sourceKey` 只覆盖「会影响信息卡高度的方案特征」）—— 把 `hasOverrideHint` 关进缓存，「调整一次班次」之后那个键不变 ⇒ 「已调班」胶囊要预留的高度**永远不更新**。改成只缓存真正贵的那两样（`tally` / `hasNoSchedule`），两个布尔照旧现算；键里**必须有语言**（反向验证：删掉 `L10n.isEn`，换语言那条立刻红）。
  **⑧ 顺手修好一条既有缺陷**（与本次改动无关、在 v0.10.19 的干净树上一样红）：「挤字只变换绘制、不改布局」**锚在「今天」那格、却断言 `day-card-2` 被挤** —— 这两格在月历里相邻**只有每月头两天成立**，所以它从月初第三天起就一直红。改成与同文件拖选用例同一条做法：固定锚点 8/9（月初偏移为 6 时取 9/10）。
  **⑨ 独立审查（全新上下文的 agent 跑整个分支 15 个提交）抓出三处，v0.10.21 一并修**（它自己写探针复测过，我逐条复现后再改）：**① 小组件去重指纹漏项**（Critical，相对 v0.10.19 的回归）—— 指纹复用了 `chain.cacheKey`，而那个**不含按天改班 / 周期 / 班组错位 / 基准日，也不含语言** ⇒「调一次班」或「换一次语言」之后**不重推**，桌面小组件一直画着旧的（实测：改前各只有 1 次推送）。改成**比内容本身**（`genAtMs` 换成常量再编码一次）。**②「本月统计」缓存键漏项**（同一个 `cacheKey`）—— 「调过班之后那一行还是旧数字」（实测 `早8 中8 夜8 休7` vs 真值 `早7 中9 …`）。新增 `ScheduleChain.rotationKey`（基准日 / 周期 / 班组错位 / 覆盖表**按键排序**再拼），`_factsFor` 改用它。**③ 拖选那条带子仍在每帧重建整页** —— `onTipPos` 每帧 `setState`，实测 **509** 个 widget/帧（比滑行那条路还狠），而规格 §4.1 本来就把 `_rangeTipPos` 列进了要外置的四个字段里；改成走 `_publishFrame`，护栏补一条「长按拖选」的臂。**教训写下来**：`cacheKey` 是**信息卡高度**的指纹（它自己的名字与注释都这么写），这一轮悄悄给它加了两个消费者，**两个都栽了** —— 要判「排班变没变」用 `rotationKey`。
  **数字**：测试 773 → **803**，工装 349 条不变；`tool/visual` 逐张比 **228/238 逐像素相同**，10 张差异**全在响铃页的时钟带**（差异包围盒 840×1800 上 `445,494–633,623`，既有的「时钟跳字」假象）。四个探针的前后对比与全部裁定记在 `.superpowers/sdd/2026-10-10-smoothness-first-pass/progress.md`（工作区，随最终提交删除）。

  **① `toPath()` 的竖直兜底分支是「上圆 + 下圆 + 中矩形」三个子路径并起来的。** 填色对，但**描边会把三段边界全画出来**（包括互相重叠的内部接缝）—— 而四层光谱**全是描边**，于是钮的内部出现横线与内侧弧。用户原话：「彩边贴错位置了……它已经穿到滑块里边了，而且还不规则，也不贴边」。**这不是本轮引入的：v0.10.10 的开关按住时宽 29.69 < 高 33.38，真机上一直在踩**；底栏在窄窗（`itemW 39`）按住时同样。判据：`shape.toPath().computeMetrics().length == 1`。

  **③ 修法：竖直档改成「按目标宽搭好、再纵向拉伸」**（`_verticalStretched`）。⚠️ **别改成「整体转 90°」** —— 转过去之后局部坐标的左右两端会落到屏幕的**上下**两头，「头大尾轻」就变成「上大下小」，而用户把这条说得很死：「头重脚轻肯定不能是上下的，肯定要左右」。**拉伸**两样都保住：落在屏幕上就是「两枚高低不同的椭圆 + 外公切线」。另一条：局部那两个圆的半径**不能**直接用 `_cap`（= 宽/2）—— 拉伸不能把圆变回来，`rl + rr ≥ 宽` 时尾部整个落进头部圆里、轮廓退化成一个圆，而且 `mx` 正好等于 1、踩 `arcTo` 扫 2π 那个坑；改成 `capV = 宽/2 × (1 − 0.175·stretch)` 留出余量，`stretch = 0` 时余量归零（局部是正圆，靠 `d` 钳位兜住）。

- **v0.10.7**（测试版 · 彩色边缘 = 折射光晕）：v0.10.6 真机反馈两条，**第一条又是算式里读得出来的硬缺陷**，第二条是取舍（用户明确要「往外也散一点」）。
  **① 彩边只有左边和上边有。** 用户原话「不管我往左滑还是往右滑，感觉只有左边和上边有彩边，右边和下边缘都没有」。那圈颜色是一道**扫掠渐变**，亮度写在算式里：`α = (0.06 + 0.86·toward²)·motion`，而 `toward = (1 + cos(角度 − 225°)) / 2` 的峰值锚在**左上**、并且**又平方了一次**。代进八个方位：左上 **0.92** / 左 0.69 / 上 0.69 / 右上 0.28 / 左下 0.28 / **右 0.08 / 下 0.08 / 右下 0.06** —— 后三档等于没有颜色。它画在**固定的屏幕方位**上，所以与往哪边滑无关（用户观察到的正是这一点，也正是这条判据的鉴别力所在：跟着运动方向走的写法过不了）。修法：把 `floor/span/pow2` 抽成参数，彩线改成 `0.58 + 0.42·toward²`（**四面八方都有色，左上只是略亮**），整份渐变抽成顶层纯函数 `spectralSweep()` 供四层共用。
  **② 「像在边缘加了一层彩带」→「折射的光晕」。** 拆成四件可测量的属性：**等宽**、**等亮**、**硬边**、**贴在表面**。「彩带」就是这四件凑出来的，自然界里没有等宽的彩色光带。改法：`_paintHalo` 用同一条扫掠渐变画**又宽又糊**的两层（22px/σ6 与 12px/σ3，色相各偏 −30°/+22° = 色散把光谱**摊开**），挂在本体那层 `ClipPath` 底下 —— **外半边被裁掉，于是只往玻璃里散**；多出来的 `_LensGlowPainter` 是**单开的一层**（与浮起阴影同层位，在裁剪之外）负责往**外**散（24px/σ7），因为本体根本画不到轮廓外面。彩线从 4.5 收到 2.4、白芯从 1.2 收到 1.0 且浅色 0.85 → 0.70（它们自己也是硬边）。四层与 `motion` 共用一个门：**静止时一个彩色像素都没有**。
  **两条判据上的自我纠错**（都是反向验证时才现形的，值得记）：① 第一版用「色相偏离主色 > 25°」判「这里有没有彩边」——**判不出来**：色相沿轮廓走 300°，**在正右那一点正好绕回主色**，偏离恒为 0。换成「与**同一枚透镜但不画环**那一帧做差」。② 那个对照帧第一版写的是 `velocity: 0` —— 那会**连带把形状也改掉**（`stretch` 是从速度推的），于是两帧到处都不一样、判据变成永远为真。必须把 `stretch` 显式钉住、速度只留一个正值（`velocity: 1`，`movingRight` 一致、`motion` 落在门下）。③ 做差还要带一个**可见门槛**（单通道 ≥ 8，与 `scripts/diff_visual.py` 同一个值）：底面压到 0.06 时像素仍会动 1~2 级，不设门槛一样没有鉴别力。三条都反向验证过（把光晕与外溢层一起关掉 → 「右边一个像素都没被彩边影响」；把外溢那层的门从 `motion` 改成 `lift` → 静止时轮廓外有 16 个像素随主色变）。
  **标定**：彩边带色相的**面积 277 → 2092 像素、厚度 2 → 7px**（判据「厚度必须远大于那条细线」就是「光晕不是等宽带」的可断言形式）。`00_home_shell_*` 五张与 v0.10.6 基线**逐像素相同**（10 张 home_shell 里只有 5 张液态档变了）。

  **① 浅色下「胶囊左边很浅、几乎看不清，右边有镜片效果」** —— 用户猜是背景渐变光，**不是**。沿胶囊水平中线取样：胶囊**外侧**左右两边都是 `rgb(254,247,255)`，一模一样（而且 `FlowingBackground` 只在日历页与响铃页，另外三个 tab 根本没有它）。差在**边光自己**身上：`glassRimProbe()` 配的是 `topLeft → bottomRight` 的**对角**线性渐变，这套配方是照**近方形卡片**量的（在卡片上读作「左上高光 + 右下收边」），可底栏胶囊是 **372×64（约 6:1）**，渐变轴几乎就是水平的 —— 于是退化成**左端纯白、右端 10% 黑**。左边那圈 **α=1.0 的纯白**既压在近白的底上看不见，又把胶囊自己那条 14% 的深色轮廓线（`navBorder`）**整个盖掉**。实测：改前左缘 `rgb(251,250,251)` / 右缘 `rgb(203,199,204)`；**改成竖直轴**（t 只跟 y 有关 → 左右结构性一致、与宽高比无关）并把浅色峰值从 1.0 压到 0.48（不再盖掉轮廓线）之后，左右各为 **218 / 216**，而胶囊外底色两侧都是 245。护栏在 `glass_tier_test.dart`（光栅化取左右两条边的**最暗像素**，断言差值 ≤ 4 且左缘比底色暗 ≥ 20；**反向验证过**：轴改回对角立刻红，报 `251 vs 203`）。`CapsuleRimPainter` 与 `glassRimProbe*` 全仓只被 `liquid_lens.dart` 用、唯一调用点是 `_buildLiquid` —— 标准档一个像素不动。
  **② 「折边」与「凸出」在动起来之后是坏的**（扫 `LiquidLensShape` 的 (lift, 速度) 参数空间扫出来的）。原早退条件是「**两个端头半径都**大于胶囊半高」，而速度一上来后缘半径（`×(1 − 0.35·stretch)`）必然先掉下去 —— **整条折边被一票否决**。实测 lift=1 时超过约 **150px/s** 它就完全不画，而常态拖动是 300~1000px/s：**这个效果只在「按住而且手指不动」时存在**，恰好是唯一不会去拖的状态。同一张表还照出第二件：`height = (基准 + 2·凸出·lift) × (1 − squash·s)` 把压扁**乘在凸出上**，squash 还是 0.12 的版本里 700px/s 时透镜高 **63.4** 而胶囊高 **64** —— **透镜整个沉回胶囊里面**，「按住」这个动作的全部读感就在那零点几个像素上。修法：外扩**加在压扁之后的基准上**（squash 一并收到 0.08），折边的门开在「**至少一端**够到」＋够不到的那端半径**钳到相切**＋按凸出量**连续淡入**（`lensEdgeFade`）。几何判据抽成纯函数 `refractedCapsuleEdge(shape)`（原来整个住在 painter 里，失败方式只有出图才看得见）。护栏三条，都反向验证过；其中「凸出量恒等于 `2×navLensProtrude`、**与速度无关**」是**差值**断言 —— 第一版只写「还高于胶囊」，squash 收到 0.08 之后改回乘法顺序照样绿（**这条是反向验证时才发现的**）。
  **③ 120Hz 上速度被算成一半**：`_onTick` 里 `seconds = max(dt, 16ms)` 那个地板本意只是防「除以一个极小的 dt」，可 **16ms 正好是一帧 60Hz**。这台机器 dt ≈ 8.33ms，被 max 抬到 16ms → 速度**恒为真实值的一半**；帧间隔在 8.33/16.7 之间一跳（可变刷新率），同一根手指就算出两个拉伸量 —— 这就是用户说的「像帧率不够」。算式搬进纯函数 `lensVelocityStep`，护栏断言「同一段位移在任何帧率下算出同一个速度」（反向验证：装回地板 → 120Hz 那路掉到 **156.25**，60Hz 是 300）。
  **④ 彩边「一动就满」**：环的亮度原先是 `× stretch`（= 速度 / `lensVelocityRef`），要甩到满速才满亮，常态拖动长期停在半亮 —— 用户原话「彩色边缘不明显……本来它这个效果范围就不大」。门换成新的 `motion`（`lensRingFullSpeed = 60px/s` 就封顶），峰值 α 0.80 → 0.92（实测彩边面积 229 → **277** 像素）。**`stretch` 与 `motion` 因此分了家**：形变跟速度走（头大尾小），环只问「动不动」——喂同一个量就只能二选一，而用户两轮说的正是这两件事。`_LensBodyPainter.shouldRepaint` 补比 `motion`（形状可以一模一样而环在变）。
  **⑤ 形变改走弹簧**：瞬时速度是一根毛刺，直接拿它当形变就是「起步啪一下到满、停下啪一下归零」——机械感的来源。新增 `_stretchSpring`（`lensStretchOmega/Zeta` = 30 / 0.62，过冲约 9.5%、包络衰减到 2% 约 210ms），复用已有的 `LiquidLensSpring`。`lensVelocityRef` 700 → **900**：那个 700 其实**从来没生效过**（被 ③ 的地板减半成 1400），地板撤掉之后 700 才会真正落到手上、比用户见过的任何一版都强一倍，所以取中间值。**这是本轮唯一一个凭手感定的数。**
  **工装的盲区（这一条比上面任何一条都值得记）**：`40_nav_lens_dragging` 是在 `beforeCapture` **之后**经 `settleVisual`（60 帧）再取像的，而手指停在原地 → 透镜速度衰减到 0。**光谱环、折边、形变全都由速度驱动**，所以那一屏拍到的其实是「按住但静止」—— 这个档位唯一一切都正常的那个状态。**「彩边看不出来」因此从没在任何一张图上现形过。** `pumpScreen`/`renderScreen` 新增 `settleAfterCapture`，并补了 `41_nav_lens_moving`（取「还在动」的那一帧，速度**故意取慢的** 312px/s —— 取快了旧代码的环本来就是满的，那条屏单刚好会盖住要看的那个变化）。
  **验收**：全套 603 → **612** 条，工装 307 → **312** 条；`00_home_shell_*` 五张与基线**逐像素相同**（224 张里 209 张零差异，其余 15 张全是液态档两屏 + 响铃页那 5 张**时钟跳字**——差异框固定为 `(547,494)-(634,623)` 那一小块，已知假象）。

- **v0.10.3**（测试版 · **底栏液态玻璃重做**）：v0.10.2 真机测完之后用户的判断是「bug 还是挺多的，重新理一下思路」，并要求先梳理开源实现、再给「符合本项目设计理念」的方案。规格 `docs/superpowers/specs/2026-10-01-liquid-nav-redesign-design.md`，计划 `docs/superpowers/plans/2026-10-01-liquid-nav-redesign.md`。
  **一次结构性的重做，不是修 bug。** v0.10.1/0.10.2 的病根是**同一件事有两个真相来源**：滑块本体由 painter 画在胶囊**之下**（于是被半透明胶囊压暗），而真 widget 身上的装饰又被摘掉了。用户反馈的第 1 条（静止时滑块比胶囊大）、第 6 条（吸附僵硬）、以及独立审查抓出的对比度问题，**是同一个病的三次发作**。这一版把它拆掉重来：**底栏两条档位各一棵树**（`_buildStandard` / `_buildLiquid`），手势与动画状态机两档共用 —— 于是「关掉液态玻璃不影响磨砂玻璃」从「比对后证明」变成**结构上不可能**（`00_home_shell_*` 与基线逐像素相同）。
  **调研结论里最要紧的一条**：所有开源实现（`oc_liquid_glass` / `Prismal` / `liquid_glass_widgets` / RN 那份）都是**借背景的光** —— 把背景那片彩色弯掉、拉开成光谱。**色散只把已经存在的颜色分开**，主色是青的、折射出来还是青的。iOS 底栏那圈彩虹来自它背后那块彩色内容，而本 App 的底色是刻意的极简黑白 —— 所以**我们那圈彩色只能「画」出来**。这也正是 `liquid_glass_widgets` 给 iOS 26 那档校准**主动把色散关成 0** 的原因（它自己的注释写着「真实的 iOS UI 玻璃几乎没有虹彩」）。
  **透镜是什么**：`LiquidLensSpring`（阻尼谐振子，ω=38 / ζ=0.55 —— **按与实现同一套离散格式扫出来的**，连续解的理论公式在这儿会把人带偏；帧间隔封顶 **16ms**）驱动 `LiquidLensShape`（两端半径可不同的圆 + 两段**外公切线** = 水滴；半径相等时精确退化成胶囊）→ `LiquidLens`（轮廓裁剪 + 半透明主色 + **光谱环**（绕主色色相走 300°，实测最大偏离 179.6°）+ 浮起阴影 + 把胶囊那条边**折进去**）。升程一个通道同时管三件事：放大、凸出胶囊、**跟不跟手**。
  **交互契约（用户 2026-10-01 原话）**：「点一下滑块自动过来、然后切页；长按滑块自动吸附、松手才切到它最终所在的区域」。点按**不提起**、长按才提起 —— 凸出胶囊是「按住」的专属信号。两档由**同一份手势代码**产生，所以契约一字不差（`glass_tier_test` 里有断言）。
  **三处实测撞出来的坑**：① `ImageFilter.matrix` 的坐标空间**永远是根坐标**（`Positioned` 的偏移、`Transform.translate`、`BackdropGroup` 都搬不动它，四条探针），于是「放大透镜底下的东西」这条路要透镜知道自己的屏幕绝对位置，而底栏外面还套着一层会动的 `QScale` —— 改成了自己画那条被折射的边；② `maxStep` 第一版按「半隐式欧拉的失稳门槛 2/ω」取成 48ms，结果在 40ms 一帧下**弹簧直接发散**（速度 2528 格/s，透镜被甩出屏幕几千像素）—— 那个门槛只是**临界**，能用的步长要严得多；③ 透镜位置**量纲混了**（弹簧存中心、目标算的是左缘），弹簧把透镜一路拽到胶囊最左边。后两条都是**看图看出来的**，当时那几条只比相对位移的手感用例全都照过。
  **工装**：新建 `scripts/diff_visual.py`（逐像素比两组出图，把「哪些屏变了」列出来）；屏单补 `40_nav_lens_dragging`（**静止帧拍不到「按住」这一档的全部**）；`tool/gif/` 补一条「点按换页」，与「底栏拖动」成一对反例。
  **范围**：液态档自这一版起**只作用于底栏**（用户拍板），判据只许出现在 `core/glass/glass.dart（定义处）` 与 `features/home/` 下 —— 由 `test/liquid_scope_guard_test.dart` 扫源码守着。`GlassRim` / `GlassLensGlow` 连同四个共享件上的液态效果一并删净。
