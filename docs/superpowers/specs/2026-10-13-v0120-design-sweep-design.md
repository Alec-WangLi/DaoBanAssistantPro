## 2. C 的八条

### ① 底部弹层没有标题行（用户点出的那条）

**现状**：`GlassDialog` 的标题行是「4×18 主色竖条 + 标题 + 关闭钮」，全 app 二十来个弹窗都有。
**底部弹层一个都没有**，标题就是一行裸文字，跟下面的列表同重。

**改**：把弹窗那套标题行抽成共享件，弹层也用它；弹层另加**拖拽把手**与**标题下的分隔线**
（用户拍的 D）。把手同时把「这个面板可以往下拉关掉」说出来 —— 底下那层本来就支持，
只是没有任何东西提示（`ModalBottomSheetRoute` 的下拉手势直接写在路由的 controller 上）。

**要改的五个弹层**：`shift_override_picker`（调整班次）、`profile_screen` 的铃声弹层、
`glass_pickers.showGlassOptionPicker`（贪睡时长 / 提醒档位这些都走它）、`shift_color_picker`（取色层）、
`calendar_screen` 的排班时段总览。
**时间 / 日期 / 月份三个滚轮不做**：它们本来就没有标题，加一个「标题 + 把手」是加内容，不是拉齐。

**Builder 复核出来的三件、动手前必须知道**：

1. **五个弹层不是共用一个头部，是各写各的** —— 共用的只有 `showGlassSheet` 那层壳
   （透明遮罩 + 入场动画）。所以「抽共享件」抽的是**头部**，而且要在四处文件里改。
2. **`showGlassOptionPicker` 一个件带六个调用点**（贪睡 ×1、提醒 ×2、编辑页 ×2、待办 ×2）——
   给它换头部等于同时改六处，出图要覆盖到。
3. **其中两个弹层的头部带第二行，而那行是内容不是装饰**：调班弹层的日期区间（回答「这次改哪几天」）
   与时段总览的「其余时间…」那句。**共享件必须留一个副标题槽**，别被 D 那套（把手 + 竖条 + 标题 + 分隔线）
   挤掉。

**我的判断（可推翻）**：

- **弹层标题保持 `titleStrong`（16），不涨到弹窗的 `dialogTitle`（20）。** 弹窗是居中的模态、弹层是
  贴底的抽屉，后者矮一档正合适；而且用户已经按 16 看过 D 那张图并点头了。**要涨是另一件事，得再出图。**
- **共享件留关闭钮槽位**：弹窗要（现在那个 ✕），**弹层一律不要**（下拉关闭是弹层的语义）。
- **副标题槽留着**（见上第 3 条）：`range` 与「其余时间…」都进这个槽。

**判据**：`11_override_picker` 那一屏出图；**弹窗那侧必须逐像素不变**（那是纯搬运，用
`scripts/diff_visual.py --threshold 0` 比）。

### ② 小节标题有三副面孔，装在五份各写各的小函数里

| 在哪 | 用的字号令牌 | 实际 |
|---|---|---|
| 排班管理页 `_sectionHeading`、使用帮助 `_groupHeading` | `sectionTitle` | **18 / w700** |
| 闹钟页 `_sectionTitle` | `titleStrong` | **16 / w700** |
| 我的页 `_sectionTitle` | `labelSecondary` + `inkMuted` | **13 / w400 灰** |

同一个角色，三种字号三种颜色；五份私有函数里有两份（使用帮助那两份）是 v0.11.17 刚抄的 ——
等于上一版把这个毛病又复制了一遍。

**改**：抽一个共享件，四份**页面级**私有函数删净（`_sectionHeading` ×2 → 一个）。

**Builder 复核订正了两处**：一是它其实是**两级**不是「三副面孔」——页面级之外，使用帮助的
卡片里还有一档更小的**子标题**（`microStrong` + 灰），那是正当的第二级，**不并进共享件**；
二是那四份私有函数里有两份（使用帮助那两份）是 v0.11.17 刚抄的 —— 上一版把这个毛病又复制了一遍。

**标准已定：`titleStrong`（16 / w700）。** 用户看过对照图后拍的，**接受「我的」页那五个标题
从 13 灰变成 16 黑**（这是全 app 观感变化最大的一处，已知情）。

### ③ 全 app 最显眼的两颗主操作按钮不是自家的件

**现状**：仓库有 `GlassButton`（主色渐变玻璃 + 顶部镜面高光 + Q 弹按压缩放），闹钟页的
「新建 / 测试」走它。但 `FilledButton`（Material 原生、平的、**按下是水波纹**）还在两处：
编辑排班页的「保存并重排闹钟」、排班管理页的「新增排班」。而 AGENTS.md 记着当初专门把
全 app 的按压反馈从水波纹换成玻璃按压缩放 —— 这两颗正好漏在外面。

**Builder 复核订正：不是两颗，是四颗 `FilledButton`。** 除上面那两颗，还有
`schedule_editor_screen.dart:625`（班次卡里的「添加班次」）与 `:333`（找不到方案时的「返回」）。
后两颗**不在这一轮的改造范围里**：625 是卡内一颗 **40 高的次级控件**（`GlassButton` 是 56 高，
换上去会在卡片里顶出一个又高又重的块），333 是错误态按钮。**这条要写进「不做」里，别让后人以为漏了。**

**改**：上面那两颗改用 `GlassButton`。

⚠️ **编辑页那颗不是换个件就完事**（Builder 实测出来的三处几何差）：
- 高度 **48**（`_saveButtonHeight`，是量出来的）vs `GlassButton` 默认 **56**；
- 圆角是**胶囊**（`AppTokens.pillOf(48)` = 24）vs `GlassButton` **写死 `radiusM` = 16**；
- 它外面已经套着一层 `DecoratedBox` 投影，而 `GlassButton` **自带投影** —— 直接换会**叠成两层**。

**我的判断（可推翻）**：**保住 48 + 胶囊形**，为此**给 `GlassButton` 加一个圆角参数**（默认仍是
`radiusM`，既有调用点一个像素不动），并**把外面那层 `DecoratedBox` 的投影去掉**（用 `GlassButton`
自己的）。理由：`kFloatingSaveInset = 92` 是**从 48 算出来的**（`16×2 + 48 + 12`），
`schedule_editor_test` 里两条几何 + 命中测试用例钉着它，而 v0.9.19 那次「蒙板」修复的成果全压在
这套算式上 —— 为了「换个件」去动它，风险与收益不成比例。**形状变化不是这条的目的，用自家的件才是。**

### ④ 还留着两处裸文字按钮

模板选择页的「管理模板」（`TextButton`）、权限卡的「去开启」（`TextButton`）。
这个仓库为同一类事改过两次（v0.9.13 把「重复待办」从裸文字改成胶囊、v0.11.4 把「已完成 N 条」
改成胶囊），理由都是「裸文字读起来像正文，不像能点的东西」。
**改**：换成胶囊（`GlassPill` 非 accent 那一档）或现成件，按所在行的角色定。

### ⑤ 按压反馈两套，还在同一页里混着

全 app 的规矩是「玻璃按压缩放」（`GlassPressable`）。还留着 **12 处 `InkWell`**（Material 水波纹）：
编辑排班页 7、日历 2、模板选择页 2、待办页 1。编辑页同一个文件里还有 3 处 `GlassPressable`，
其中一处是 `GlassPressable` 套着 `InkWell` —— **两个反馈叠着来**。

**Builder 复核把这段里我说错的两处订正了（重要，别照原文改）**：
- 数出来是 **12 处不是 14** —— 我把两行**注释**也数进去了。
- **我举的那处「有意的波纹」正好说反了**：`calendar_screen.dart:2669` 那条注释讲的是
  「完整信息卡**故意不用** `InkWell`、改用 `GestureDetector`」（波纹只该出现在弹层的 `ListTile` 里）。
  真正可疑的是它下面那**紧凑信息卡**（`:2437`），它 `GlassPressable` 套 `InkWell`，
  而它的注释自称与完整卡「同源」—— **和完整卡那条规矩正好相反**。

**我的判断（可推翻）**：动手时**逐处核**，判据用**位置的种类**而不是文件：
「卡片/列表行里的点按」一律 `GlassPressable`（全 app 的规矩）；**只有弹层里的 `ListTile` 留波纹**
（那正是完整信息卡那条注释承认的例外）。按这条，**12 处里绝大多数要换**，紧凑信息卡那处要
**顺带把它注释里那句「同源」改准**。**每换一处都要出一张图**，别一把梭。

### ⑥ 空态从没被拍过 —— 41 屏屏单里一条空态都没有

现有空态（闹钟页「近 30 天无班次闹钟」、重复待办面板、桌面小组件、日历整月无排班那句）
写法大差不差（次要文字色的一行字），但留白不一致（有的上下 24、有的统统 16），
**没有任何护栏、也没有人看过**。这正是 v0.8.1 那次的同一类：四处设计跑偏过了三道评审，
根因就是「没进屏单 = 没人真正看过」。

**改**：抽一个共享的空态件（一句话 + 统一留白），**并把空态补进屏单**。

### ⑦ 加载态没有共享件

7 处 `CircularProgressIndicator`：两处手写粗细（`strokeWidth: 2.6` / `2`）、五处用默认。
同一屏上两种粗细看得出来。**改**：抽一个共享件，粗细一处定。

### ⑧ 「新建一个东西」这类主操作，四个页面摆了四个地方

待办页 = 悬浮 FAB、闹钟页 = 底部按钮条（这两个用**同一个 76px 偏移**，是对的）、
编辑排班页 = 底部悬浮胶囊、而**排班管理页 = 列表末尾一颗通栏实心按钮**。那页通常只有
一两套排班，于是那颗按钮**悬在页面中间、底下一大片空**（见 `03_management_light.png`）。

**改**：排班管理页改用**与闹钟页同款的底部按钮条**（同一 76px 偏移、同样悬浮在内容之上）。
于是「新建」在三个列表页上是同一个位置、同一个件。
⚠️ 顺带要查：这页的列表底部留白（`kNavCapsuleInset` / `kFloatingActionInset` 那一族常量，
见 `core/layout.dart`）——按钮条从「列表里」挪到「悬浮」之后，最后一行的让位要重算，
而且**要叠系统栏**（`MediaQuery.paddingOf(context).bottom + …`，测试视口没有系统栏，这类错只能靠算式堵）。

## 3. A 的（上一版留下的两条 Minor）

1. **内容护栏只覆盖条目，没覆盖小节与小节的标题。** `help_content_test.dart` 的「英文不是照抄中文」

2. **小窗 200×400 在字号护栏里是「冒烟」档**（只打印、不判失败）。这是仓库既有策略

   **这一条不是缺陷，不用改文本**；要做的是**把新加的两屏（使用帮助的两级）在小窗那一档上人工看一眼**
   —— 已经在 v0.11.17 做过（`18_help_center_small` / `59_help_faq_small` 出过图、无截断）。

## 4. B 的结论：干净

按最容易漂的四类各查一遍，**一处都没找到**：

| 类别 | 查了什么 | 结果 |
|---|---|---|
| 带数字的 | 测试闹钟「10 秒后响」= `Duration(seconds: 10)`；闹钟页 30 天；每班 10 条 = `maxAlarmsPerShift`；5 种主色调 = `accentPalette`；14 天预览条；颜色示例 `#4C8DFF`；贪睡 1–30 | 全对 |
| 指路型的 | 文案里所有「我的 → X → Y」逐条走一遍（排班管理 / 排班时段 / 使用帮助 / 权限 / 外观 / 检查更新 / 桌面） | 目标都存在 |
| 讲后果的 | 权限卡每一条「不开会怎样」（通知 / 精确闹钟 / 悬浮窗 / 全屏通知 / 小米两项 / 自启动 / 电池） | 与实现一致 |
| 讲时限的 | 贪睡档位、提醒档位（准时 / 5 / 15 / 30 / 60 / 1440 分钟）、响铃三档落点 | 与实现一致 |

**上一版帮助里那种漂移（写了「最多 6 条闹钟」而实现是 10）这次一处都没有** —— 它当时是例外，
不是常态。所以 B 这一线**没有要做的东西**；剩下的是「以后别再漂」——见 §5 第 3 条。

## 5. D 的规格（正式版门面）

正式版（末位 `Z = 0`）发布前**必须过一遍仓库门面**（AGENTS.md 里那条，用户提过两次）：

1. **`README.md` 文案**逐条对着当前实现核（版本号、功能清单）。
2. **`README.md` 配图重跑**：`flutter test tool/promo/render_promo_test.dart` → `python scripts/make_promo_images.py`。
   **改了 UI 不重跑，README 上挂的就是几个版本前的界面。**
3. **GitHub 仓库描述与 topics**（`gh repo edit`）。
4. **`PRODUCT_SPEC.md`** 抬头版本 + 受影响条目；**`AGENTS.md`** 版本史与「最近改动」；
   **`docs/coolapk-post.md`** 对应段落。
5. **酷安评论区更新稿**：`docs/v0.12.0-update-post.md`，格式照 `docs/v0.11.0-update-post.md`。
6. **⚠️ 动图（用户这一版特别强调的）**：用户原话「这一次一定要把关键动图都加上，我看之前 GitHub
   上面的更新简介，它就没有动图，显得不那么直观」。
   - 现状：`tool/gif/` 有出帧管线（`flutter test tool/gif/render_gifs_test.dart` + `scripts/make_gif.py`），
     但产出的 GIF 过去只落在 gitignored 的 `work/gif/`，**没有进过仓库、也没有进过 Release 说明**。
   - 要做：挑这一版真正「动起来才看得懂」的几条，出 GIF，**并让它们在 GitHub 上看得见**
     （GitHub Release 说明里贴图要引用一个可访问的 URL —— 要么把 GIF 提交进仓库按 `raw.githubusercontent.com` 引，
     要么上传到一个稳定的图床）。**放哪儿、多大、几张，是 builder 要定的事**；约束是 GIF 体积
     （仓库会被每个 clone 的人拉走，单张控制在几百 KB 量级、别一次塞十张）。
   - **必须是真实录制**：走仓库既有的出帧管线，不许手搓「示意图」。

   **Builder 复核确认这条路走得通，并给出两条排期上的硬约束**：
   - 管线现成（`tool/gif/render_gifs_test.dart` 出帧 → `scripts/make_gif.py` 合成，默认「≤10 秒、几百 KB」），
     过去每张 GIF 大致就是这个量级；把产物从 gitignored 的 `work/gif/` 改写到 `docs/images/` 是小事一桩。
   - ⚠️ **发布说明那个文件在 gitignored 的 `tools/gh/` 里** —— 所以 **GIF 必须先提交进 `main`，
     `release.ps1` 才发得出去**，否则 Release 正文里引的是还不存在的 URL。
   - `docs/images/` 现在已经有 13MB 的 PNG，**一张 GIF 都没提交过**；唯一真正的成本是
     「每个 clone 的人都要拉一遍」，所以**控制在少数几张**。
