# 重复待办（定期重复提醒 + 统一管理）· 设计规格

> 2026-09-29 头脑风暴定稿。**目标版本由用户拍板**（末位 `Z` 归 AI，`X.Y` 归用户）。

## 1. 背景与目标

用户反馈：**「我每周三要定期开个会，能不能这周三它自己弹出来，完成之后删掉，下周三又自己冒出来一条新的？这样我就不用每周三都单独设一次了。还有这种定期重复的待办，能不能给个统一管理的面板？」**

现状：待办是「**一条 = 一天**」，`ScheduleEvents` 里没有任何周期概念；想每周三开会，只能每周手动建一条。

**目标**：设一次「每周三 09:00 开会」，之后每周三它自己出现、能勾、能删；重复项在待办页有一个统一管理入口。

**成功标准**：
- 建一个「每周三」的重复待办之后，不再需要任何手动操作，它每周三都会出现在列表里；
- 提醒**到点就响**，且**App 长期不开也不漏**（见 §5）；
- 在待办页能一眼看到有哪些重复项、各自的周期与下一次是什么时候，能改、能停用、能删。

## 2. 已定决策（来自 2026-09-29 的头脑风暴）

① **列表形态：每次一行、到点才出现。** 一个系列在列表里同时只有一条「当前这次」（未完成）；**勾过的那些留成历史**（带删除线，跟现在的一次性待办一样），由用户自己删。
② **过期未勾：下一次到点时直接顺延成新的。** 当前那条未完成的行**就地改日期**（勾选状态本来就是未勾），不另起一行。于是「上周三那次没做」不会堆出来，也不留记录。
③ **粒度：每天 / 每周几（可多选）/ 每月某日。** 不做「每隔 N 天」，不做「每几周的某几天」（「每周几」多选已经够）。
④ **提醒：原生自己续排**，App 长期不开也不漏（§5）。

## 3. 数据模型（schemaVersion 10 → 11）

### 3.1 新表 `RecurringTodos`（系列定义）

```dart
class RecurringTodos extends Table {
  IntColumn get id => integer().autoIncrement()();
  TextColumn get title => text()();
  IntColumn get timeMinute => integer().nullable()();          // 空 = 全天
  IntColumn get advanceRemindMinutes => integer().nullable()(); // 空 = 不提醒
  BoolColumn get alarmEnabled => boolean().withDefault(const Constant(false))();

  /// 0 = 每天，1 = 每周（看 weekdays），2 = 每月（看 monthDay）
  IntColumn get repeatType => integer().withDefault(const Constant(0))();
  /// 每周：`1 << (weekday - 1)`，与 `CustomAlarms.weekdays` 同一约定（周一=1）。
  IntColumn get weekdays => integer().withDefault(const Constant(0))();
  /// 每月：1..31；该月没有这一天时取该月最后一天。
  IntColumn get monthDay => integer().withDefault(const Constant(1))();

  /// 首次生效日（纯日期，`dateOnly` 口径）。这一天之前不产生任何发生日。
  DateTimeColumn get startDate => dateTime()();

  /// 「这次不要了」记到哪天为止（自 epoch 天数，与 `dayNumber` 同口径；空 = 没跳过）。
  IntColumn get skipThrough => integer().nullable()();

  /// 停用：不再生成、不再续排提醒；**已经出现的那条留着**（见 §4.3）。
  BoolColumn get enabled => boolean().withDefault(const Constant(true))();

  DateTimeColumn get createdAt => dateTime()();
}
```

### 3.2 `ScheduleEvents` 加一列 `seriesId`（可空）

`IntColumn get seriesId => integer().nullable()()`。语义：`null` = 一次性待办；非空 = 某系列的**某一次**（当前那次，或一条历史）。

不变量：**一个系列至多一条「未完成」的行**（`seriesId = X AND isCompleted = 0`）。由生成器维持，`recurring_todo_test.dart` 有一条用例钉住。

### 3.3 一处**有意的不对称**，写下来免得后人当 bug 修

`seriesId` 只指「这一次属于哪个系列」，**系列不反过来存 `currentEventId` 指针**。理由：指针要在新建/顺延/删除/跳过四条路径上保持同步，漏一条就是「系列指向一条不存在的行」；而「当前那条 = 这个系列里未完成的那条」是**从数据本身推出来的**，天然自愈 —— 真出现两条未完成时，生成器能自己收敛（§4.2 第 5 条）。代价是每次要多查一次未完成行，那张表很小，不值一提。

### 3.4 迁移

```dart
if (from < 11) {
  await m.createTable(recurringTodos);                       // 纯新增，不碰既有数据
  await m.addColumn(scheduleEvents, scheduleEvents.seriesId); // 可空列，老待办自动是 null
}
```
照 v8→v9（纯新增一张表）与 v7（给 `schedule_events` 加列）两条先例。**必须补 `migration_v10_to_v11_test.dart`**：老待办一条不丢且 `seriesId` 为 null、新表能写能读。

## 4. 领域层（`domain/recurring_todo.dart`，纯 Dart 可直接单测）

### 4.1 两个发生日函数

- `occurrenceOnOrBefore(series, day)` —— **不晚于 `day` 的最近一次发生日**；`startDate` 之前返回 null。
- `nextOccurrenceAfter(series, day)` —— **严格晚于 `day` 的下一次发生日**（排提醒用）。

（第三个纯函数 `upcomingFireTimes` 在 §5.2 —— 它返回的是**触发时刻**，比发生日多一层「提前提醒」的偏移，所以放在提醒那一节。）

规则：
- **每天**：从 `startDate` 起每 +1 天。
- **每周**：`weekdays` 掩码里最近的一个匹配日。掩码为 0 时**视为不生成**（防呆：界面上不允许出现空掩码，但库里可能有脏数据）。
- **每月**：`monthDay`；**该月没有这一天时取该月最后一天**（每月 31 号 → 2 月落在 28/29）。
- **日期算术一律 `DateTime(y, m, d + n)`，绝不用 `Duration(days:)`** —— 后者加的是绝对 24 小时，碰上夏令时切换会把日期挪掉。这条在 `alarm_service.dart` 与 `shift_rotation.dart` 里都已经写过一次，这里是第三次。

### 4.2 生成器 `advanceRecurringTodos(repo, {required DateTime today})`

**`today` 必须由调用方注入，不许内部读 `DateTime.now()`** —— 否则整套用例都写不成（照 `planShiftAlarms(from:)` 的写法，那一条的理由写在那里）。

一个事务里对每个系列：

1. `enabled == false` → 跳过（不生成也不顺延，那条已出现的行留着不动）。
2. `occ = occurrenceOnOrBefore(series, today)`；为 null（还没到 `startDate`）→ 跳过。
3. `skipThrough != null && dayNumber(occ) <= skipThrough` → 跳过（「这次不要了」，见 §6.4）。**两边都是「自 epoch 天数」，`occ` 要先过 `dayNumber`** —— 一个 `DateTime` 一个 `int`，直接比是拿毫秒数去比天数，恒不成立（那正是「删了又回来」的写法）。
4. 该系列**未完成**的那条行：
   - **没有** → 新建一条（`date = occ`，`seriesId` 指过来，标题 / 时间 / 提醒档位 / 联动闹钟都从系列取，`createdAt` 取此刻）；
   - 有、且它的日期**早于** `occ` → **就地顺延**（只改日期，行的 id 不变）；
   - 有、且它的日期**晚于或等于** `occ` → **不动**（见下）。
5. 防御：真出现**多条未完成**（历史脏数据 / 并发）→ 保留日期最新的那条，其余按已完成处理，并留一条日志。

**第 4 条「不动」那一支是有意的**：用户手工把这一次改到别的日子（比如这周的会挪到周五），生成器**不能把它拽回来**。所以顺延只往**前**走，永不回退。

**代价是「改周期」这条路径必须自己对齐**：把「每周三」改成「每周五」之后，当前那条未完成的行还停在周三，而生成器不会回退去纠正它。所以**编辑系列的流程在保存后要显式把当前那条未完成行改成按新规则算出的 `occ`**（新规则下 `occ` 为 null，即起始日被改到将来时，那条行留着不动）。生成器与编辑路径的分工写在这里，免得后人把「不倒退」当成 bug 去改。

**跑在三个时点**：App 启动（挂在 `home_shell` 那个「三个流到齐」的启动闸上，与 `_tryStartupReschedule` 同一处）、**回到前台**（`HomeShell` 加 `WidgetsBindingObserver`，照 `alarm_screen` / `profile_screen` 的现成写法）、改完系列之后。第二条是为了「一直没关过的 App 跨过午夜」—— 列表本身是 drift 流，不写库就不会重发。

### 4.3 停用为什么不顺手收走当前那条

「停用」的语义是「**以后别再自动出现了**」，不是「把这条待办从我眼前拿走」—— 那是一条还没做的事，替用户删掉它，用户就再也看不见了。所以停用只停「生成 / 顺延 / 提醒」，当前那条留着，用户自己勾或自己删。面板里能再启用。

## 5. 提醒链路

### 5.1 排「下一次」，不是排「这一条」

**这是最容易写错的一条。** 假如下午打开 App，这周三 09:00 早就过去了 —— 如果照今天那套「拿行的日期算提醒时刻、过去就不排」，那么这条重复待办的提醒**永远不会被排上**（每次都算出一个已经过去的时刻）。

所以重复项的提醒时刻一律由 `upcomingFireTimes(series, from: now, ...)` 算：**从此刻之后的下一个触发时刻开始**。触发时刻 = 发生日的 `timeMinute` 再扣掉 `advanceRemindMinutes`（提前一天的那档会落在前一天）。

### 5.2 时刻表（为什么不是把规则复制一份到 Kotlin）

重复待办的提醒要「App 长期不开也不漏」，就得由**原生接收器响完自己续排下一次**（`CustomAlarms` 就是这么做的）。但规则里那些边角（月末特例、多选星期几跨周、提前提醒的偏移、夏令时）如果照抄一份到 Kotlin，就成了**第二份实现**，而且原生在这个仓库里**没有可跑测试的目标** —— 两份实现迟早对不上，症状还是「某天没响」这种不报错的。

所以：**时刻表在 Dart 侧算好，原生只做「取下一个」。**

- `upcomingFireTimes(series, {required DateTime from, int days = 180, int cap = 200})` —— 未来 180 天内的触发时刻，最多 200 条（每天重复的 180 天正好 180 条；每周 26 条；每月 6 条）。
- 排定时把这条时刻表整串塞进 Intent extras（`Long[]`）+ 落盘进 `AlarmStore`；原生响完**弹掉队首、用队里下一个续排**（队空则不再续）。
- 每次 App 打开都会重排（`rescheduleAll` 那条老路），所以时刻表一直是满的；180 天是「用户还在用这个 App」的合理上界。

### 5.3 提醒正文用「规则描述」，不带日期

一次性待办的正文是「9月30日 周三 · 09:00」（`eventReminderBody`）。但重复项的**同一条提醒会跨很多次**，写死日期第二次就是错的。所以重复项的正文改用**规则的可读描述**（「每周三 · 09:00」），由 `L10n` 产出、整条时刻表共用一条串。标题仍是系列名。

### 5.4 行与系列的提醒不重复响

`rescheduleEventReminders` **跳过 `seriesId != null` 的行** —— 重复项的提醒由系列那一条负责。否则同一次会响两声。

### 5.5 号段与取消（一处顺带修掉的既有隐患）

现状：待办提醒 id = `20000 + 行的自增 id`，**取消时盲扫 `20000..20999`**（1000 个号）。而 `AUTOINCREMENT` **永不复用**：行号一旦越过 1000，那条提醒就**排得下去、谁也取消不掉**（幽灵提醒）。现在一个「每天」的重复待办每年会产生几百行，两三年就能把这个号烧穿 —— 这是本轮必须一并处理的。

- **两个号段**：待办行 `20000 + eventId`（`TODO_BASE_ID`，留到 39999）；重复系列 `40000 + seriesId`（新常量 `RECURRING_BASE_ID`，留到 41999）。**系列的提醒 id 由系列 id 算，与行号无关**，所以「历史行越攒越多」不再挤占提醒的号。两组都避开既有区间（0..400 班次、10000..11000 自定义、99998/99999 自检、100000+ 小组件）。
- **取消改成按清单逐个撤**：`AlarmStore` 本来就存着每一条排定的记录（开机重排靠的就是它），遍历它、把 id 落在待办两段里的逐个取消（**两个目标都取消** —— 同一条按「联动闹钟」开关走 `AlarmReceiver` 或 `TodoReminderReceiver`），并把对应记录从清单里删掉。
- **保留一小段盲扫兜底**（`20000..21000`，旧版本用过的区间）：只为清掉「升级前排下、清单里没有」的陈旧记录。这一段的开销与今天相同，**不引入新的性能代价** —— 而今天每勾一次待办都要盲扫 1000×2 次取消调用，号段直接拓宽到 2 万会让它变成几万次。

## 6. 界面

### 6.1 待办列表

- 重复项与一次性项**按日期混排**（`watchEvents` 的排序不动）。
- 副标题前面一个循环小图标（`Icons.repeat`），一眼看出「这是重复项」。
- 勾选行为不变：勾完留下带删除线的历史行。
- **删当前那条 = 「这次不要了」**（见 §6.4），不是删整个系列。

### 6.2 新建 / 编辑弹窗（复用 `_EventFields`）

- 加一行「重复」：`GlassSegment` 四档 `[不重复] [每天] [每周] [每月]`。
- 选「每周」→ 出现七个可多选的星期胶囊（`L10n.weekday(i)`，位掩码与 `CustomAlarms` 同约定）；选「每月」→ 出现「每月的 N 号」。
- 原来那行「日期」对重复项**改叫「从这天起」**（首次生效日，可以往后设）—— 一次性待办仍是「日期」。
- 「提醒（可选）」「联动闹钟」两行照旧，`_EventFields` 里那两条联动规则（不设提醒就关闹钟、开闹钟把提醒补成准时）原样保留 —— **那条规则写在 `_EventFields` 的构建里，加「重复」那一行不能绕过它**。
- 编辑一条重复的行 = 编辑它背后的系列（标题 / 时间 / 提醒 / 周期都写回系列，并同步当前那条未完成的行）。
- **改完周期之后要显式把当前那条未完成的行对齐到新规则的 `occ`**（见 §4.2 末段）—— 生成器只往前顺延，不会替这条路径回退纠正。
- 把一次性改成重复 = 建系列并把这条行挂上去（`seriesId` 赋值）；反过来 = 解绑 + 删系列（**有确认**：「以后不再重复」）。

### 6.3 管理面板

- **入口**：待办页标题那一行（`Padding` 里的 `Text(L10n.titleTodo)`）改成一行 `[标题] … [重复]`，右侧一个文字按钮。与「选择你的倒班方式」页里分组标题旁那个「管理」同一套写法。
- **形态：弹窗**（系列数量通常只有几个，照「我的模板」的管理弹窗那套配方；不必单开一页）。
- 每行：`↻ 周三例会` + 副标题 `每周三 · 09:00 · 下次 10月21日` + 停用开关（`GlassSwitch`）+ 删除（`GlassDeleteButton(compact: true)`，**带确认**并说清会连带删掉几条历史）。
- 点行打开编辑弹窗（同 §6.2）改这个系列。
- 空态：一行说明（「还没有重复待办」），照待办页空态那句的配方。

### 6.4 「这次不要了」：跳过标记

在列表里删掉重复项的当前那条行，如果只是把它删掉，**下一次打开 App 生成器又会把它补出来**（因为没有未完成的行、而 occurrence 还在今天之前）—— 用户看到的就成了「删不掉」。

所以：**删当前那条 = 往系列上写一个 `skipThrough = dayNumber(当前这次的日子)`，生成器在那天之前不再补**（§4.2 第 3 条）。下次 occurrence 一到，`dayNumber(occ) > skipThrough`，它自然又出现。删除整个系列只在面板里做。

## 7. 文案（`lib/core/l10n.dart`）

重复那一档：`repeat`（重复）/ `repeatNone` / `repeatDaily` / `repeatWeekly` / `repeatMonthly` / `everyMonthOnDay(n)` / `startsOn`（从这天起）/ `recurring`（面板标题）/ `recurringEmpty` / `nextTime(d)`（下次 …）/ `deleteRecurringTitle` / `deleteRecurringContent(name, n)` / `skipThisOccurrence` / `deleteWholeSeries` / `stoppedRecurring` 等。规则描述（「每周三 · 09:00」「每月的 1 号」）也在这里产出 —— **它是提醒正文的来源，必须是可本地化的**。

## 8. 明确不做

- **结束条件**（重复到某天为止 / 重复 N 次）—— 用停用或删除代替。
- **「每隔 N 天」**、**「每几周的某几天」**（「每周几」多选已够）。
- **农历重复**（每月初一之类）。
- **把这一次改期之外的重排**：手工把当前那条改到别的日子是允许的（生成器不倒退，§4.2），但不做「这次顺延到下周」这种批量动作。
- **重复项的完成率统计 / 历史列表页** —— 勾过的行就在列表里，没有额外视图。

## 11. 风险与坑（实施时挨个对照）

1. **提醒必须排「触发时刻晚于现在」的那一次**，不是这一条的日期 —— 否则提醒永远排不上（§5.1）。
2. **`rescheduleEventReminders` 要跳过带 `seriesId` 的行**，否则同一次响两声（§5.4）。
3. **生成器只往前顺延，永不回退** —— 回退会让用户改过的日子被拽回来（§4.2）。**因此「改周期」必须由编辑路径自己把当前那条对齐**，别指望生成器。
4. **日期算术不许用 `Duration(days:)`**（夏令时）。
5. **`skipThrough` 不写就会「删不掉」**（§6.4）。
6. **`AlarmStore` 的两份清单都要管**：重复项的提醒走系列时刻表（安静链路写 `Quiet`，联动闹钟那条走 `Entry`），取消要两份都查、`BootReceiver` 要两份都能重排。漏一份就是重启后少响 / 幽灵闹钟。
7. **`clearAll` 要连带删新表**，并清掉重复系列的提醒（照现有「每条取消路径都要同步删清单」那条）。
8. **原生那段没有测试目标**：时刻表在 Dart 侧算好并有单测，Kotlin 只做「弹队首、续队尾」——**新增的原生逻辑要尽量小**，任何规则判断都不许写进 Kotlin。
9. **号段**：行 20000..39999 / 系列 40000..41999，与既有区间（0..400、10000..11000、99998/99999、100000+）都避开；改号段要连着改 `cancelTodoReminders` 的扫描范围与 `AlarmStore` 的清理范围 —— **三个一起改**。
10. **测试里的定时器**：待办页要从 `ConsumerWidget` 变成 `ConsumerStatefulWidget`（挂 `WidgetsBindingObserver`），widget 测试要照 `calendar_screen_test.dart` 的 `_dispose` 主动拆树，否则 drift 取消查询流时排的零时长定时器会打红。
