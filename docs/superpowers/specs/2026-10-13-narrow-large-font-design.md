# 字号自管 ＋ 把「静默省略」收干净（设计）

- 日期：2026-10-13
- 起因：真我 GT7 Pro 的用户截图里，日历顶栏把「2026年10月」显示成「2026年1…」；随后是用户的追问「咱们现在这个 App 的界面显示是自适应适配所有不同尺寸的手机了吗」。
- **用户拍板（2026-10-13，两轮）**：
  1. 第一轮：**逐个收住**（不把「钳字数/钳字号」当成唯一手段），并且**真实屏幕尺寸不许我推断**，去查、写进文档。
  2. 第二轮（用户自己在真机上把系统字号调到 200% 试过之后）：**完全忽视系统字号，只用自己的设置**；**我们自己挑几档最优的字号并逐档适配好**；**尽量不要出现内容被省略、也不要出现「内容还得自己滚」**。
- 影响版本：从 v0.11.12 起。

## 1. 现状：量出来的，不是推的

一次性探针（`app/tool/probe/narrow_font_probe_test.dart`，跑完即删）把工装屏单里**全部 39 屏**在三档配置下各渲一遍，同时抓两件事：布局溢出（硬错误）、**被省略号吃掉的字**（`RenderParagraph.didExceedMaxLines`，静默）。

| 配置 | 有问题的屏 | 布局溢出 |
|---|---|---|
| 360×780 · 字号 1.0 | 12 / 39 | **0** |
| 360×780 · 字号 1.3 | **28 / 39** | **0** |
| 320×700 · 字号 1.5 | 27 / 39 | **0** |

**一处硬溢出都没有。** 界面从来不炸、不裁切、不丢控件 —— 它只是**安安静静地把字吃掉**。

这正是它一路漏到用户手上的结构性原因：`render_screens_test.dart` 写着「唯一的断言是『渲染期间没有布局溢出』」—— 而这一类它一个字都不会说。**我们从来没有一个断言盯着「字有没有被省略」。**

28 屏的毛病只有**五类**：

| # | 类 | 例子 | 正常字号下就已经省略？ |
|---|---|---|---|
| 1 | 日历顶栏的年月 | `2026年10月` | 否（360dp 下只剩约 3dp 余量） |
| 2 | 底栏信息卡那两行 | 整条农历串；`中班 18:00 – 22:00 闹钟：未开启` | 否 |
| 3 | 列表行的副标题 | 待办的 `10月13日 星期二 · 14:30 · 提前15分钟`；我的页那句贪睡说明；排班名；时段行 | 部分是 |
| 4 | 编辑器的字段标签与值 | `响铃时间`、`可选，如「午休」`、`前一天 23:00`、`次日 00:15` | **是**（360dp、1.0× 下就在省略） |
| 5 | 编辑器的 14 天预览条 | `10/13`…（**7 列 × 2 行**，不是一行 14 格） | 否（只在最窄档出现） |

## 2. 规矩：不许静默省略，也不许「面板套滚动」

1. **一行文字要么能折行、要么能按可用宽度缩小**（`FittedBox(scaleDown)`），**永远不许**用 `.ellipsis` 把用户看得见的信息静静吃掉。
   - 唯一例外是**本来就该缩写的展示**（日历格子里的农历，`LunarInfo.cellLabel`：截 3 字 + 省略号，v0.9.9 有推导 —— 「全民国防教育日」缩到 6px 比截断更糟）。这类进 §8 的具名白名单，每条写明理由。
2. **不许「嵌在页面里的面板自己滚」** —— 卡片里再套一层滚动、页面也在滚，是两层滚动打架。
   - 页面级的滚动是正常的（待办/闹钟/我的本来就是列表）。
3. **日历页在每一档字号下都保持「一屏构图」**：顶栏 + 完整的网格 + 完整的信息卡，**不需要任何滚动**。
   - 用户 2026-10-13 专门点过这一条：「尤其是日历界面，它的日期和今日信息卡片不要出现说内容太多、需要你自己滚的情况」。所以**网格也不许滚**。
   - ⚠️ 网格外面那个滚动容器**留着**（`calendar_screen.dart:763`）—— 它是给**亚像素取整**兜底用的（那里写着「一旦有亚像素取整，最后一行就会被滚动容器裁掉一条」）。**本轮要保证的是「它在任何一档下都不会真的滚起来」，不是把容器拆掉** —— 拆掉反而会把那条既有的兜底一起弄丢。

这条规矩有一半已经在仓库里：v0.9.9 定的「网格是定尺的点阵，字一律归一到格子里」与「信息卡按真实 `textScaler` 量高」就是它，只是当时只照在网格上，**没照到顶栏、信息卡、列表副标题与编辑器的行**。

## 3. 字号由 App 自己管（本轮的根决定）

**Android 上「跟不跟系统字号」完全由 App 决定** —— 系统只是把 `fontScale` 报给你，不读它就不跟。微信、酷安那类都是把 sp 当 dp 用、再自己给一个「字体大小」。用户 2026-10-13 在真机上把系统字号拉到 200% 试过：小米只有部分系统应用跟随，第三方 App 基本都不跟。

**所以本轮改成**：

- 根部把进来的 `textScaler` 置为 `TextScaler.noScaling`，**再乘上我们自己的 `AppFontScale`**。两件事都收在 `app.dart` 的 `builder` 里（那里已经有一层 `MediaQuery`，一处收口）。
- 新设置项 **我的 → 外观 → 字体大小**（`小 / 标准 / 大 / 特大`，默认标准），与主题/主色/语言一样进 `appSettingsProvider`、落 prefs。
- ⚠️ **别照抄「响铃页要直接读 prefs」那条坑**（v0.11.8 的贪睡时长）：那条是因为**那个设置项**只被响铃页读，而响铃页不 watch 任何 provider。`TextScaler` 走的是**根部那一层 MediaQuery**，**所有路由（含响铃页）都吃得到**，不需要在别处再读一次。

**代价（有意付出、写明白）**：一个把系统调到 150%~200% 的人（Android 14 起才有这一档，多半是真的看得吃力），在 App 里拿不到那个大小 —— 我们给到的最大档就是「特大」。换来的是：**天花板回到我们手里**，每一档都是我们设计过、量过的，不存在「2.0× 下卡片吃掉半个屏、网格只剩三行」那种形态。

**已知缺口（本轮不碰，单记一笔）**：**桌面小组件是原生 `RemoteViews`，仍然按系统 `sp` 排版** —— 系统调到 200% 时，桌面那张卡还会跟着变大。要它也不跟，得把 Kotlin 那几张布局里的 `sp` 改成 `dp`，那是原生侧的另一件事。

## 4. 真实设备的宽度边界（查过的）

### 4.1 手机 / 平板

Android 的布局单位是 dp（= px ÷ density），**逻辑宽度与分辨率无关**：1080p 的机器可能是 360dp，也可能是 411dp。

- 主流手机集中在 **320–450**；1080p 最常见的是 **360 / 390 / 411**（[ScreenAdaptation 的实测清单](https://github.com/ippxie/ScreenAdaptation)：320、360、384、392.7、400、410、411.4、432、480）。
- 官方基准档（[Android 资源概览](https://developer.android.com/guide/topics/resources/providing-resources)）：**320**（小屏手机）、**480**、**600**（7 吋平板）、**720**（10 吋平板）。
- 对照手上两台真机：Redmi K90 Pro Max（1200×2608 @480dpi）= **400dp**；真我 GT7 Pro（2780×1264）大概率在 **360–421dp**。

### 4.2 车机

- Android Auto 的官方基准是 **800×480 @ dpi 160**（= 800×480 dp），另有 1280×720、1920×1080（[Android for Cars DHU](https://developer.android.com/training/cars/testing/dhu)）。
- AAOS 对没适配的应用走**按包名的 DPI 缩放**（[车载显示屏兼容性](https://source.android.com/docs/automotive/app_compat/car_display_compat)）—— **车机上「App 拿到多少 dp」是厂商逐包配的、不可预测**。
- 用户的车是 **26 款吉利星瑞 · 15.6 吋 · 1920×1080**。同一块面板按 density 算出来的 dp **差三倍**：

| density | App 看到 | 落到哪一支 |
|---|---|---|
| 160 | 1920×1080 dp | 宽且不矮（`isWide`：正文按最多 720dp 居中，两侧各留约 600dp） |
| 240 | 1280×720 dp | 同上，两侧留白约 280dp |
| 320 | 960×540 dp | 宽，高度刚好过 `isShort` 线 |

**「中间一栏 720dp、两边大留白」不算坏，但也不算为车机设计过** —— 要不要给宽屏做**两栏版式**是另一件事，比这一轮大，单开。

### 4.3 字号：Android 14 起是**非线性**的，最高 200%

Android 14 起系统字体最大 **200%**，且**不是等比放大**（[Flutter 迁移说明](https://docs.flutter.dev/release/breaking-changes/android-14-nonlinear-text-scaling-migration)）。AOSP 是一张按 sp 查的表（[FontScaleConverterFactory](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/content/res/FontScaleConverterFactory.java)）：

| 原始字号 | 1.3× 实际 | 1.5× 实际 |
|---|---|---|
| ≤ 12sp | **×1.30** | **×1.50** |
| 14sp | ×1.343 | ×1.571 |
| 18sp | ×1.20 | ×1.33 |
| ≥ 30sp | ×1.00 | ×1.00 |

本 App 几乎全部建在 **12–15sp** 上 —— 正好是吃满倍率的那一档。**这条是「系统字号必须被挡住」的最硬理由**：它的设计意图是把小字放大得最多，而我们的界面全是小字。

**⚠️ 工装只能用线性**（测试环境没有平台 configuration，`PlatformDispatcher.scaleFontSize` 会退回「字号 × 倍率」）。所以工装里的 1.3 与真机 1.3 对 12–15sp 是一致的、对 ≥18sp 是**偏严**的。**别拿工装的线性去反推真机的观感。**

### 4.4 由此定下的测试矩阵

**宽度**（现有 `kVisualSize`(420×900) 之外补）：

| 尺寸 | 代表 |
|---|---|
| **320×640** | 官方「小屏」基准 —— 保证线 |
| **360×780** | 1080p 手机最常见的一档（真我那一类） |
| **411×870** | 旗舰 1080p（Pixel 一类） |
| **600×960** | 7 吋平板 |
| **1280×720** / **1920×1080** | 车机 / 平板横屏 |
| 200×400 / 900×420 | 小窗与手机横屏（已有） |

**字号**：**我们自己的四档，不再有第五个变量**（系统那一维已经归零）。

## 5. 四档字号，与「为每一档定版式」

- 起步四档：**小 0.9 / 标准 1.0 / 大 1.15 / 特大 1.3**（0.9 给「想一眼看全一个月」的人；1.3 对应 Android 常见的「特大」，是我们要够到的目标）。**实际落定：0.9 / 1.0 / 1.1 / 1.2** —— 360dp 中文下 1.3 让网格溢出 13dp、1.25 溢出 6dp、1.2 为 0；既然天花板可调，就按 §5 那条「宁可档位小」办。大档同时从 1.15 收到 1.1（1.15 与 1.2 只差 4%，用户分不出两档）。
- **天花板是我们的，所以它由「还装不装得下」决定**：跑完 §6 的五处收口之后，把四档在 **320dp 与 360dp** 上各渲一遍（§4.4 的阶梯图做法），**「特大」定在仍然满足 §2 三条规矩的最大那一档**。若 1.3 收不住，就把 1.3 降成 1.25 或 1.2 —— **宁可把档位调小，也不许留一处省略号。**（这一条是本设计与「跟系统字号」路线最大的不同：上限是可选的。）
- **因为我们知道有哪几档，就不必让一份版式容忍一切**：允许**逐档定版式**，差量很小 —— 顶栏一行还是两行、卡片里那两行放几行、列表行高。**这正是「字号自管」换来的东西**：不是少干活，而是把「无限大」换成「四个已知的点」。

**一档到底的判据（写死，免得靠感觉）**：

> 在 320dp 与 360dp 两个宽度上、该档下把日历页渲一遍 —— 顶栏年月完整、网格 6 行全在、信息卡内容全部可见且**没有内部滚动**、没有任何 `didExceedMaxLines`。

## 6. 五类各自怎么收

### 6.1 日历顶栏的年月

**现状**：一行排死 —— `‹` ＋ `[年月，Expanded]` ＋ `›` ＋ `[时段总览]` ＋ `[今天]`，年月拿「剩多少算多少」，装不下就 `.ellipsis`。
**收法**：让**这一行自己量**（`TextPainter` 量年月串的排版宽，与 `info_card_metrics` 同一套路），装不下就走**已有的两行档**（`‹ 年月 ›` / `时段总览 … 今天`，今天只留图标）。**两行档是我们的「大/特大」这两档的常态版式**，不是应急 —— 这正是 §5 说的「逐档定版式」。两行档也装不下时（320dp@特大）**才**用 `FittedBox(scaleDown)`。

### 6.2 底栏信息卡

**现状（以代码为准，订正过一次）**：农历那行**已经是 `maxLines: 2` + 省略号**（`calendar_screen.dart:2476`，`info_card_metrics.dart` 也按 2 行量），1.3× 下两行仍不够；班次行是 **`maxLines: 1`**。卡的高度是**按月**（该月最满的一天）实测的、与选中哪天无关 —— 那条约束由 `calendar_screen_test.dart`「点开某天」用例盯着，本轮**不能破坏**。

**收法**：**卡内不许滚动**（§2 第 2 条），所以卡必须在我们每一档下都装得下 —— 允许这两行折到 3 行、卡片跟着长高，网格拿到剩下的高度。**如果某一档下网格因此保不住 6 行，就按 §5 把那一档降下来**（而不是给卡片加滚动）。

### 6.3 列表行的副标题

**现状**：`ListTile` 的 `subtitle` 默认一行 + 省略号。
**收法**：全 app 列表副标题提到 **最多 2 行**，**并且把行高一起放开**（`isThreeLine: true`，或换掉 `ListTile`）—— 只改 `maxLines` 不改行高的话，Tile 会把第二行裁掉，而**段落自己认为「我没被截」**，§8 的判据 1 看不见（判据 2 才抓得住，见 §8）。
例外是**真的只能一行的密集列表**（闹钟页那种一行里并排时间+名称的）：那里把值那一列走 `FittedBox(scaleDown)`。

### 6.4 编辑器的字段标签与值

**现状**：`_labelValueRow`（v0.9.18 抽出来的那份）左标签右值，窄/大字号下两边都省略 —— **且这一类在 360dp、正常字号下就已经在省略**。
**收法**：右边的**值**按可用宽等比缩小（它短、且是主角），左边的**标签**允许折到 2 行；旁边的提示（`可选，如「午休」`）允许 2 行。

### 6.5 14 天预览条

**现状**：7 列 × 2 行（`schedule_editor_screen.dart:427`，选 7 列是为了与日历节奏一致，两行排满就没有「最后一格吊在半路」的裁切），每格约 40–48dp。
**收法**：格内文字走 `FittedBox(scaleDown)`（与日历格子同一条规矩）。它是**定尺的点阵**，不折行、不省略。

## 7. 工装要补的那一维

`visualVariants` 现在只有（浅色/深色/英文/横屏/小窗）×（标准/液态），尺寸是四个固定值。补法是给变体加一个 `fontScale`，并加两个变体：**`360×780 @特大`** 与 **`320×640 @特大`**。

**只给「常设屏单」那 6 屏铺**（4 个 tab + 编辑排班 + 排班管理，约 12 张新图），其余屏靠 §8 的护栏兜。

## 8. 常设护栏：把探针变成测试

`test/` 下新增一条，判据就是探针那两条：**把全部屏在我们每一档字号下渲一遍，任何「字被吃掉了」都算失败**，报出那串文字与它在哪一屏。

**判据要抓两种截断，只抓一种会漏：**

1. **段落自己截的** —— `RenderParagraph.didExceedMaxLines == true`。现在的 `.ellipsis` 全是这一类。
2. **容器把段落裁短了** —— 这一种 `didExceedMaxLines` 是 **`false`**，判据 1 会瞎。典型就是 §6.3 那个 `ListTile`。判据取「**段落在当前宽度下本来需要的高度 > 它实际拿到的高度**」（`getMaxIntrinsicHeight(width)` 比 `size.height`）。

**跑哪些档 / 语言：**

- **每一档字号 × 320dp 与 360dp**（保证线），加上现有的 420×900 与 200×400 冒烟。
- **中文与英文都跑**：英文文案普遍更长，「英文被静默省略」是同一条缺陷。深色不改变文字排版，**不单独跑**。
- **再加一条结构断言**：日历页在每一档下 —— 网格那 6 行**全部落在视口内**，且**网格与信息卡的 `maxScrollExtent` 都是 0**（`tester.state<ScrollableState>(...)` 读 `position.maxScrollExtent`）。**「没有东西可滚」比「滚动偏移为 0」更准**：后者只要没人滚过就成立。这是 §2 第 2、3 条唯一能被断言的形态。

其余规矩：

- **具名白名单**：本来就该缩写的（`LunarInfo.cellLabel` 那类）写在一个 `const` 表里、每条带理由；命中白名单要打日志（与 `design_tokens_test.dart` 的豁免同一套规矩 —— 故意不查的东西要看得见）。
- **顺手把现有的「溢出」断言也搬进来**（它现在只在出图用例里）。
- **两条判据各自反向验证**：把 §6.1 的顶栏改回 `.ellipsis` → 判据 1 立刻红；把 §6.3 的 `isThreeLine` 拿掉 → 判据 2 立刻红。**判据 2 是这一轮新加的鉴别力，不反向验证一次，没人知道它抓不抓得住。**

这条护栏的价值在于**它不需要有人去看图**：以后任何人往界面里加一行字，只要它在我们提供的任何一档下装不下，测试就会说话。

## 9. 验收

- `flutter analyze` 0 error / 0 warning。
- `flutter test` 全绿（新增护栏 + 两条反向验证）。
- `flutter test tool/visual/` 全绿；新增的两档共 ~12 张图**逐张看过** —— 看图是唯一能发现「缩得太小而看不清」的手段，护栏只保证「没省略」，保证不了「还读得出来」。
- **逐档出一遍阶梯图**（§5 的做法），把四档 ×（320dp / 360dp）摆在一起看一遍，确认每一档都还是「这个 App 的样子」。
- 真机复核（用户手上那台 Redmi，`wm size` 走一遍 §4.4 的宽度档；**系统字号那一维现在不需要再走** —— 它已经被挡在门外了，但要顺手验一次「系统调到 200%，App 不变」）。

## 10. 明确不做的

- **不跟系统字号**（用户 2026-10-13 拍板）；代价已在 §3 写明。
- **不改字号的绝对大小**（12–15sp 这套令牌不动）—— 这一轮只解决「装不下」，不重新设计排版。
- **不给卡片加内部滚动**（§2 第 2 条）。
- **不动原生侧**：桌面小组件仍然吃系统 `sp`（§3 末尾的已知缺口）。
- **不做「按字号换大版式」**（比如大字号下把日历换成列表视图）—— 先看四档收口之后够不够用。
- **不做车机两栏版式**（§4.2）。

## 11. 留给构建者的

- §4.4 的宽度档来自查出来的真实分布（§4.1–4.2 有来源），不是拍的；要加档请先补来源。
- §2 那三条是**总判据**；遇到本文件没列的第六类，按它办。
- §6 的五处各自独立、可以分开验收，但**这一轮一次交付**：先把 §8 的护栏搭起来（它当场会红，红在 §6.2~6.5 那几类上）→ 再逐类修到它转绿 → **最后用阶梯图定「特大」是哪一档** → 才发版。
- §5 的「特大最终取多少」**必须由出图 + 断言共同决定**，不许拍脑袋定 1.3。

### 11.1 起草时替用户定的（看文档时核对一下）

| 定的事 | 理由 |
|---|---|
| 四档起步 0.9 / 1.0 / 1.15 / 1.3 | 0.9 给想一眼看全一个月的人；1.3 对应 Android 常见的「特大」 |
| **「特大」是可达成的目标、不是承诺** —— 收不住就降到能收住的那一档 | 用户的原话是「自己设置**最优**的几种」，天花板可调；宁可档位小，也不留省略号 |
| 字号档位进「我的 → 外观」、默认标准 | 与主题/主色/语言同一处，用户找得到 |
| 一次交付、护栏放最前、修完才发版 | 用户说的「整组过一遍」；分版会让护栏需要一张过渡白名单 |
| 护栏跑中文和英文；不跑深色 | 英文文案更长、属于同一类缺陷；深色不改排版 |
| 车机按 960×540 / 1280×720 / 1920×1080 三档横屏铺 | 同一块 1920×1080 面板按 density 算出的 dp 差三倍 |
| 车机/平板的两栏版式、桌面小组件的 dp 化 —— **都不在本轮** | 各自是独立的一件事 |

### 11.2 用户原话的边界（2026-10-13 已确认）

用户说「尽量不要出现内容省略，**内容还要自己滚**的情况」，随后确认：**就是不要内嵌滚动**，并专门点了日历页 ——「它的日期和今日信息卡片不要出现说内容太多、需要你自己滚的情况」。

**读成两件不许的事**：① 省略号；② **面板里再套一层滚动**（页面级滚动不算 —— 待办/闹钟本来就是列表，整页滚是正常的；**但日历页的网格与信息卡都不许滚**）。由此推出 §2 第 3 条「日历页在每一档下都保持一屏构图」。
