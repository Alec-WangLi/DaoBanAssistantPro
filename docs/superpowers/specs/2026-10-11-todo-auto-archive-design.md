# 待办自动归档（已完成收进底部折叠区）

- 日期：2026-10-11
- 起因：v0.11.0 真机反馈第 1 条。用户原话：「勾选的事项不是代表已完成了吗？但并没有删除，能不能自动归档？归档数可以设成 100 条，这样待办事项多的时候，就不会同时有已完成和未完成的事项，显得很乱。」
- 已确认的一个取舍（2026-10-11）：**先划掉、再收走** —— 勾完那一刻留在原地（划掉、淡下去），等下次进这一页才收进归档。
- 影响版本：v0.11.3 测试版

## 1. 现状

- 待办页是一维平铺列表，没有分区。已完成的**不消失**，只划删除线 + 变淡（`schedule_screen.dart:237-245`、`:249-259`）。
- 排序是**按日期从旧到新**（`app_repository.dart` 的 `watchEvents()`：`date` asc、`timeMinute` asc）—— 于是**过去那些做完的会一直顶在最上面**，正是用户说的「很乱」里最扎眼的一块。
- 已完成的待办**没有任何清理**：只有用户手删、删整个重复系列、或「清空重置」才会消失。
- 重复待办的「历史行」就是普通行：`isCompleted == true` 且 `seriesId != null`。**没有独立的归档表**。
- 不变量「某个系列当前那一条 = 该系列里未完成的那条」**完全由查询推出**（`r.seriesId == s.id && !r.isCompleted`），表上不存指针；防复活的 `skipThrough` 记在**系列**上，不在行上。⇒ **把已完成的行移走 / 删掉，不会破坏这条不变量。**

## 2. 目标 / 非目标

**目标**

- 主列表只列**未完成**的（加上「本次进来之后刚勾掉的」那几条 —— 见 §3）。
- 已完成的收进列表**底部**一个默认收起的「已完成 N 条」折叠区，点开能看到。
- 归档**上限 100 条**，超出丢最旧的。
- 折叠区里每条能**删除**（不提供取消勾选 —— 见 §5 的理由）。

**非目标**

- **不做设置项**：100 写死成常量。用户原话「归档数可以设成 100 条」读作「要的就是 100」，不是「要一个可调开关」。
- **不做单独一页**：多一次跳转不值当，日常只想瞟一眼昨天干完了什么。
- 不改提醒链路（`rescheduleEventReminders` 只关心未完成的行，这一版不动）。
- 不改重复待办的生成规则（`advanceRecurringTodos`）。
- 不改数据表（`isCompleted` 与 `date` 已经够用，**无 schema 变更**）。

**反目标**（技术上做成了也算失败）

- 因为归档而让「当前那一条 = 该系列里未完成的那条」失效 —— 症状是用户勾完、下次打开又冒出一条一样的。
- **任何情况下删掉未完成的行。** 截断只许碰 `isCompleted == true`。
- 勾一条待办时整页跳一下 / 那一条突然飞到底部。

## 3. 「先划掉、再收走」的确切规则

一条待办被勾掉时，**它仍留在主列表里原来的位置**（划掉、淡下去），直到这一页**被重新创建**（切走再回来 / 重开 App）才收进归档区。

实现上：页面 State 里一个 `Set<int> _justCompleted`（行 id）。

- `GlassCheck` 的 `onChanged` 里**先乐观地**把该行 id 放进这个集合（取消勾选则移出），**再**去写库；写库失败再回滚。
  **必须是乐观的**：若等 `await` 完再放，流会先吐出一帧「这一行已经 `isCompleted`、又不在集合里」的状态 —— 那一帧里它会离开主列表、归档边界也跟着重算，正是 §2 反目标里那条「勾一条整页跳一下」。
- 主列表 = `events.where((e) => !e.isCompleted || _justCompleted.contains(e.id))`，**保持 provider 的日期升序** —— 于是刚勾的那条停在原地，不会跳。
- 归档区 = `events.where((e) => e.isCompleted && !_justCompleted.contains(e.id))`，**按日期降序**（最近做完的排最前 —— 这一区是「回头看一眼」，不是「从头读到尾」）。

切 tab 会重建这一页（v0.10.22 明确决定**不做** tab 保活），所以「切走再回来」天然成立，不需要额外机制。

## 4. 上限 100

- 常量 `kArchivedTodoLimit = 100`（放 `domain/` 或 `data/`，由实施定）。
- 截断动作：把**已完成的**行按日期**从旧到新**排，超出的删掉 —— **只许碰 `isCompleted == true` 的行**。
- 跑在**一个**时点：App 启动那段就绪闸（与 `advanceRecurringTodos` 同一处）。
  **刻意不在 `setEventCompleted` 里也跑一次**（原稿写了两个时点，写计划时改了）：待办是按**它的日期**排序丢掉最旧的，而用户完全可能勾一条**去年**的待办 —— 在勾选那一刻就截断的话，它会被**当场删掉**，连「先划掉再收走」这一眼反馈都看不到。放到下次启动再裁，这一趟的反馈就保住了，上限也只是在一趟会话里短暂超出几条。
- 结果显示为「已完成 N 条」里的 N = 当前实际条数（启动后最多 100）。

**删除历史行是安全的**（§1 最后一条已核实）：不变量按 `!isCompleted` 推，`skipThrough` 在系列上。既有先例是 `deleteRecurringTodo` 本来就连带删历史行。

## 5. 折叠区里只有一个动作：删除

**不做「取消勾选」。** 原稿写过它，被 builder-check 推翻了：

- 归档里的行可能是**旧 occurrence**，而同一个系列**已经走到下一次**了（第 1 周勾掉的行在归档里、第 2 周的行才是当前那一条）。对旧的那条 `setEventCompleted(false)` 会让**一个系列出现两条未完成的行** —— 而既有实现处处假定「至多一条」：`recurring_panel` 的 `_edit` 直接 `live.single`（两条时当场抛 `StateError`，点开那个系列就崩），生成器下一次跑又会把旧的那条悄悄收回归档（用户看到的是「我明明取消了勾选，它又变回去了」）。
- 误勾的救援窗口就是**它还在主列表里的那一次**：同一趟里再点一下勾就退回来了（§3 的 `_justCompleted` 保证它还在原地）。这一趟过去之后再改主意，那已经是「改历史」，不是「撤销误点」。

**删除**沿用主列表尾部那颗删除键的语义（一次性直接删；重复项仍走 `_askDeleteRecurring` 的二选一：删整个系列 / 只删这一次）。

⚠️ **但「只删这一次」会踩到一处既有缺陷，这一版必须一起修**：`skipRecurringOccurrence(sid, date)` 现在是无条件写 `skipThrough = dayNumber(date)`。主列表里被删的那条永远是**最新**的 occurrence，所以这个标记只会往前走；而**归档里有更旧的 occurrence** —— 删掉它会把标记**往回写**，于是生成器发现「下一次 occurrence 还在标记之后」，就把用户刚删掉的那一条**又补出来**（「删了又回来」那一类）。

修法：**`skipRecurringOccurrence` 改成单调**（`skipThrough = max(当前, 新)`）。水位线本来就不该倒流 —— 这条无论有没有归档都该修，归档只是让它第一次变得可达。

## 6. 界面

- 折叠区标题行：`已完成 N 条` + 一个展开箭头。收起时只这一行；展开时列出各行（复用主列表那套行配方，含划掉与删除键）。
- **主列表为空时也要能点开折叠区**：现在的空态是整块居中一句话（`schedule_screen.dart:133-147`）。主列表为空但归档非空时，那句话仍要出现（「还没有待办事项」之类），而折叠区挂在它下面 —— **不能让归档区被空态顶掉**。
- 新 l10n：`archivedTodos(int n)`（`已完成 $n 条` / `$n completed`）、`archivedTodosEmpty` 之类；中英语序不同，整串交给 `t()`，别拼前缀。
- 底部留白仍走 `kFloatingActionInset`（FAB 压着列表尾部那个既有约束不变）。

## 7. 验收

**新增用例**

- 仓库层：勾完一条之后它仍在「本次可见」的那一批里；`_justCompleted` 清空后它进归档（用 `ScheduleScreen` 的 widget 测试做，或把这段筛选抽成纯函数直接测 —— 由实施选）。
- 仓库层：截断到 100 —— 造 105 条已完成 + 3 条未完成，跑截断，断言**剩 100 条已完成、3 条未完成一条没少**，且丢的是**日期最旧的**那 5 条。
- 仓库层：**截断绝不碰未完成的行** —— 造 101 条已完成但**日期全都早于**某一条未完成的，跑截断，断言那条未完成还在。
- 界面层：主列表里不出现已完成的行（除刚勾的）；折叠区标题的 N 与展开后的行数一致。
- 界面层：勾掉一条 → 它**仍在主列表里、且位置不变**（划掉）；重建页面后 → 它进了折叠区。
- 界面层：折叠区里取消勾选 → 它回到主列表且未划掉。
- 界面层：重复待办的历史行也在折叠区里（不再混在主列表）。
- **仓库层：`skipRecurringOccurrence` 单调** —— 先删新的那条 occurrence、再删归档里旧的那条，断言生成器**不会**把新的那条补回来（水位线不倒流）。
- **界面层（走 `HomeShell`）**：切走再切回，断言刚勾的那条**已经进了折叠区**。这一条不是凑数 —— 「下次进来才收走」唯一靠的是 `PageView` 会把离屏那一页 dispose（v0.10.22 明确决定不做 tab 保活），而现有待办用例都是**直接挂 `ScheduleScreen`**、观察不到这件事。将来谁把保活加回来，只有这条用例会红。

**既定用例 / 基线要跟着改的**

- builder-check 找过一遍：`recurring_screen_test.dart` 里**没有**「勾过的行仍在主列表里」那种按行数断言的用例（原稿这句猜错了）。
- `advance_recurring_test.dart` 那几条断言「历史行留着」的是**仓库层**的，按设计不受影响。
- 真正会变的是**工装基线**：`05_todos` / `24_todos_recurring` / `39_todos_liquid` 那几屏的种子库里带已完成的行，它们会从主列表挪进折叠区 ⇒ 那几张图必然变。按仓库规矩逐张比一遍，把「变了」与「该变」对上。

**工装**

- 新屏（或改既有屏）：`05_todos` 一族的折叠区**收起**与**展开**两态。归档区里的行、以及「主列表为空 + 归档非空」那一态，只有出图能看出版式对不对。

## 8. 留给实施的决定

- `_justCompleted` 的筛选是抽成纯函数（好单测）还是留在 State 里（跟 provider 近）。
- 截断常量的落点与函数名。
- 折叠区那一行小标题的措辞（含英文），以及展开 / 收起要不要动效。
- 归档行的视觉：与主列表行**完全同一套**（含划掉与淡），还是收得更紧一档（更矮、无副标题）。
