# 班次颜色扩展与自定义取色（设计）

- 日期：2026-10-11
- 起因：v0.11.0 真机反馈第 3 条。用户原话：「咱们在编辑排班界面，目前每个班次只有 8 种颜色。能不能拓展颜色，并加入自定义颜色功能？可以自己取色，或者输入那个叫什么颜色的数值。」v0.11.3 真机测完后用户又补了一句：「里面没有我想要的，所以用户反馈，还需要一个自定义颜色。」
- 影响版本：v0.11.5 测试版
- 与用户的约定（2026-10-11）：
  - **自定义色不设限、不警告** —— 用户原话：「即使到时候桌面小组件确实因为他选的颜色不太好看，那也是他的问题。」
  - **反过来，我们给的那批默认色必须保证在日历和桌面小组件上都看得清** —— 这是我们的责任。
  - 自定义色的用途是**照着调出来**（用户心里已经有一个具体的色），**顶部的十六进制输入框**是主要入口。
  - **不做吸色**（从图片或屏幕取色）—— Android 上要么全程录屏权限、要么搬一整套相册进来，为一个班次颜色不值当；而用户要的是「把那个色原样调出来」，十六进制比吸色更准。

## 1. 现状

**可选颜色只有 8 个，全 app 只有一处盘**：`app/lib/features/calendar/schedule_editor_screen.dart:42-45` 的 `_palette`（`0xFF4C8DFF / 0xFF7A5CFF / 0xFF9AA0B4 / 0xFF5A5F73 / 0xFF34C759 / 0xFFFF9F0A / 0xFFFF375F / 0xFF00C7BE`）。两个消费点：取色弹层（`:1505`）与**新建班次时循环取色**（`:1595`）。Kotlin 侧没有盘（`WidgetChip` 收任意 ARGB），工装里也没有盘（只有写死的夹具色）。

**颜色怎么存**：`ShiftClass.color` 是一个 ARGB `int`（`domain/shift_rotation.dart:194`），默认 `0xFF5B7FFF`（**注意：这个默认值不在那 8 个盘色里**，`shift_rotation.dart:165` / `app_database.dart:64` / `schedule_template.dart:140` 三处都是它）；随方案落库、随「我的模板」的 JSON 一起走。**没有任何东西按颜色做判断**，所以换一批预设不动数据库。

**内置模板烘着这 8 个色号**：`domain/shift_templates.dart:178-222` 里 13 个班次原型逐个写死了颜色，8 个盘色全都用到了 —— 而且**没有「角色 → 颜色」的映射**，颜色是逐个原型字面量写的。⇒ 盘里少任何一颗，都会让某个内置模板的班次指向一个**取色盘上再也选不到**的颜色。

**这 8 颗色号还被两处测试写死**：`test/design_tokens_test.dart:990-1001`（拿它们逐个断言 `onSolid` 过 AA）与 `:1014-1018`（钉住其中 5 颗的具体返回值）；另 `test/schedule_editor_test.dart:1087-1097` 断言新建班次取到 `0xFF4C8DFF`。

**一处死代码**：`core/theme/app_colors.dart:19-22` 的 `shiftDay/shiftNight/shiftAfterNight/shiftRest` —— 注释说它们是「班次数据色」，但**全仓没有任何引用**（真正的默认值在 `shift_rotation.dart` 与 `shift_templates.dart`）。这一版不动它，留一笔。

### 一个自定义色要在这些地方都成立

| 画法 | 在哪 | 配方 |
|---|---|---|
| **实心 + 文字** | 日历格子里**选中**那一格的胶囊（`calendar_screen.dart:1916/1918`）、编辑器的 `GlassChoiceChip` 选中态（`glass_choice_chip.dart:66/95`） | 实心填充 + `AppTokens.onSolid` 取黑或白 |
| **14% 淡染 + 45% 描边 + 中性字** | 日历格子胶囊（`calendar_screen.dart:1916/1936/1919`）、信息卡「其他班组」小胶囊（`:2719/2721`）、信息卡的「已调班」徽章（`:1989/1991`）、桌面小组件的所有班次胶囊（`WidgetChip.kt:40-72`，`alpha 36/115`） | 见 §4 |
| **16% / 50%** | **只有编辑器底部那条 14 天预览条**（`schedule_editor_screen.dart:464/466`）—— 全仓唯一一处比例不同的 | 比 14/45 更重，不是约束方 |
| **实心，无文字** | 信息卡左侧色条（`:2691`）、信息卡班次圆点（`:2523`）、编辑器行末圆点（`:839`）、取色盘上的色块（`:1513`）、「调整班次」选择层的色点（`shift_override_picker.dart:203`）、模板选择页的色点（`shift_template_picker_screen.dart:515`）、桌面的 bar/circle（`WidgetRenderer.kt:619/674/740`） | 直接铺 |
| **当文字色用** | 闹钟页某处标题（`alarm_screen.dart:257`，走 `inkFor`） | `inkFor` |
| **刻意不走 `inkFor`** | 桌面小组件的「已调班」文字用班次色本身（`WidgetRenderer.kt:702`，`:744-746` 写明是有意为之） | — |

**⚠️ 两条只有做过才知道的约束（都指向同一件事：自定义色一律不透明）**：

1. **`WidgetChip.tintedChip` 里的 `Paint.setAlpha` 会覆盖颜色自带的 alpha 字节**（`WidgetChip.kt:52-64`，`WidgetRenderer.kt:266-270` 也警告过）—— 一个带透明度的自定义色，在桌面上会渲成一道实心描边环，而不是更淡的一层。
2. **`widget_snapshot.dart:141` 用 `color: 0` 当「这天没班」的哨兵**（Kotlin 侧 `WidgetRenderer.kt:620/676` 靠 `hasShift` 兜底）—— 一个全透明的自定义色会撞上它。

⇒ **十六进制输入框只收 6 位（`#RRGGBB`），不收 alpha**。这条不是省事，是上面两条逼出来的。

## 2. 目标 / 非目标

**目标**

- 可选预设从 8 扩到 **16**：色相绕满一圈，明度分两档。
- 新增**自定义取色**：色相条 + 饱和度/明度方盘 + 十六进制输入框。
- **默认那 16 个必须保证在日历格子与桌面小组件上都看得清**（判据见 §4）。

**非目标**

- 不做吸色（见上）。
- 不给自定义色设取值范围或弹警告（见上）。
- 不动 `ShiftClass` 的结构、不加表、不加列 —— 颜色本来就是一个 int。
- 不改桌面小组件的原生渲染（Kotlin 侧一个字都不动：它本来只认一个 int 色号 + 既定配方）。

**反目标**（技术上做成了也算失败）

- 预设里混进一个「在浅色日历上基本看不见 / 在深色桌面上糊成一片」的颜色。
- 自定义取色把某一档应用不上去（比如选了色却只改了预览、没落到班次上）。
- 取色的面在**小窗 200×400** 下溢出或够不着「确定」。

## 3. 预设：8 → 16

**这一版取「现有八个 + 新加八个」—— 这是个硬约束，不是偏好。** 理由查过（不是猜的）：`shift_templates.dart` 里的内置班次原型烘着其中 **7 个**盘色 —— 白班蓝 / 夜班紫 / 下夜灰蓝 / 大休深灰 / 橙 / 玫红 / 青。盘里少哪一颗，用它的那些内置模板班次就指向一个**取色盘上再也选不到**的颜色：不崩，但那个班次打开取色层时一颗都不高亮，用户想改都不知道从哪儿改回去。

**唯一空着的是绿 `#34C759`** —— 全仓除了盘本身没有任何引用。（**不是**「八个全被模板用到了」；这一条是 builder check 纠正的。）它仍留在盘里（何必删），但真要挪一颗，它是唯一不欠谁的。

⇒ **给用户挑的那张图是「在这八颗不动的前提下挑新加的八颗」**，不是重挑十六颗。他要是说「现有的某颗我也要换」，那是他的决定 —— 但得先把上面那条代价讲清楚再换。

**新加那八个的目标**：补上现在空着的色相段 —— 正红、品红、浅蓝、靛蓝、深绿、深青、棕，以及**黄**那一档。

**选取原则**（三条，按优先级）：

1. **每一个都必须过 §4 那条线** —— 这是硬闸，先筛再挑。
2. **色相铺满**：现在这八个里黄与红是空的，而「心里有个具体的色」的人多半落在那两段。
3. **在同一段色相里尽量拉开明度**：让人不用开取色盘也能挑到「深一点的那个」。

**新加那八个的提议**（已逐个量过 §4 那条线，全部过）：

| 色号 | 是什么 | 四处卡底里的**最小**（门槛 1.34906） |
|---|---|---|
| `#E53935` | 红 | 1.662 |
| `#D81B60` | 品红 | 1.500 |
| `#B8860B` | 琥珀（**黄**那一档） | 1.585 |
| `#E65100` | 深橙 | 1.778 |
| `#2E7D32` | 深绿 | 1.591 |
| `#00796B` | 深青 | 1.548 |
| `#795548` | 棕 | 1.436 |
| `#F06292` | 粉 | 1.595 |

另有四个**备选**（按四处卡底重算，**也都过**那条线）：`#7CB342` 黄绿（1.427）、`#1E4FD8` 靛蓝（1.390）、`#29B6F6` 浅蓝（1.419）、`#9C7A00` 暗金（1.708）。

⚠️ **这八颗（以及那四个备选）是 2026-10-11 出的那张并排对照图交用户挑过之后定的** —— 用户的原话是「你推荐呗」，即**照提议的这一组**。表里的数字按 §4 那四处卡底重算过，与当时图上只标 App 两处的数字不同（那是同一件事在更宽的模型下的读数）。

⚠️ **这一批是提议，不是定案** —— 2026-10-11 出了一张**并排对照图**（每颗都画了实心 / 浅色卡上的胶囊 / 深色卡上的胶囊三态，下面标着实测的下界）交给用户挑，**以他挑的那一组为准**。理由：这一条反馈的原文就是「里面没有我想要的」—— 那是一个审美判断。仓库的既有做法也是这样（v0.10.7 / v0.10.8 / v0.10.12 / v0.10.18 都是「几档并排出图，用户在图上选」）。

### ⚠️ 一处对用户说法的订正（量出来的）

2026-10-11 我跟用户说的是「色相铺满，**明度分两档**」。**按 §4 那条线算过之后，这句得收一收。**

那条线把可用颜色夹成了一个**带**，两头都出不去：

|---|---|---|---|
| 正黄 `#FFCC00` | **1.22** | 3.33 | ✗ 白卡上没了 |
| 深紫 `#6A1B9A` | 2.45 | **1.25** | ✗ 深卡上没了 |
| 靛蓝 `#283593` | 2.42 | **1.23** | ✗ 深卡上没了 |

**所以「明度分两档」的深色那一档只能浅尝辄止** —— 真正的深色（深紫 / 靛 / 深棕）在深色主题下会糊进卡片里。这一档实际能给的是「同一色相的**浓**一点的那颗」，不是真正的暗色。

**另外，「黄」这一档只能是琥珀 / 暗金 / 橄榄那一类** —— 正黄在浅色卡片上过不了线（浅色卡底是白的，14%/45% 合成之后一个亮黄的描边基本就是白色）。这件事值得在文档里留一笔：**它看起来像「调色盘少了黄色」，其实是被那条线筛掉的。**


## 4. 硬约束：默认色必须过「日历 + 桌面小组件」那一关

**为什么这一条必须量、不能眼估**：日历格子和桌面小组件上的班次色**不是直接铺上去的**，是「**14% 淡染 + 45% 描边 + 中性字**」那一套配方（与 App 日历格同一套；桌面小组件侧在 `WidgetChip.tintedChip`）。淡染只有 14%，所以**真正让那颗胶囊读得出来的是那道 45% 的描边**。一个接近卡片底色的色号会让描边也近乎消失 —— 那种颜色「看起来还行」是因为在取色盘里它是实心的，落到日历上就没了。

**判据（可计算、不需要渲染）**：对每个预设色 `c`，分别算它在**浅色卡底**与**深色卡底**上的

- 描边 = `c` 在卡底上按 45% 合成后的颜色，与卡底的对比度；
- 淡染 = 按 14% 合成后与卡底的对比度。

**四处卡底（都要量）**：

| 在哪 | 卡底 | 怎么来的 |
|---|---|---|
| App · 浅色 | `#FFFFFF` | 页面 `#F5F6FA` 上压 92% 的白卡 |
| App · 深色 | `#16161E` | `AppTokens.surfaceDark`（`design_tokens.dart:13`，仓库既有对比度用例用的也是它） |
| 桌面小组件 · 浅色主题 | `#F5F5F5` | `wg_card_to_light` = `#F5FFFFFF`（96% 白）压**纯黑壁纸** —— 它最暗的一档 |
| 桌面小组件 · 深色主题 | `#24242B` | `wg_card_to_dark` = `#F016161E`（94% `surfaceDark`）压**纯白壁纸** —— 它最亮的一档 |

**桌面那两档必须算**（用户 2026-10-11 拍板，见 §8）。`WidgetChip.tintedChip` 与 App 走的是同一套 14%/45% 配方，但小组件的卡是**半透明压在任意壁纸上**的 —— `widget_colors.xml` 顶部那段注释把这件事讲透了（它已经为此把不透明度提到 94~97%）。壁纸的取值范围就是上面两个极端，所以那两行是最坏情况。

**门槛：1.34906。** 取法是「把现有八个在**这四处**卡底上逐颗算一遍，取最小的那个」—— 落在 `#FF9F0A` 压小组件浅色卡（`#F5F5F5`）上。这条线不是拍的 WCAG 数字：这套配方本身就刻意很轻，换成 3:1 那种门槛等于要重做整张日历与三张卡片的观感，远超这一版的范围。

⚠️ **写用例时把门槛写成 `1.3490`，别四舍五入到 `1.35`** —— 而**更早一稿里的 1.395 / 1.39472 已经作废**：那两个数是**只算 App 两处卡底**得出的。两版数字都被 `#FF9F0A` 卡住，因为它既是定线的那颗、又留在盘里（§3）。**`>= 1.3490` 它过（1.34906），`>= 1.35` 它就红** —— 这正是这道门槛最容易第一跑就挂的地方。

**模型：描边直接压在卡底上**（不是压在 14% 淡染上）。这是**有意的保守取法** —— 两个平台实际画的是「45% 描边压在 14% 淡染**上面**」，合成出来约 52.7% 的颜色，比本模型**更清楚**（例：`#4C8DFF` 实际 1.787，本模型 1.633）。取保守的那一侧，门槛才拦得住东西。

**现有八个实测**（描边对卡底）：

| 色 | 白卡 | 深卡 |
|---|---|---|
| `#4C8DFF` 白班蓝 | 1.633 | 2.114 |
| `#7A5CFF` 夜班紫 | 1.837 | 1.787 |
| `#9AA0B4` 下夜灰蓝 | 1.477 | 2.397 |
| `#5A5F73` 大休深灰 | 2.001 | 1.522 |
| `#34C759` 绿 | 1.445 | 2.585 |
| `#FF9F0A` 橙 | **1.395** | 2.713 |
| `#FF375F` 玫红 | 1.855 | 1.907 |
| `#00C7BE` 青 | 1.447 | 2.650 |

**淡染那一列不用列**：14% 合成之后全都落在 1.11~1.28 之间，本来就几乎贴着底色 —— 这一区的可读性**全压在描边上**，所以判据只看描边。这也解释了为什么「在取色盘里看着挺清楚、落到日历上就没了」：盘里看的是**实心**色，日历上是 14% 的一层。**

**谁来守**：一条**纯函数用例**（不需要渲染、不需要真机）：遍历 16 个预设 × 2 档卡底，逐颗算描边合成后的对比度，断言每一个都 ≥ 1.395。另外出图目视核对一遍（`02_editor_*` 与 `01_calendar_*`）。

**自定义色不在这条线内**（用户明确拍板：他自己选得不合适是他的事）。但**取色的那个面上要摆一颗真的日历格子当小样**，让他自己看得见 —— 这是那一条拍板的配套：不拦你，但也不让你蒙着选。

## 5. 取色的面

玻璃弹层（`showGlassSheet` + `GlassPanel(solid: true)`，与现在这个同一个壳），自上而下：

1. **预览**：当前颜色一颗大圆点 + **十六进制输入框**（可编辑，接受 `#RRGGBB` / `RRGGBB`，大小写都收；非法输入不生效、输入框转为警示色）。
2. **一颗真的日历格子小样**：把它按 §4 那套配方画出来（浅色 / 深色各一颗），让人一眼看到「落到日历上是什么样」。
3. **色相条**（横向）+ **饱和度 / 明度方盘**。
4. **16 颗预设**（`Wrap`，与现在同一套圆点配方）。**当前色在其中时带选中描边；不在其中时一颗都不带描边** —— 这是既有行为，而 `0xFF5B7FFF`（域 / 库 / 模板三处的默认色，见 §1）**从来就不在任何一版盘里**，所以「一颗都不高亮」是会真实发生的；那时候「当前是什么色」只由上面那颗预览圆点承担。
5. **取消 / 确定** 两颗按钮（`GlassActionButton` 的 secondary / primary）。

**一处与现在不同的交互，需要留意**：现在是「点一颗圆点 = 立即应用并关窗」。加了方盘之后，**「点一下就提交」与「拖着调」混在一层里会有歧义**（拖完松手算不算提交？），所以这一版统一成**选完点「确定」**。代价：走预设那条快路多一次点击。**这是本设计里唯一一处「为交互一致性牺牲速度」的地方**，如果用户嫌慢，退路是「点预设 = 直接确定，动方盘 / 改十六进制才需要按确定」。

**小窗 200×400 与键盘**：整层可滚动（`SingleChildScrollView`），方盘高度取 `min(160, 可用高)`。**「确定」必须量着 `MediaQuery.viewInsetsOf(context).bottom` 来留位** —— 十六进制那个输入框会弹起软键盘，把可用高吃掉一大截；这正是 v0.7.3 那个坑的同一类（键盘把动作行顶出面板，按钮画在屏幕上却点不到，见 `AGENTS.md`）。**别只按「可用高」算。**

**两处沿用既有约定的、文档不写就得自己猜的**：

- **十六进制框与色相条 / 方盘里那一串颜色字面量会被令牌守门拦下**（`design_tokens_test.dart` 不许 `lib/` 里出现裸 `Color(0x…)`，`app_colors.dart` / `app_theme.dart` 除外）。色相条本质上就是一串颜色 —— 用现成的豁免写法 `// design-tokens-ignore: <理由>`（同文件里已有先例）。**预设那 16 颗仍然存 `int`**（与现在的 `_palette` 一样），不要变成 `Color(0xFF…)`。
- **触觉**：现在的色块是裸 `GestureDetector`，**不震**。新盘沿用 —— 点预设、拖方盘都不发触觉（`core/haptics.dart` 的三档语义里没有「调了个颜色」这一档）。这是一处**明写的选择**，不是漏掉的。

## 6. 界面与文案

- 新 l10n：`shiftColorCustom`（自定义）、`shiftColorHex`（十六进制）、`shiftColorInvalidHex`（颜色值格式不对）、以及取消 / 确定沿用既有的 `L10n.cancel` / `L10n.ok`。
- 编辑页那颗可点的颜色圆点（`_colorDot`）不变 —— 变的是它弹出来的那一层。

## 7. 验收

**新增用例**

- **纯函数：16 个预设逐个过 §4 那条线** —— ⚠️ **只断言描边**（§4 末尾那条：淡染那一列只是记录，14% 合成落在 1.11~1.28，**按它断言是无解的**），**四处卡底各算一次**（含桌面小组件那两档半透明卡 —— 它是定出门槛的那一处），门槛取 **1.3490**。这一条是这一版的主要护栏。
- **纯函数：门槛自己也要钉住** —— 断言 `#FF9F0A` 在这四处上的最小值就等于那条门槛（1.34906）。理由：门槛是「现有八个的下界」，要是哪天有人调了现有某颗、或改了卡底常量，这个数会漂 —— 让它漂的时候测试当场红，而不是悄悄放宽。
- **纯函数：那 16 颗要放在一个能被测到的公开位置。** 现在是 `_ScheduleEditorScreenState` 里的 private `static const _palette`（`schedule_editor_screen.dart:42`），上面那条护栏**读不到它**。挪到 `domain/shift_palette.dart` 之类的地方；**仍然存 `int`**，别变成 `Color`。
- 纯函数：十六进制解析 —— `#RRGGBB` / `RRGGBB` / 大小写 / 三位缩写怎么处理 / 非法输入返回 null（**不进位、不抛异常**）。
- 界面层：点开取色层 → 选中一颗预设 → 点「确定」→ **班次的颜色真的变了**（读回 `ShiftClass.color`）。
- 界面层：在十六进制框里敲一个合法值 → 点「确定」→ 颜色是敲的那个。
- 界面层：敲一个**非法**值 → 点「确定」→ 颜色**不变**（不许把非法值当成某个默认色写进去）。
- 界面层：点「取消」→ 颜色不变。
- 界面层（小窗 200×400）：整层不溢出、「确定」点得到。
- **一组既有用例要跟着改**（§1 查到的）：
  - `test/design_tokens_test.dart:990-1001` 那份写死的 8 颗样本要换成 16 颗 —— 它逐个断言 **`onSolid` 过 AA**。这一条**不会**成为新预设的负担：`onSolid` 取黑或白里更好的那个，而 `max(对白, 对黑)` 的最小值就落在亮度 0.179 处、恒 ≥ 4.58:1，**任何颜色都过**。加进去只是让护栏跟着盘走。
  - ⚠️ **`test/schedule_editor_test.dart:1087-1097` 并不能当「新建班次循环取色」的护栏**（builder check 查出来的）：那条用例是自己造了一个带指定颜色的班次、只断言它渲染出来，**压根没走** `_addClass` 里那句 `_palette[idx % …]`；而 `_pickColor` 与那个循环取色**目前一条用例都没有**。所以「新盘第一个仍放 `#4C8DFF`」这条纪律是**没有护栏的** —— 顺手给 `_addClass` 的循环取色补一条（它现在整条裸着）。

## 8. 两条已拍板，与留给实施的

**用户 2026-10-11 的原话是「你推荐呗」** —— 即照下面这两条推荐办：

1. **护栏覆盖桌面小组件。** 卡底按 §4 那**四处**算（含小组件半透明卡的两个极端），门槛由「现有八个在这四处上的下界」定出：**1.34906**。
   代价要写明：这条线比「只管 App」那一版（1.39472）**低一点点** —— 低下去的那部分**正是现有盘里橙色本来就有的问题**，不是新预设带来的。换句话说，这一版是**把既有的天花板照实量了出来**，而不是降低了标准。
2. **新加的八颗就按 §3 那张表**（现有八个不动，理由在 §3）。四个备选按新模型也全过线，真要换任一颗都有得换。

**留给实施（builder check 顺手定下的）**：

- 方盘**手搓 `CustomPaint`**（色相走渐变、方盘叠两层渐变），不拆成两条滑杆 —— 方盘才是「划一划挑个顺眼的」那件事本身。
- 三位缩写 `#ABC` **收**。合法输入：`#RRGGBB` / `RRGGBB` / `#RGB` / `RGB`，大小写都收；非法 → `null`，**不进位、不抛异常、不改任何状态**。
- 非法输入时**保留上一次的有效色**、输入框转警示色；点「确定」用的仍是那个有效色（§7 有一条钉它）。
- 「取消」与「点外面关掉」都当作没选过（沿用现在那句 `if (picked != null)`，`schedule_editor_screen.dart:1531`）。
- 对比度一律走现成的 `AppTokens.contrastRatio`（`design_tokens.dart:555`），别手搓一份 WCAG。
- 取色层是一个**新的界面态**，要进 `visual_screens.dart` 的屏单（命令式弹层走那层薄壳，见 `AGENTS.md`「新界面一律补进屏单」）。
