## 1. 背景与目标

### 1.1 用户原话

> 小组件展示内容有点问题。首先是高度最窄的时候，我看你的意思是要显示两天的班次信息，但是它第二天的班次信息被遮挡一部分。然后高度应该是三行的时候吧，它要展示三行的班次信息，没问题。然后高度是四行的时候，它还是展示三行的信息。然后每一行的高度变大了，看着有点奇怪，不美观。然后就是高度 5 行的时候，它变成了一周的班次信息，但是显示有点难看呀。高度 6 行的时候也是这样。我想实现的效果是，在高度有限的情况下嘛，咱就把本班的未来 n 天的信息显示一下。然后高度可有的情况下，就显示未来一周的班次信息，然后下方再附上咱的今日信息卡片。

### 1.2 上一版为什么会长成这样（真机实测还原）

v0.8.5 的分档只有三个阈值（`SMALL` 高 <130、`MEDIUM` 130≤高<260、`LARGE` 高 ≥260），而**实测这台机器上高度有七个可达值**（下一节）。于是三个版式被摊到七个高度上，**两个版式被拉伸**：

| 用户观察 | 真因 |
|---|---|
| 「最窄时第二天的信息被遮挡一部分」 | 1 行 63dp 走 `SMALL`（今天一张牌），而那张卡底部有一行「明天 …」预告 —— 63dp 装不下它的第 4 个元素，被裁掉一半。用户读成「设计想显示两天」，其实是它**塞不下自己** |
| 「四行的时候还是三行、每行变大」 | 2 行(158dp) 与 3 行(253dp) **都落在 `MEDIUM`** —— 同一套三行布局塞进两个高度，行高从约 43dp 被拉到约 75dp |
| 「五行/六行变成一周，难看」 | 4~7 行(348~633dp) **全落在 `LARGE`** —— 4×2 的八格被拉伸到最高 633dp，格子又大又空 |

**一句话**：分档按「估算阈值」定，而真机的可达高度是七档等差数列，导致版式与高度不是一一对应。

### 1.3 目标

**高度 → 内容**一一对应，不再有「同一版式被拉成不同高度」：

- 矮：**未来 n 天**的列表，n 随高度增加（2 / 3 / 5 天）
- 高：**网格**（一周或两周）+ 下方**今日信息卡片**（照搬 App 的底栏信息卡）

### 1.4 非目标

见 §10。

## 2. 本次已定决策（来自 2026-09-19 的头脑风暴）

| # | 决策 | 理由 |
|---|---|---|
| ① | **1 行(63dp) 那档 = 两行紧凑列表**（今天 + 明天），与中档同一套行配方 | 用户选定。版式统一、信息最多；「今天一张牌」那一档**取消**（它的位置被它取代） |
| ② | **4 行(348dp) 起换成「网格 + 今日卡片」** | 用户选定 A：348dp 已经放得下网格与卡片两块，最贴「高度可有的情况下」 |
| ③ | **最高的两档（6–7 行）排两周** | 用户选定。快照本来就带 14 天，数据现成；比让格子继续长大更充实 |
| ④ | **今日卡片照搬 App 的底栏信息卡** | 用户选定：含「其他班组」色块与「N 项待办」徽章 |
| ⑤ | **布局用 `addView` 嵌套 RemoteViews** | 用户选定 B。槽位 + 行/格的结构天然对上「按高度显示 N 行/N 格」，且避免五张近千行的重复 XML |
| ⑥ | **网格仍然从今天起排**，今天那格用主色日期标记 | 沿用上一版；今天在网格与卡片里各出现一次，卡片是**详情**不是重复 |

## 3. 尺寸 → 内容映射（真机实测）

**实测数据**（Redmi 25102RKBEC，400dp 宽屏 / 480dpi，横向 4 列；小组件拉满 4 列 = **实测宽 328dp**）：

| 占几行 | 实测高度 | 步长 |
|---|---|---|
| 1 | 63dp | — |
| 2 | 158dp | 95 |
| 3 | 253dp | 95 |
| 4 | 348dp | 95 |
| 5 | 443dp | 95 |
| 6 | 538dp | 95 |
| 7 | 633dp | 95 |

**完美等差数列，步长 95dp。** 上一版从没拿到过这份数据 —— 它只有一次实测（`328x158dp → MEDIUM`），其余靠估算。

> ⚠️ **标定基准只有一把尺：`OPTION_APPWIDGET_MIN_WIDTH/HEIGHT` 报出来的值。**
> 上表的七个数、以及 §3.1 的四个阈值，全都对这把尺成立 —— 因为 `WidgetTier.pick` 收到的就是它
> （Task 1 的评审用 logcat 坐实过：`id=34, 328x158dp → MEDIUM`）。
>
> **另有一把「渲染尺」：卡片实际排版出来的像素尺寸**，Task 1 实测 id=34 是 **342.7 × 173.3 dp**
> ，每轴比报告尺大约 15dp（173.3 不在这条等差数列上，两把尺不同源）。
> **阈值绝不许对渲染尺标定** —— 那会让四个阈值整体平移约 15dp，而 `pick` 收的仍是报告尺，
> 正是这一轮返工的同类病。渲染尺只用来做一件事：**算内容放不放得下**（例如「报 158dp 的实例，
> 布局里实际有约 173dp 可用」—— 固定行高与居中的决策该按这个数核）。

### 3.1 映射表

| 高度（实测 dp） | 档位 | 内容 |
|---|---|---|
| `h < 110` | `LIST_COMPACT` | 列表 **2 天**（今天、明天），行高 22dp |
| `110 ≤ h < 205` | `LIST_3` | 列表 **3 天**，行高 40dp |
| `205 ≤ h < 300` | `LIST_5` | 列表 **5 天**，行高 40dp |
| `300 ≤ h < 490` | `GRID_WEEK` | **一周网格**（8 格，末格空）+ 今日卡片 |
| `h ≥ 490` | `GRID_FORTNIGHT` | **两周网格**（16 格，末两格空）+ 今日卡片 |

**阈值取在实测值的相邻中点**（110 / 205 / 300 / 490），这样任一档都离边界至少 40dp，不会因一两个 dp 的抖动跳档。

**宽度闸门**：网格要求 **宽 ≥ 300dp**（4 列）。窄于 300dp 时，本该走网格的两档**降级为 `LIST_5`** —— 本轮的网格**只有 4 列一种**，不为窄版另做 2 列网格（见 §10）。

> **档位由高度决定，宽度只当网格的闸门。** 这句话要写进 `pick` 的注释：两个入参管的是两件事，别把它们混成一个「面积够大就上网格」的判断 —— 一个 60×633dp 的细长条面积很小但高度很高，它该走 `LIST_5` 而不是网格。

### 3.2 这条映射要写成一个纯函数

`WidgetTier.pick(widthDp, heightDp)` 仍然存在，但档位从三个变五个，且**判定依据是真机实测的 dp 值**，不是估算。实施时用 `AlarmLog.info` 把每次 `onAppWidgetOptionsChanged` 的实测值打出来，对着七档各停一次核对（上一版就是这么标定的，但只标定了一次就上线了 —— 这次要把**七档全过一遍**）。

## 4. 两条结构上的根治

### 4.1 行高/格高固定，不再随高度拉伸

上一版让行用 `layout_weight` 分掉全部高度，所以高度一变、行高就变。现在：

- 每个槽位是**固定高度**（列表行 22/40dp、网格格 56dp）
- 内容整体**垂直居中**，多出来的高度成为上下均匀的留白

### 4.2 最高的两档仍有留白，这是**有意的**

按 §3.1 的固定尺寸估算：

| 档位 | 内容高度（约） | 可用高度 | 留白 |
|---|---|---|---|
| `GRID_WEEK` @348dp | 网格 120 + 卡片 158 ≈ 278 | ~320 | ~42dp |
| `GRID_WEEK` @443dp | 同上 | ~415 | ~137dp |
| `GRID_FORTNIGHT` @538dp | 网格 248 + 卡片 158 ≈ 406 | ~510 | ~104dp |
| `GRID_FORTNIGHT` @633dp | 同上 | ~605 | ~199dp |

**先做垂直居中，真机出图之后再定**要不要让格子略微长大（封顶）或让卡片更舒展。这一条不预设 —— 上一版的教训正是「靠估设定死」。§11 的验证清单会逐档截图。

## 5. 布局结构（`addView` 嵌套 RemoteViews）

### 5.1 为什么改

上一版逐档写死布局：8 格的大卡一张就约 340 行 XML。这次要五档、还有个 16 格的，写死会到近 1500 行且档间高度重复。

`addView` 嵌套让「槽位」与「内容」分开：外层布局只摆**空槽位**，渲染时把同一张「行/格」布局的 N 份塞进去。

### 5.2 一条必须遵守的规则：槽位用 `FrameLayout`

`RemoteViews.addView(viewId, nested)` 把嵌套视图加到容器里，用**容器的默认 LayoutParams**。而：

- `FrameLayout.generateDefaultLayoutParams()` → `MATCH_PARENT × MATCH_PARENT` ✓ **会填满槽位**
- `LinearLayout.generateDefaultLayoutParams()` → `WRAP_CONTENT × WRAP_CONTENT` ✗ 不会填满
- `GridLayout` 的默认参数按容器推导，语义不直观 ✗

所以：**所有槽位一律是 `FrameLayout`**，它自带 `MATCH_PARENT` 语义，嵌套内容自动填满。槽位自己的尺寸由外层布局给（列表：`layout_height="40dp"`；网格：`layout_columnWeight="1"` + `layout_height="56dp"`）。

### 5.3 文件清单

| 文件 | 作用 |
|---|---|
| `layout/widget_list_compact.xml` | 2 个行槽位（22dp） |
| `layout/widget_list.xml` | 5 个行槽位（40dp） |
| `layout/widget_row.xml` | **一张**行：色点 + 相对称法 + 日期 + 班次名 + 时间（被上两者共用） |
| `layout/widget_grid_week.xml` | 8 个格槽位（4×2） |
| `layout/widget_grid_fortnight.xml` | 16 个格槽位（4×4） |
| `layout/widget_cell.xml` | **一张**格：日期 + 班次胶囊（被上两者共用） |
| `layout/widget_today_card.xml` | 今日卡片 |
| `layout/widget_placeholder.xml` | 占位态（沿用，不动） |
| `layout/widget_small.xml` / `widget_medium.xml` / `widget_large.xml` | **删除** |

行/格共用一张布局，靠**渲染期设字号**区分档位：`RemoteViews.setTextViewTextSize(id, TypedValue.COMPLEX_UNIT_SP, size)` 是支持的，所以紧凑档（12sp）与普通档（13–14sp）不必各写一张。

### 5.4 `addView` 嵌套：已真机验证（2026-09-19，Task 1）

结论：**成立**。证据：`work/probe_addview.png` —— 两条 `FrameLayout` 槽位（各 40dp）里
各渲染出一条嵌套的行，红色底 `#44FF0000` 在两条槽位上纵向连续 **239px ≈ 79.7dp = 恰好 2×40dp**，
槽内上下与槽间都**没有深色空档**（卡顶到红底顶 24px = 8dp，正是根布局的 `padding="8dp"`）。

⚠️ 因此一条硬规则：**槽位必须用 `FrameLayout`**。`LinearLayout` 的默认 LayoutParams 是
`WRAP_CONTENT`，嵌套内容会缩成一小团且不报错。

**这条结论的覆盖范围要说准（Task 1 的评审点名）：**

1. 被验的父子链是「**竖向 `LinearLayout` → 直接子 `FrameLayout` 槽位 → `addView` 嵌套内容**」。
   §5.3 的网格档是「`GridLayout` 里放 8/16 个槽位、再往那些槽位里 `addView`」—— **不是同一条
   父子链，本次没覆盖**。动网格之前要在真机上复验一次。
2. 探针的嵌套根**自己显式写了** `android:layout_height="match_parent"`。所以本次证的是
   「嵌套根自己声明的 `match_parent` 能穿过宿主进程的 inflate 被槽位尊重」，
   **不是**「槽位会用默认 LayoutParams 补齐」。§5.3 的 `widget_row.xml` / `widget_cell.xml`
   因此**必须显式写出 `layout_width/height="match_parent"`**，别省。

## 6. 快照要新增的字段

照搬信息卡（决策④）需要三样现在快照里没有的东西：

| 新增 | 来源 | 说明 |
|---|---|---|
| `todayCard.lunarShort` | `lunarOf(date).shortLabel` | 农历短标签（「初八」）。`lunar_info.dart` 是纯 Dart、现成 |
| `todayCard.lunarIsHoliday` | `LunarInfo.isLegalHoliday` | 决定农历那行走 `holiday` 红还是 `muted` |
| `todayCard.adjusted` | `schedule.dayOverrides.containsKey(dayNumber(date))` | 「已调班」徽章 |
| `todayCard.todoCount` | **新入参** | 今日**未完成**待办数。`buildWidgetSnapshot` 现在拿不到待办，要加一个入参（`List<ScheduleEvent>` 或直接一个计数） |
| `todayCard.crews[]` | `schedule.teamShift(i, today)` 逐个班组 | 「其他班组」色块：`{name, abbr, color}`，**不含我们班组** |

`buildWidgetSnapshot` 的签名因此扩为：

```dart
Map<String, Object?> buildWidgetSnapshot({
  required ShiftSchedule? schedule,
  required DateTime now,
  required String themeMode,
  required int accent,
  required int todayTodoCount,   // 新增
})
```

**不变量 A 不破**：农历、班组名、待办文案全部由 Dart 侧 `L10n` / `lunar_info.dart` 产出，原生只排版。

**不变量 B（相对文案按偏移索引）不受影响**：`todayCard` 是「今天」这一天的详情，天生按日期烘焙 —— 它不参与跨天右移（跨天后整份快照会因边界闹钟重渲染，而重渲染时…… **等等，这里有个坑**）。

> ⚠️ **跨天之后 `todayCard` 会腐坏。** 原生手上只有快照，跨天刷新时它拿 `LocalDate.now().toEpochDay()` 去 `days[]` 对表右移 —— 但 `todayCard` 是对**生成那天**的详述，右移不了（农历、待办数、其他班组都是那天的）。
>
> **处理**：`todayCard` 里带上它自己的 `day`（epochDay）。原生渲染时若 `todayCard.day != 今天`，就把今日卡片换成**降级态**（只显示 `days[todayIndex]` 里已有的日期/班次/时间，农历与其他班组留空），而不是把旧数据当成今天显示。**绝不能让卡片理直气壮地写错** —— 这是本设计（以及上一版）反复强调的那条。
>
> 更彻底的做法（本轮**不做**）：跨天闹钟触发时让 Dart 重新生成快照。但小组件刷新时 App 未必在跑（那正是闹钟存在的意义），所以做不到；降级是唯一诚实的答案。

## 7. 今日卡片的配方（照搬 App 的信息卡）

逐项抄 `calendar_screen.dart` 的 `_infoCard`（**完整版**，不是 `compact` 版）：

| 元素 | 配方 |
|---|---|
| 左侧色条 | 4×18dp，`radiusS`(12) 圆角，颜色 = 当天班次色（无班次时用主色） |
| 日期 | `L10n.monthDay`（如「9月19日」），`sectionTitle`(18/w700) |
| 「今天」徽章 | 主色胶囊（14% 淡染底 + 45% 同色描边） |
| 「N 项待办」徽章 | 同一族胶囊，`L10n.pendingTodos(n)`；**仅 `n > 0` 时出现** |
| 农历 | `shortLabel`，`rowSecondary`；`isLegalHoliday` 时走 `AppTokens.holiday` 红 |
| 班次 | 12dp 色点 + 班次名（`rowPrimary`）+ 「已调班」徽章 |
| 时间 | 另起一行（挤在一行会在窄宽下把时间全截掉 —— 那是 App 里踩过的） |
| 其他班组 | 每个班组一个胶囊：14% 淡染底 + 45% 同色描边 + 8dp 色点 + `『班组名 简称』`，文字色走 `AppTokens.inkFor` |

原生侧仍然一个中文字面量都不出现 —— 上面每一项的文字都来自快照。徽章的「14% 淡染底 + 45% 描边」用 `WidgetChip` 已有的圆角位图机制画（颜色动态，不能走静态 `<shape>`）。

**点击**：整张今日卡片 = 打开 App 到日历（与整卡一致）。

## 8. 顺带要修的既有问题

1. **`requestCode` 空间要扩。** 现在每个 widget 占 16 个槽（`Root` + 7 个格）。新版需要 `Root` + 5 个列表行 + 16 个网格格 = 22 个 → **槽位基数从 16 提到 32**。
   注意 `AGENTS.md` 里写着这条保留区间与「同一个 PendingIntent 池既有最高占用 99999、余量只有 1」—— 基址 100000 不变，但基数变 32 后溢出上限从 1.34 亿降到约 6710 万，仍然够用。**`AGENTS.md` 那条要同步更新。**
2. **`empty()` 与正常档复用同一张布局**是上一轮修过的隐患（宿主 `reapply` 时只重放新动作，没被重设的视图保持旧状态）。新版档位变多、共用布局变多，这条风险面**变大**。规则要写死：**每个渲染函数对它用到的每个 id，无条件显式设一次可见性**。
3. **`large()` 里那句描述失准的注释**（「没有班次（空表/休班）时…兜底」）随本次重做一并改准 —— 本计划前后被「描述失准的注释 / 假保证」咬过五次。

## 9. 边界与容错

| 情况 | 表现 |
|---|---|
| 无快照 / 快照过期（`todayIndex < 0`） | 占位态（`widget_placeholder`，沿用不动） |
| `hasSchedule == false`（空白表方案） | 空表提示（沿用 `empty()` 的语义，但要改用新的档位布局） |
| `todayCard.day != 今天`（跨天且 App 未重开） | 今日卡片**降级**：只显示 `days[todayIndex]` 的日期/班次/时间，农历与其他班组留空（§6 的 ⚠️） |
| 今天没有任何其他班组数据（`teamCount == 1`） | 「其他班组」那一块整体隐藏 |
| 今天没有班次（休班） | 卡片照常显示日期/农历/其他班组；班次那一块隐藏 |
| `days[]` 不足以填满网格（窗口末段） | 该格隐藏（沿用上一版的边界闸语义） |
| 宽度 < 300dp | 一律列表档，不上网格 |

## 10. 明确不做

- **窄版网格**（2 列）—— 宽度不足 300dp 时只走列表。真要窄版网格是下一轮的事
- **两周以上**（三周、整月）—— 快照只有 14 天
- **逐分钟倒计时**（沿用上一版决策③）
- **小组件配置页**（沿用决策④）
- **今日卡片里放交互控件**（快速打卡、跳到编辑器）—— 点击仍然只是「开 App / 跳那天」
- **跨天时让 Dart 重新生成快照**（§6 已说明做不到），本轮用降级态
- **`Flutter 位图渲染整卡`**（沿用决策②）

## 13. 风险与坑

1. **`addView` 嵌套是唯一未验证的技术假设**（§5.4）。**实施第一步就验**，验不过退 §5.3 的「逐档写死」。不要铺开五档之后才发现。
2. **跨天后 `todayCard` 会腐坏**（§6 的 ⚠️）。这是本设计最容易静默出错的地方：农历、待办数、其他班组都是**生成那天**的，跨天之后若原样显示就是「理直气壮地写错」—— 这个项目已经被同类问题咬过多次。降级态必须在实现里走通，且要有测试。
3. **槽位必须是 `FrameLayout`**（§5.2）。写成 `LinearLayout` 不会报错，只会让嵌套内容缩成一小团。
4. **可见性要无条件设满**（§8.2）。档位从三个变五个、共用布局从一张变三张，`reapply` 的残留风险面显著变大。
5. **阈值必须按实测 dp 定，且七档全过一遍**（§3.2）。上一版只标定过一次就上线，这是本轮的起因。
6. **`requestCode` 基数从 16 提到 32 之后，溢出上限降到约 6710 万** —— 仍够用，但 `AGENTS.md` 那条文档要跟着改，别留下一句算不平的话（上一轮刚修过一次同类）。
7. **不要跑 `dart format`**（工具链是新版 tall style，一跑就重排整个文件）。
8. **构建环境变量**：bash 里构建必须 `export ANDROID_HOME/JAVA_HOME/GRADLE_USER_HOME` 指向 `toolchain/`。
9. **装真机必须 `build apk --release`**（手机上是 release 密钥签的；卸载重装会丢用户的真实排班数据）。
10. **改了小组件资源色之后，验证前先重启桌面**（小米桌面按资源 id 缓存 drawable）。
