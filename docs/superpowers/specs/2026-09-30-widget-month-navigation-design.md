# 月历小组件：相邻月连起来 + 上下月切换 · 设计规格

> 2026-09-30 头脑风暴定稿。**目标版本由用户拍板**（末位 `Z` 归 AI，`X.Y` 归用户）。

## 1. 背景与目标

用户 v0.9.15 真机反馈的第二条（原话）：

> **「咱们桌面小组件里，最大的那个显示月历的小组件，能不能把上个月和下个月都连起来显示？同时支持切换上下月呢？」**

现状：4×5 那张卡只画**今天所在的月**，月头月尾那一圈格是 `GONE`（挖空），所以卡片看着是一块有洞的月历；而 `LocalDate.now()` 写死了它渲染哪个月，翻不动。

**目标两条**：① 相邻月那几格画出来，整张卡读起来是连续的日子；② 标题行能翻上 / 下月。

**一条不能破的硬约束**：**小组件不依赖 App 进程**。三张卡的数据全部来自上一次 App 运行时算好的快照（`widget_snapshot.dart`），原生只负责排版 —— 这是 v0.8.4 以来这条链路的性质，也是「翻月」必须落盘、不能用进程内状态的原因。

## 2. 已定决策（2026-09-30 拍板）

① **相邻月那几格：日数字变灰，班次胶囊照画** —— 与 App 日历格同一条读法（月分界只靠日数明度差表达）。
② **翻月：标题行左右两个箭头**，`‹  2026年9月  ›`；**点中间那行文字回到今天那个月**。
③ **能翻的范围 = 快照覆盖到的月份**（上月 / 本月 / 下月），到头那侧**箭头变灰**。不做无限翻（那要 App 活着去查库）。
④ **翻走之后跨天、跨月不被拽回来** —— 停在你翻到的那个月。所以锚点存**绝对值**（哪一年哪一月），不是「相对今天的偏移」。

## 3. 现状（要动的四处）

| # | 位置 | 现状 |
|---|---|---|
| 1 | `widget_snapshot.dart` 的 `widgetWindow` | `[min(本月1日, 本周一), 下月最后一天]`，上限 `kWidgetSnapshotMaxDays = 68` |
| 2 | `WidgetRenderer.monthCard` | 月份 = `LocalDate.now()`；42 格中「不在本月」的那些 `GONE` |
| 3 | 原生**没有任何实例状态** | RemoteViews 没有进程内状态，翻到哪个月必须落盘 |
| 4 | 没有「翻月」这条 IPC | 现在只有：点格 → 开 App；整卡 → 开 App；刷新 → `ACTION_REFRESH` |

## 4. 设计

### 4.1 快照窗口（Dart 侧）

```
widgetWindow(now):
  本月 1 日  = 今天所在月的 1 日
  from = (本月-1 个月) 的 1 日所在周的周一
  to   = (本月+1 个月) 的最后一天所在周的周日
```

最坏 105 天（`6 + 31 + 31 + 31 + 6`），`kWidgetSnapshotMaxDays` **68 → 112**（留余量，并由现有断言 `dayCount <= max` 兜住）。

三条要写进代码注释的推论：

- **协议版本仍是 2，不升。** 这次只改窗口**范围**，字段结构一个没动：旧代码读新快照照常渲染「今天那个月」（多出来的天被忽略），新代码读旧快照只会在相邻月那几格降级成 `GONE`。**升版本会把所有小组件立刻打成占位态**（`v` 对不上就按无快照处理），代价远大于收益。
- **`months[]` 不用改**：它本来就是「窗口覆盖到的每个月」的升序列表，3 个月窗口会得到 3~4 条（补齐的那一周可能蹭到第 4 个月），标题仍按「年-月」查。
- **`boundaries` 会变多**（每天最多 3 条 × 105 天）。这只影响这份 JSON 的大小（几十 KB），排下一次刷新仍是「取第一个未来的时刻」，逻辑不动。

**「这个月能不能翻到」的判据**：该月的 **42 格全部落在快照 `days[]` 覆盖的范围内**。
不新增协议字段 —— 原生在 `snap.days` 的首尾日期上现算即可（42 格 = 从该月 1 日所在周的周一起连续 42 天）。这条判据对**上月末/下月初**那些边角格同样成立，也自动处理「App 很久没打开、窗口走偏了」的情形。

### 4.2 原生状态：每个实例一份「显示哪个月」

`WidgetStore` 新增（prefs 仍是 `shift_widget` 那个文件，不另开）：

```
month_<widgetId> : Int   // 那个月 1 日的 epochDay；不存在 = 跟随今天
```

两条纪律：

- **渲染前先校验，不成立就当作「跟随今天」，且不留着。** 锚点那个月的 42 格不全在窗口里（数据过期、被别的状态挤掉）时按 null 处理 —— **让「看到的」与「箭头作用的」永远是同一个状态**。留着一个看不见的锚点，就会出现「点一下箭头跳到莫名其妙的地方」。
- **`ShiftWidgetBase.onDeleted` 里清掉被删实例的锚点。** 不清的话，`widgetId` 被系统复用时新卡片会继承上一张卡的月份 —— 而且是静默的。

### 4.3 渲染（`WidgetRenderer.monthCard`）

- **显示哪个月** = 锚点 ?? `LocalDate.now()` 那个月（再按 4.2 校验一次）。
- **42 格**：从「该月 1 日所在周的周一」起**连续 42 天**，逐格按绝对日期在 `snap.days` 里查（现在也是这么查的，只是起点从「1 日」变成「1 日所在周的周一」）。
- **日数字**：本月内 → `ink`（今天 → `snap.accent`）；**相邻月 → `muted`**。这是唯一表达月分界的地方。
- **班次胶囊**：照常（`hasShift` 决定），相邻月的格也一样画 —— 用户选的就是这个。
- **农历那一行**：照常（法定节假日仍然红）。
- **窗口外的格**：仍然 `GONE`（数据没到，不能画出半张错的）。**注意这与「相邻月」是两回事**：相邻月有数据就画，窗口到头了才不画。
- **标题**：从 `snap.months` 按 (y, m) 查；**查不到就隐藏标题行**（既有纪律，不借相邻月顶上）。
- **点格**：不变 —— 开 App 并跳到那天；相邻月的格同样如此（点 8 月 31 日就跳到 8 月 31 日，语义自洽）。

### 4.4 交互

**布局**（`widget_month_card.xml`）：标题那一个 `TextView` 换成一行：

```
LinearLayout(horizontal, height=28dp)
  ├ TextView  id=wg_m_prev   ‹        （宽 ~32dp）
  ├ TextView  id=wg_m_title  （weight=1，居中，13sp，maxLines=1）
  └ TextView  id=wg_m_next   ›
```

箭头用 `‹` `›` 两个符号（`TextView` 在 RemoteViews 白名单里，也就没有「加一张矢量图」带来的小米缓存 drawable 那类问题；这两个符号与语言无关，不违反「Kotlin 里不许有用户可见的中文字面量」）。

**点击**：两枚箭头各是一枚**广播** `PendingIntent` 打到**已有的** `WidgetRefreshReceiver`（新增一个 action `WIDGET_MONTH_STEP`），extras 带 `widgetId` 与 `delta`（`-1` / `+1`；点标题 = `0` → 清锚点回今天）。

  子视图自己的点击会**吃掉**落在它身上的那一下 —— 整张卡「点哪儿都开 App」那枚 `setOnClickPendingIntent(wg_m_root)` 不受影响，与「点某一格跳那一天」是同一条机制（那一格也是子视图自己的 PendingIntent）。已经在今天那个月时点标题是个 no-op（锚点本就是 null）。

- **不新增 receiver**：`widget_fixed_cards_guard_test.dart` 里那条「manifest 必须四个 receiver」因此不用动，也避免为一张卡再拆一个落点（三张卡平级那条纪律）。
- **接收端要做的事**：解析 `widgetId` → 校验这个 id 还在（`AppWidgetManager.getAppWidgetInfo`）→ 算出目标月 → **目标月不可翻就什么都不做**（见下一条）→ 落盘锚点 → 只重渲染这一个实例（`ShiftWidgets.render(..., intArrayOf(widgetId))`）。不需要重排刷新闹钟。
- ⚠️ **「到头了」必须由接收端判，因为箭头变灰也不能不设点击**：`RemoteViews` 的 `reapply` 只重放**新的**动作串，**没有任何办法撤掉上一次设过的点击**（与 v0.9.9 那条 `removeAllViews` 同源：宿主会复用已在的那棵视图树）。所以渲染时**永远设** PendingIntent，颜色（`muted`）只作提示，越界由接收端吞掉。
- **requestCode（广播池，不是活动池）**：`BASE = 900_000`，`req = BASE + widgetId * 4 + dir`（`dir`：0=prev、1=next、2=today；再留一档给将来）。必须**每个实例、每个方向各一枚** —— `Intent.filterEquals` 不比 extras，撞号会让两张卡共用一个箭头（点这张、那张翻页）。要避开的既有占用：班次闹钟 `0..400`、自定义闹钟 `10000..11000`、待办提醒 `20000..39999`、重复待办 `40000..41999`、`WidgetRefreshScheduler.REQ = 40081`、`MainActivity.REQ_PICK_RINGTONE = 40071`。900_000 离这些都够远；`widgetId * 4` 到约 **5.36 亿**才溢出 Int（系统发的 widgetId 是个小整数，而活动池那边同样的算式 `100_000 + widgetId * 64` 早已上线运行，两池各自独立）。**注意目标组件是 `WidgetRefreshReceiver`（广播）**，与小组件点格那套 `launchIntent`（活动池，`100_000` 起）互不相干 —— 但别把两者记混（AGENTS 里那条 requestCode 清单就是为这件事写的，本次要同步更新它）。

### 4.5 降级与边界

| 情形 | 行为 |
|---|---|
| 无快照 / 解析失败 | 既有占位态，一字不改 |
| 锚点那个月没数据（42 格不全在窗口内） | 当作「跟随今天」（4.2），箭头照常可用 |
| 跨天（午夜那次重渲染） | 锚点是绝对值 → 仍然画你翻到的那个月 |
| 跨月（Anchor 变成「上个月」） | 同上；箭头可用性按新窗口重算 |
| App 两三个月没打开 | 窗口耗尽 → 能画的照画、到头的箭头变灰（与现状同一套退化） |
| 快照只有旧的小窗口（用户升级前 push 的那份） | 相邻月那几格 `GONE`，箭头变灰；下次 App 起来 push 后就正常 |
| 接收端收到一枚指向「已删除实例」的点击 | 校验 `getAppWidgetInfo` 拿不到就返回（用户删卡与点击可以同时发生） |

## 5. 不做什么

- **4×1 本周条与 4×3 今日卡一个字不改**（它们的内容与「哪个月」无关）。
- **不做无限前后翻**：那需要 App 活着查库，会破掉「小组件不依赖进程」这条性质。
- **不做滑动翻月**：RemoteViews 收不到滑动手势（要手势就得走 `ListView`/`StackView` 那套 Adapter 机制，为两个月历翻页不值得）。
- **不做「今天」按钮之外的快捷跳转**：点标题回今天已经够用。
- **不把月历改成可配置起始周几**：周一开头是既有约定，与 App 一致。

## 6. 验收

**Dart 侧（可自动化）**

- `widgetWindow` 的性质用例：跨年（1 月 / 12 月各一次）、5 行月与 6 行月、**「上月 / 本月 / 下月」三者的 42 格都落在窗口内**（这是翻月的前提，写成断言而不是注释）。
- 窗口长度 ≤ `kWidgetSnapshotMaxDays`（既有断言会自然覆盖，补一条上限本身没被随手改小的用例）。
- `widget_fixed_cards_guard_test.dart` 补钉子：两枚箭头 id 在布局里存在且被 Kotlin 按名取到、新 action 常量两边一致（这套没有编译期保护的约定一向靠它）。

**真机（Kotlin 没有可跑的测试目标，只能真机 + 出图）**

- 相邻月那几格：日数变灰、胶囊照画、月分界一眼能分。
- 箭头翻月、点标题回今天、到头那侧变灰且点了没反应。
- **每格高度**：42 格恒定 6 行，行高从 5 行月的约 77dp 降到约 63~65dp —— **这一条只有真机能判**，是本次唯一需要用户拍板的观感变化。
- 小米 / HyperOS：改资源后先 `am force-stop com.miui.home` 再验（否则会误判成「没生效」）。

## 7. 风险与取舍

- **每格变矮**（42 格恒定 6 行）：换来的是「整张卡是连续的日子」。（替代方案 —— 只在本月的行内补相邻月、不补满 42 格 —— 会让 5 行月与 6 行月的观感不一致，且「连起来」这件事只做了一半。）
- **协议版本不动**：新旧快照互相降级（旧读新忽略多余天、新读旧相邻月挖空），**不会黑屏**；代价是升级后的第一屏可能少画相邻月，等 App 起来 push 一次就正常。
- **广播池的编号纪律**：这次要往池子里加东西，AGENTS 里那条清单必须同步更新（它是唯一记着「哪些号段被谁占了」的地方）。
