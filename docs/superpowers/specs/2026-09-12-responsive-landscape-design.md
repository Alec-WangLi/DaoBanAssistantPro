- 日期：2026-09-12
- 目标版本：`0.6.4+75`（测试版）
- 状态：待评审

---

## 1. 背景与目标

### 1.1 现状

用户实测 v0.6.1：**手机横屏模式与小窗模式下，界面几乎无法使用。**

排查后确认这不是「不好看」，是三处**算术上必然发生**的失效：

**(a) 底部弹层高度写死，横屏溢出。** 三套玻璃弹层都是 `Column(mainAxisSize: min)` + 固定高度的子项，高度不随屏幕变化：

| 弹层 | 估算总高 | 说明 |
|---|---|---|
| `showGlassTimePicker` | ≈ 340 | 标题 22 + 8 + 滚轮 180 + 4 + 按钮行 48 + 内边距 28 + 外边距 24 + 安全区 |
| `showGlassMonthPicker` | ≈ 400 | 标题 22 + 8 + 年份滚轮 120 + 12 + 4 行月份 × 46 = 184 + 内边距 28 + 外边距 24 |
| `showGlassDatePicker` | ≈ 370–400 | 标题行 48 + 最多 6 行日期格 × 44 = 264 + 内边距 32 + 外边距 24 |

手机横屏（约 900×420 逻辑像素）扣掉系统栏与弹层自身的外边距后，可用高度约 **340–360**；小窗（约 360×360）约 **320**。三个弹层在横屏下全部或部分溢出（黄黑条纹），小窗下全部溢出。

**(b) 日历格子高度只按宽度算。** `calendar_screen.dart::_buildGrid` 里：

```dart
final cellW = (constraints.maxWidth - _hPad * 2) / 7;
final naturalCellH = cellW / _aspect;   // _aspect = 0.78
final fillCellH = (availHeight - _weekdayH) / _weekRows;
final cellH = fillCellH > naturalCellH ? min(fillCellH, cellW / _aspectMin) : naturalCellH;
```

横屏下 `cellW = (900 − 24) / 7 ≈ 125` → `naturalCellH ≈ 160`。而可用高度只有约 200（已被顶栏与底部信息卡吃掉大半），`fillCellH ≈ 33 < 160`，于是走 `naturalCellH` 分支 → **格子高 160**，一个月六行要 960px。一屏只能看到一行多一点。

`_aspectMin` 那道「不许太瘦」的下限只在**空间富余**时生效，空间不足时反而没有任何压缩通道 —— 逻辑正好反了。

**(c) 悬浮导航胶囊在短屏下占比过大。** 胶囊高 64 + 上下留白，横屏下约占可用高度的 1/5，且它悬浮在内容之上（`extendBody: true`）。

### 1.2 与车机目标的关系

用户已确认车机路线是**自己往车机上装 APK**。这条路的结论（调研见 §7）：

- **可行**：Android Automotive OS 与国内常见的开放式安卓车机跑的就是 Android，Flutter 应用在这里没有任何特殊性，是普通 APK。
- **但横屏适配是前置条件**：AAOS 默认对未声明 `android.hardware.type.automotive` 的应用启用**兼容模式**，把界面信箱化渲染成一个手机形状的小窗口 —— 这正是「无法使用」的另一种成因。声明特性后应用全屏渲染，横屏大屏的布局责任就全部落到我们身上。

**因此本轮做的就是车机适配的第一步**：让布局在横屏大屏上成立。车机专属项（§7.3）不在本轮。

### 1.3 目标

1. 手机横屏、小窗、宽屏（平板/车机）三种形态下，**七个主要界面与全部弹层不溢出、不重叠、可完整操作**。
2. 竖屏手机（`420×900`）下的观感**与 v0.6.1 逐像素一致** —— 本轮不趁机改竖屏设计。
3. 把「溢出」从只能靠肉眼发现的问题，变成**自动化测试会失败的信号**。

### 1.4 非目标

- 不改竖屏布局结构。
- 不做每个页面各自一套横屏专属设计（见 §2 的分档说明）。
- 不做车机专属功能（§7.3）。
- 不做 Android Auto / CarPlay 投屏（§7.4，明确排除）。

## 2. 分档

新增 `app/lib/core/layout.dart`：

```dart
/// 布局分档。三个判据彼此独立 —— 手机横屏是「宽且矮」，
/// 车机是「宽且不矮」，小窗是「窄」，用单一档位枚举表达不了。
class AppLayout {
  const AppLayout({required this.isNarrow, required this.isShort, required this.isWide});

  /// 可用宽 < 360：小窗、分屏。
  final bool isNarrow;

  /// 可用高 < 480：手机横屏、小窗。
  final bool isShort;

  /// 可用宽 >= 720：平板、车机、手机横屏。
  final bool isWide;

  static AppLayout of(BuildContext context);

  /// 宽屏下正文的最大宽度。表单在 1280 宽的车机上拉满整屏会难以阅读。
  static const double maxContentWidth = 720;
}
```

`AppLayout.of` 从 `MediaQuery` 取 `size`，扣除 `viewInsets`（键盘）与 `viewPadding`（刘海/系统栏），用**可用区域**判定，不用整屏尺寸。

**为什么是三个独立布尔值而不是 `compact / regular / expanded` 三档枚举**：手机横屏（900×420）与车机（1280×720）宽度都大，但一个矮一个不矮，需要的处置完全不同；小窗（360×360）宽和矮同时成立。用枚举会立刻需要 `compactButWide` 这种名字，等于把布尔值藏起来。

| 形态 | 可用尺寸（估） | isNarrow | isShort | isWide |
|---|---|---|---|---|
| 竖屏手机 | 420×900 | ✗ | ✗ | ✗ |
| 手机横屏 | 900×420 | ✗ | ✓ | ✓ |
| 小窗 | 360×360 | ✗ | ✓ | ✗ |
| 窄小窗 | 320×360 | ✓ | ✓ | ✗ |
| 平板 / 车机 | 1280×720 | ✗ | ✗ | ✓ |

## 3. 逐项改动

### 3.1 弹层：高度自适应（修溢出）

统一原则：**弹层的内容高度上限 = 可用高度 × 0.85**，超出部分按各自的机制消化。

**但只改内容高度是修不掉的**：三个弹层里**时间与月份这两个没有开 `isScrollControlled`**，而 `showModalBottomSheet` 默认把弹层高度压到屏幕的 9/16 —— 横屏 420 高的屏上，弹层最多只有 236px，而时间选择器的内容要 340px。真正溢出的主因是这个上限，不是内容本身。所以三处都要：

1. `isScrollControlled: true`（去掉 9/16 的限制，让弹层能长到屏幕高）；
2. 内容用 `LayoutBuilder` 拿**弹层自己的真实预算**（已经扣掉弹层 margin 与 SafeArea），按它收缩大块部件。

用 `LayoutBuilder` 而不是再算一遍 `MediaQuery`：弹层自带 `margin: 12` 与 `SafeArea`，`constraints.maxHeight` 已经是扣完之后的数字，自己再扣一次容易漏项。

| 弹层 | 改法 |
|---|---|
| `showGlassTimePicker` | `isScrollControlled: true`；滚轮高度 `(constraints.maxHeight − 106).clamp(96, 180)`（106 = 内边距 28 + 标题 22 + 间距 12 + 按钮行 44） |
| `showGlassMonthPicker` | `isScrollControlled: true`；年份滚轮 `(constraints.maxHeight × 0.30).clamp(72, 120)`；月份格行高 `(constraints.maxHeight × 0.10).clamp(32, 40)` |
| `showGlassDatePicker` | 已经是 `isScrollControlled: true`；日期格行高 `(constraints.maxHeight × 0.10).clamp(32, 40)`；整块包 `SingleChildScrollView` |
| 编辑器「班次颜色」弹层 | 色块 36 → 32，间距 `spaceLg(16)` → `spaceMd(12)`（`isShort` 时） |
| `GlassDialog` | 内容包 `SingleChildScrollView`，高度上限 = 可用高 − 80（`insetPadding` 的上下 40）− 标题与按钮行 |

各式的下限（96 / 72 / 32）是**可操作性下限**，不是审美取值：低于它滚轮滚不动、格子点不准，那时宁可让外层滚动或截断。上限（180 / 120 / 40）就是今天的取值，而且 `clamp` 的算式在**高屏上必然取到上限**（900 高的测试视口下 `maxHeight − 106` 远超 180，`0.30 × maxHeight` 也远超 120）—— 所以**竖屏与所有既有测试的结果与今天完全相同**。

**两个选择器不加外层滚动**：时间与月份弹层里各有一个 `CupertinoPicker`，它自己吃垂直拖拽手势；外面再套一层纵向滚动视图会与之抢手势，表现为滚轮滑不动或整块乱跳。它们靠**压缩子项高度**收敛，不靠滚动。

日期弹层没有滚轮（都是点击格子），可以安全地包滚动视图作为兜底。

### 3.2 日历

**(a) 格子高度改为双向约束**（这是 (b) 类失效的直接修复）：

```dart
final fill = (availHeight - _weekdayH) / _weekRows;
final cellH = fill >= naturalCellH
    ? math.min(fill, cellW / _aspectMin)   // 空间富余：拉高，但不超过「不许太瘦」的比例
    : math.max(fill, minCellH);            // 空间不足：压缩到够用，但不低于可读下限
```

`minCellH = 56`：日期 `18×1.15` + 间距 2 + 班次 `12×1.15` + 间距 2 + 农历 `11×1.15` ≈ 51，加格子自身内缩 4 —— 再压就要裁字了。

效果：横屏单栏下六行网格从 960px 降到 336px（不再「一屏一行」），小窗下同理；实在放不下时仍然滚动（网格外层已是 `SingleChildScrollView`）。

**(b) 宽屏左右分栏**（`isWide`）：

```
┌───────────────────────────────────────┐
│ ‹  2026年9月  ›   ⇅        [今天]     │
├────────────────────────┬──────────────┤
│  1  2  3  4  5  6  7   │  9月12日     │
│  8  9 10 11 12 13 14   │  白班        │
│ 15 16 17 18 19 20 21   │  08:30–20:30 │
│ 22 23 24 25 26 27 28   │  闹钟 07:00  │
└────────────────────────┴──────────────┘
```

左栏网格 `Expanded(flex: 3)`（最小宽 320），右栏信息卡固定宽 300 且可滚动。分栏后网格可用高度大幅增加，格子不再被压。信息卡从「底部横卡」改为「右侧竖卡」，内容不变。

**(c) 短屏且非宽屏时的信息卡**：压成单行紧凑版（日期 + 班次简称 + 时间 + 闹钟图标），高度从约 110 降到约 56，把高度让给网格。

**(d) `isNarrow` 的顶栏**：「今天」按钮收成纯图标钮（去掉文字），保证年月完整显示。

### 3.3 悬浮导航胶囊

`isShort` 时：高度 64 → 52，左右外边距 24 → 16，图标 22 → 20，文字仍 10。

各页底部的内容留白（日历信息卡 120、编辑器 100 等）在 `isShort` 时同步收紧（各减约 44，即胶囊省下的高度）。

**不做成 `胶囊高 + 留白 + 安全区` 的统一公式**：那样算出来是 76，而日历今天用的是 120 —— 差的 44 是信息卡与胶囊之间的呼吸余地，属于刻意的视觉间距，不是由胶囊尺寸推导出来的。套公式会把竖屏的观感改掉，而「竖屏逐像素不变」是这一版的硬约束。所以只在短屏收紧，竖屏原样保留。

### 3.4 宽屏内容限宽

`isWide` 时，**编辑器、模板选择页、日历以外的四个 tab 页**的内容居中并限宽 `maxContentWidth = 720`。

理由：车机常见 1280×720，表单拉满整宽后一行文字跨度过大、阅读困难，且「标签在左、值在右」的行会在两端离得太远。限宽居中是宽屏表单的通行做法，也是这一轮为车机做的性价比最高的一处改动。

### 3.5 编辑器与模板页的紧凑档（`isNarrow`）

- 卡片内边距 `spaceLg(16)` → `spaceMd(12)`。
- 周期行右侧的只读时间文案隐藏（v0.6.3 的 chip 组已按此设计，本轮对齐）。
- 班次行的简称输入框宽度 60 → 52。
- **字号不缩** —— 窄屏本来就更需要可读性，缩字号是反的。

## 4. 视觉工装扩展（把溢出变成失败信号）

现工装（`app/tool/visual/`）把屏幕尺寸写死为 `kVisualSize = 420×900`，因此**横屏的问题它拍不到** —— 这就是这些缺陷能一路走到用户手里的原因。

改动：

1. `visualVariants` 的每条增加 `size` 字段；现有三个变体填 `kVisualSize`，**出图与今天完全一致**（不产生噪音 diff）。
2. 新增两个变体：
   - `横屏 900×420`（浅色，中文）
   - `小窗 360×360`（浅色，中文）
3. `setUpVisualViewport` 改为接收尺寸参数。
4. `render_screens_test.dart` 的 `failOnOverflow` 保持不动 —— 它在**渲染期间**捕获 `FlutterError` 溢出，加了横屏尺寸后，任何弹层溢出都会让测试失败。**这就是本轮的验收手段**：不靠肉眼找黄黑条纹。
5. `contrast_audit_test.dart` 与出图共用 `visualScreens` / `visualVariants`，因此会自动多跑两个尺寸。对比度与尺寸无关，审计侧**只跑原有三个变体**，避免白烧一倍时间。

## 5. 边界与容错

| 场景 | 行为 |
|---|---|
| 横屏下弹层仍放不下（极端窄高比） | 压缩到下限后若仍溢出，时间/月份弹层允许滚轮区域自身截断；日期弹层由外层滚动兜底 |
| 小窗下网格仍放不下整月 | 滚动（既有行为），格子不低于 `minCellH` 以免裁字 |
| 键盘弹出（`viewInsets` 变化） | `AppLayout` 用扣除键盘后的可用高度判定，编辑器会切到紧凑档而非溢出 |
| 系统字号放大 | 字号走令牌照常缩放；`minCellH` 是固定值，大字体会更早触发滚动（可接受，不裁字） |
| 竖屏 420×900 | 三个布尔值全为 false，所有分支都不生效 → 与 v0.6.1 一致 |

## 6. 验收标准

1. `flutter analyze` —— 0 error / 0 warning。
2. `flutter test` —— 全绿。
3. **`flutter test tool/visual/render_screens_test.dart` 在 5 个变体 × 7 个界面下全部渲染通过、零溢出。** 竖屏三个变体的产出图与 v0.6.1 逐像素一致（人工抽查）。
4. 新增 widget 测试：
   - `AppLayout.of` 在 5 组尺寸下判定正确（§2 表格逐行断言）。
   - **日历格子高度**：给定 `900×420`，断言 `cellH < naturalCellH` 且 `cellH >= minCellH`（即进入了压缩分支，不再等于按宽度算出的 160）；给定 `420×900`，断言 `cellH` 与 `_aspect` 旧公式算出的值相等（竖屏零回归）。
   - **弹层高度**：给定 `900×420` 与 `360×360`，断言时间选择器的滚轮高度等于其下限值且弹层总高不超过可用高 × 0.85；给定 `420×900`，断言滚轮高度仍是 180（竖屏零回归）。
5. 手工验收：真机横屏开日历、编辑器、三个选择器；小窗下滑动整月、走一遍新建排班全流程、打开日期选择器。
6. 对比度审计脚本跑一遍无新增不达标项。

## 7. 车机路线（调研结论与待办）

### 7.1 可行路径

**自己往车机上装 APK** —— 这条路成立。Android Automotive OS（车机里跑的完整 Android）与国内常见的开放式安卓车机，运行的就是 Android 应用；`adb install` 或 U 盘拷贝即可安装。Flutter 在这里没有特殊性：它是普通 APK，自绘渲染层照常工作。这与鸿蒙 NEXT（根本不运行 APK）是完全不同的性质。

### 7.2 关键约束：AAOS 的兼容模式

AAOS 默认对**未声明** `android.hardware.type.automotive` 特性的应用启用兼容模式 —— 系统把应用信箱化成一个手机形状的窗口渲染，四周留黑边。在 1280×720 的横屏车机上，得到的就是一个又窄又小的竖屏窗口。

声明该特性即可关闭兼容模式、全屏渲染，**代价是横屏大屏的布局责任全部自负**。本轮（§3）做的就是这件事的前置部分。

### 7.3 车机专属待办（本轮不做）

- 清单声明 `android.hardware.type.automotive`；`android.hardware.screen.portrait` / `landscape` 声明为 `required=false`。
- 屏幕常亮（车机使用场景下熄屏无意义）。
- 旋钮 / 物理方向键导航（车机常见输入方式，现在完全没处理）。
- 非标准 DPI 与系统栏占位。
- 无 GMS 环境（检查更新已走 GitHub 直连，不受影响）。
- 车机上的保活与闹钟策略（车上闹钟意义有限，但需确认不误触发）。
- 车机分辨率专项测试（1280×720 / 1024×600 / 1920×720 等）。

### 7.4 明确排除：Android Auto / CarPlay 投屏

**不做。** 两条理由，任一条都是否决性的：

1. 投屏不是把界面显示到车机上，而是要求手机端用 Car App Library 的**模板**（Navigation / Place List / Message）渲染 —— Flutter 自绘的 widget 树无法投上去。
2. 投屏只开放媒体 / 导航 / 消息 / POI / 天气几类应用；「排班日历」不属于任何一类，过不了类别门槛。

## 8. 范围外（本次明确不做）

- 竖屏布局的任何改版。
- 平板 / 折叠屏的专门布局（宽屏限宽与日历分栏会顺带改善，但不做专门设计）。
- 每个页面各自的横屏专属设计（本轮是「同一布局在不同尺寸下成立」，不是「横屏另画一套」）。
- §7.3 的全部车机专属项、§7.4 的投屏。
