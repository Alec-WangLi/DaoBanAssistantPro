- 状态 Riverpod；数据 Drift（SQLite，纯本地离线，无后端）；农历 lunar_plus；通知 flutter_local_notifications。
- Drift 表：`ShiftScheduleRows`（排班方案；`isCurrent` = 「其余时间」用哪一套，可全 false = 「无」）/ `ScheduleSpanRows`（**时间线上的段**：`scheduleId` + 可空的 `startDate`/`endDate`；一套方案可以出现在多段上，见「关键决策与坑」）/ `ShiftClassRows`（班次定义）/ `ShiftCycleRows`（周期序列）/ `ShiftClassAlarms`（班次闹钟：复合主键 `classId + order`，`order` 同时是原生 id 的「序号」；**没有自增 id**，因为没有任何东西引用单条闹钟）/ `ScheduleEvents` / `CustomAlarms` / `ShiftAlarmOverrides`（按天覆盖班次闹钟，主键 `day` = 自 epoch 天数，`dayNumber()` 计算）/ `ShiftDayOverrides`（按天改班覆盖，复合主键 `scheduleId + day`，`classId` 指到本方案的班次定义；只作用于我们班组）/ `CustomTemplates`（「我的模板」：name + 整块快照（classes 走 JSON、cycle/teamOffsets 走逗号分隔）+ teamCount + createdAt）/ `RecurringSeriesRows`（重复待办的**系列定义**；表名带 `Rows` 后缀是因为 drift 会按表名生成行类，叫 `RecurringTodos` 就与领域层的 `RecurringTodo` 撞名。v15 起每月用 `monthDays` 位掩码、按班次用 `shiftNames`（JSON 名字数组））。**当前 schemaVersion = 15**。
- **改 Drift 表后必须重生成**：`dart run build_runner build`。
- **`watchActiveSchedule()` 必须同时监听覆盖表**：它原先只 `watch` 方案行，子表（班次 / 周期 / 覆盖）在 `asyncMap` 里读一次。只盯方案行的话，用户改完覆盖**落库成功**，这条流不会重发 —— 日历上**纹丝不动**，不报错也不崩，从界面上完全看不出原因。现在把 `shiftDayOverrides` 也挂进触发源，两张表任一变化就重新装配一次。
- **「我的模板」整块存一列，不拆三张表**：模板是**只读快照** —— 没有按字段查询、没有跨表引用、也不与任何行共享身份，拆表只会多两张表和一套装配代码（方案那边拆表是因为**按天改班的覆盖要引用稳定的 classId**，模板没有这个需求）。编解码在 `domain/schedule_template.dart`（纯函数、可单测），**班次 id 不入模板**（模板里的班次不需要稳定身份，存了反而会与新方案的自增 id 撞车）。两个必须记住的点：① 保存模板时把「我们班组」**归一化到第 0 位、错位归零**（`ScheduleTemplate.fromSchedule`）—— 新建排班那条路写死 `ourTeamIndex: 0`，不归一化的话用模板建出来的方案里「我们班组」会指到别人身上；② 读取走**一次性 `listTemplates()` 而不是 `watch()`**，页内改名 / 删除由 `ref.invalidate(savedTemplatesProvider)` 重读。第②条是踩过的坑：drift 的查询流在取消时用 `Timer.run` 排一个零时长定时器清理缓存，而 widget 测试在测试体结束**立刻**校验「没有待处理的定时器」—— 用流的话，每条挂选择页的用例都会报「A Timer is still pending even after the widget tree was disposed」（`calendar_screen_test.dart` 的 `_disposeCalendar` 就是为同类页面准备的解药，但没必要为一个短命页面付这个代价）。③ **但这个 provider 必须 `autoDispose`** —— 改一次性读的第一版忘了它，于是第一次读到的结果被缓存一整个会话：用户先开过一次「新建排班」（那时还没模板），之后在编辑器里存下模板，回去**看不到**，要重启 App 才出现。v0.8.11 发出去当天就被用户逮到（「我保存模板后，没看到呀」）。修法：`FutureProvider.autoDispose` + 存完顺手 `ref.invalidate`。**回归测试在 `saved_template_test.dart`（「先开过选择页…存完再回来必须看得到」），已反向验证：去掉 autoDispose 这条立刻变红**；真机上按「开选择页 → 存模板 → 不重启再看」复现并验证过。教训：**「一次性读 + 缓存」这套写法，凡是「别的页面会往里写」的数据，都必须 autoDispose 或显式 invalidate**。
- **一条自我纠错，写下来免得后人照抄错的：`watchSingleOrNull()` 对带 `where` 的查询照样会在整表任意一行变动时重发。** v0.9.12 实施时的原计划写的是「不许 watch 整表就不会重发」——**实测不是这样**。所以「改非当前方案看不见」的根因不是触发源，而是**装配**只装了 `isCurrent` 那一套。改成整表 `.watch()` 换来的是另外两件事：装配得到全部方案、以及再也不会在两行 `isCurrent` 时往流里推错。反向验证也重做过：把**方案表那条触发源整个删掉**（而不是换成过滤版），`schedule_chain_repository_test` 立刻红（`Expected: <1> Actual: <0>`）—— 那条用例守的是「触发源不能少」。**教训：护栏要反向验证，但验证的必须是「换个真错法」，不是「换个等价写法」** —— 第一版验证正是后者，差点把一条假保证写进注释。
- **迁移分支一律按倒序跑，所以「谁碰了什么表，所有更早版本的迁移 fixture 就都得有那张表」。** v10→v11 给 `schedule_events` 加了一列，于是 v7→v8 / v8→v9 / v9→v10 三份 fixture 全被迫补上它的 DDL —— 否则会在 `ALTER TABLE` 上抛 `no such table: schedule_events`，而**真机上不会**（真库什么表都有），所以那是只在这个仓库的测试里才现形的坑。改动迁移链时先看这一条。另一个同源的细节：迁移测试里**比日期一律走 `dayNumber` / `isSameDay`** —— drift 读回来的是**本地** DateTime，存进去的是 UTC 纯日期，直接比 `DateTime` 在东八区就差 8 小时。
- **数据备份走「暂存 + 启动时替换」，不在运行中换库**：导出用 `VACUUM INTO`（连同 WAL 的一致快照）；导入先解到 `pending_restore/`，冷重启后由 `main()` 在**任何数据库打开之前**替换。替换顺序必须是「先写 `<db>.restore` → 删旧库与 `-wal` / `-shm` → rename」，中途失败旧库仍在。换完置 `needsAlarmReplan`，由 HomeShell 首帧后按新库重排 —— 漏了这一步，系统里排的还是旧排班的闹钟。格式与校验在 `features/backup/backup_format.dart`（纯函数），读写盘在 `backup_service.dart`。
