- **班次定义的 id 必须稳定（按天改班的地基）**：`saveSchedule` 从前是把该方案的班次行**删光重建**，于是每保存一次所有 `classId` 全变 —— 按天覆盖会在第一次保存后**静默指飞**。现已改成**增量**（带 id 的 UPDATE、没 id 的 INSERT、不在新列表里的 DELETE）。因此 `ShiftClass.id` 这条链上一个环节都不能漏：`ShiftClassRowX.toDomain()` 必须带出 id、编辑器的 `_editClass` 必须把 `id: c.id` 显式带上（它**有意不走** `copyWith` —— `copyWith` 把可空字段写成 `xx ?? this.xx`，没有把可空字段**清成 null** 的通道，切休班时时间 / 闹钟就永远清不掉；图省事「简化」成 `copyWith` 会把这个 bug 带回来）、`saveSchedule` 必须按 id 走增量而不是重建 —— 漏任何一环都不报错，只让那天的覆盖指向别的班次或指向空。删班次时引用它的覆盖行一并清掉（`saveSchedule` 收尾扫一遍悬空 `classId`）；`deleteSchedule` / `clearAll` 也要连带删覆盖。
- **班组错位（`teamOffsets`）只有一条规则：按周期长度均分** —— 第 i 个班组落在 `i × cycleLength ÷ teamCount` 天处（四班两倒 4/4→0/1/2/3、两班倒 14/2→0/7、DuPont 28/4→0/7/14/21、五班四倒 5/5→0/1/2/3/4）。全部内置模板都符合它，`shift_templates_test.dart` 现在逐条反查（模板里的错位是人手抄的，抄错只有这条抓得住），另外每个模板还会跑一遍 `crewClashes` 确认没有两个班组撞班。**错位与周期长度不匹配的症状是「同一天两个班组上同一个班」**：周期从 5 天改成 10 天（每个班连排两天）而错位还按 1 天来，10 天里 9 天都撞 —— 起因是编辑器的 `_setCycleLength` 只管周期、不碰班组起始日（2026-09-21 用户反馈，当时以为是 App 坏了）。修法是**提示 + 一键均分**（`evenTeamOffsets`，均分时**我们班组原地不动**，否则会把用户自己的班表平移），不是静默改掉用户手工设过的起始日。
- **排班时段：段在**自己的表**里（`ScheduleSpanRows`），一套方案可以出现在多段上。** 这条是 v0.9.14 重做时被一个**装不下的形状**逼出来的：旧规则（起点最晚的赢）能表达「外段被内段截断之后还要接着用」—— 例如 `B[7/1, ∞)` 与 `C[9/1, 9/30]`，用户看到的是「7/1–8/31 归 B、9 月归 C、**10/1 起又归 B**」，而「一套方案只有一对起止」表达不了。同理，用户在界面上也排不出「9 月临时换、之后换回来」。**别把段再塞回方案行上的两列。**
- **`ScheduleSpan` 带两个 id，别搞混**：`id` 是**段**的行 id（编辑 / 删除 / `conflictingSpans` 判「是不是自己」），`scheduleId` 是**方案**的行 id（`scheduleIdOn` 给按天改班用 —— 覆盖表主键是 `{scheduleId, day}`）。混了的症状是覆盖记到错的方案名下：**不生效、也不报错**。用例里故意让两个 id 取不同的值，这样它才分辨得出。
- **解析规则全 app 只有一处实现，而且「日期比较一律走 `dayNumber`」。** `ScheduleChain.scheduleOn`（`domain/schedule_chain.dart`）：覆盖那天的段（**至多一段**，因为重叠是界面禁止 + 迁移规整过的）→ 没被覆盖就用「**其余时间**」（`isCurrent` 那套，**可能为 null** = 用户把它设成了「无」，那几天真的没排班）。两处容易写错：① **`covers` / `_startsLater` / `_overlaps` 三处都必须走 `dayNumber`**（段表那两列由 drift 读回来是**本地** DateTime，而调用点传进来的可能是 UTC 纯日期，直接比 `DateTime` 在东八区差 8 小时、边界那天静默判错）；② 实现里那条「起点最晚的赢」**只剩防御作用**（只在脏数据下生效），**别读成「重叠是允许的」** —— 用户可见的语义是唯一解。
- **迁移是「按边界切 → 逐区间重放旧规则 → 合并相邻同胜者」，不是「截断水位线」。** 前者天然无损（同一套方案会因此产生两段），后者会把「外段截断之后接着用」的尾部**丢掉**（那些天会掉给「其余时间」）。两条实现上的坑：① 那两列已经从 schema 删掉了（生成的行类上没有 getter），迁移必须**直接读原始列**（`customSelect`），而且要在 `TableMigration` 删掉它们**之前**读；② 循环要跑满 `bounds.length` 轮 —— 最后一个边界之后还有一段开到 +∞ 的区间（「一直持续」全靠它），写成 `i + 1 < bounds.length` 会把整段漏掉。
- **`deleteSchedule` / `clearAll` 要连带删段**（段也是方案行的子表）。另外「除了显式点『设为无』，其余时间不会变 null」—— 删掉一套方案时仍然自动把其余时间交给列表里的第一套，否则「删掉默认那套」会让整张日历变空。
- **`ShiftSource` 让「单套」与「多套」在调用点无法区分 —— 这是「原生侧一个字都没改」的全部依据。** 闹钟（`planShiftAlarms`）与桌面小组件（`buildWidgetSnapshot`）本来就**逐天遍历**、每天问一次「今天什么班」，所以只要把查询面抽成只有 `shiftOn(date)` + `label` 的接口、把入参从 `ShiftSchedule` 换成它，`WidgetRenderer.kt` / `AlarmScheduler.kt` 一行都不用动。**加新的「按天」消费者时照这条走**：要 `teamShift` / `teamCount` 那些（只有小组件的今日卡、日历的信息卡需要）用 `chain.scheduleOn(date)` 取当天那套再问它。
- **空白表（跟随法定节假日）：两件事必须分开 —— 「这天有没有班表在管」与「这天画不画得出东西」。**
  - **判据用 `ScheduleChain.hasScheduleOn(day)`**（= `scheduleOn(day) != null`）。别用 `shiftOn == null`：空白表的 `cycle` 是空的，`shiftOn` **天天**返回 null，拿它判就会把空白表当空库 —— 日历整月被「这段时间没有排班」盖住（v0.9.14 真机反馈），桌面小组件写「还没有排班」（同一条反馈的另一半）。
  - **显示上什么都不写**：空白表没有班次定义，日历格子 / 小窗信息卡 / 桌面小组件**都只画日期与农历**（法定节假日照旧标红、调休照旧打「班」）。用户 2026-09-30 的原话是「确实不应该显示上班嘛，它本质上可能就想当个日历看」。信息卡那一支同样什么都不写 —— **不是**「没有排班」那句，那句只在 `scheduleOn(day) == null`、真的没有任何班表盖着那天时才出现。
  - **三个 getter 的分工，混用一次就有一条现成的用户反馈**：`shiftOn`（这天有没有**班次**）、`hasScheduleOn`（这天有没有**班表在管**）、`hasCycle`（链上有没有**班次可挑**的班表）。拖选与「调整班次」的闸门用 `hasCycle`（空白表必须算「没有」，否则用户拖出一片淡染、松手什么也不发生）；桌面小组件的 `hasSchedule` 用 `hasAnySchedule`（「用户到底排没排班」，空白表也算 —— 否则只有一套法定班次时桌面又写「还没有排班」）。`schedule_chain_test.dart` 里那条用例把三者摆在一起钉住。
  - ⚠️ **v0.9.15 走过一次弯路，别再走**：当时为了让那句指路的判据不再误盖，给空白表**合成**了一个「上班 / 休息」班次（`domain/day_display.dart` 的 `displayShiftOn`，色号借内置模板的白班蓝与休班灰）—— 那是**拿显示去迁就判据**，用户第二天就指出来了。判据归判据、显示归显示；那个文件与那两个色号已删净，`shiftOn` 从头到尾都是真值。
  - **信息卡那一行的高度是逐日算的**（`info_card_metrics.dart`）：空白表那天按 0 算。那一段曾经是一次性算好的常量，会给空白表白留约 16dp —— 而用户对「卡片底下那截空白」是报过一次的（v0.9.7 整轮的起因）。
- **`setDayOverrides` / `clearDayOverrides` 必须按天找方案，不能写死「当前方案 id」。** 覆盖表的主键是 `{scheduleId, day}`：有了衔接之后，用户能给属于**非当前**方案的那天「调整班次」—— 记在当前方案名下的话那条覆盖**既不会生效、也不报错**，用户看到的是「改了班、日历纹丝不动」（与「覆盖表没挂 watch」「勾掉重复待办又回来」同属一类静默失败）。修法是逐天 `chain.scheduleIdOn(date)`，**签名不变**，所以既有的 20 处调用一行都不用改（老库没有时段时它恒等于当前方案 id）。**跨边界的多天拖选由界面上拦住**（`adjustDays` 里那句「请分开调整」）—— 那是「列了 A 的班次却只对 A 的日子生效」的静默半生效，比报错更难查。
