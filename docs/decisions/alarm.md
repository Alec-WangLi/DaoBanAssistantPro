- **改动「今天归哪套」的入口，必须同时重排闹钟（v0.12.1 立的规矩）**：排班结构一变（换「其余时间 / 全部日子」、增删改排班时段、删一套方案、编辑页保存、日历改班），日历会立刻跟上（它 watch 着库），**原生闹钟不会** —— 不调 `AlarmService.rescheduleAll` 的话，旧计划里的班次闹钟照旧在原定时刻响。2026-10-18 真机就是这么响的：当天白班，19:30 响了旧方案（按月排班）里上夜班的闹钟；真机上复现过「切过去日历变了、`dumpsys alarm` 一条没变」。调用点一律放在**关窗之后**（整链重排真机上要几百毫秒，别让弹层陪着卡）。**回前台不会重排**（`home_shell._tryStartupReschedule` 有一次性闸门 `_startupRescheduled`），别指望它兜底。加新入口时先问一句：这一步有没有改变「某天归哪套」？
- **界面上的钟点一律 24 小时制**：响铃界面那台时钟曾经用 `TimeOfDay.hourOfPeriod`（12 小时制的 0..11）却不带 AM/PM，20:10 的闹钟显示成「08:10」（2026-10-18 真机）。全 app（闹钟列表 / 编辑页 / 信息卡）都是 24 小时制，新写的格式化不要再用 `hourOfPeriod`。
- 闹钟链路：`setAlarmClock` → `AlarmReceiver` → `AlarmRingService`（前台服务 MediaPlayer + Vibrator + WakeLock + fullScreenIntent）；`MainActivity` 在 `super.onCreate` 前 `setShowWhenLocked`/`setTurnScreenOn`。
- `AlarmService.reschedule` 排**未来 60 天**班次闹钟 + 自定义闹钟（一次性/每天/每周，重复型由原生侧同一 id 续排）；按天覆盖值为 false 的日期跳过。
- **班次闹钟一个班次可以挂多个（上限 10），落在哪天是算出来的，别退回「班次当天 + 钟点」**：判据是 `alarmDayAnchor(shift, alarm)`（纯函数，`domain/shift_rotation.dart`）—— ① 钟点落在**值班窗口** `[start, end)` 内 → **那一刻出现所在的那一天**（窗口跨过午夜时就是**次日**：中班 16:30–次日 0:30 的 00:15、零点班的班中 03:00 要的都是这一档，2026-09-21 与 2026-10-11 两次用户反馈问的正是它）；② 否则**晚于上班钟点** → **前一天**（00:00 上班 + 23:00 响铃：排在班次当天那一刻这个班已经结束 15 小时，v0.8.9 修的那条，**这一版不动它**）；③ 否则 → **当天与次日里离窗口更近的那一个**（「下班之后那一刻」：同一个班次配 01:00 → **次日** 01:00）。**24 小时值班（`span >= 1440`）一律算当天** —— 不加这条例外，内置三个 duty 模板的 07:00 上班提醒会从「上班前 1 小时」变成「下班前 1 小时」（`shift_templates_test` 的模板差集用例钉着它）。落点由 `shiftAlarmFireAt(date, shift, alarm)` 算。**四处显示都要跟着标**（班次编辑的钟点块与它下面那行说明、闹钟列表行、日历信息卡的 `_alarmText`）—— 标「前一天」或「次日」，不标会被读成班次当天；多条时**每条标各自的**。**`offset` 与原生 id 仍按班次那一天算**，跟着前移的触发时刻走会让每个午夜班的闹钟都换号。**`planShiftAlarms` 的窗口从「昨天」起算**（0.11.2 修的那条回归）：次日档的闹钟属于昨天那个班次、却在今天响，而 `reschedule` 开头会把 `0..600` 全部取消再照计划重排 —— 窗口里没有昨天就等于「取消之后再也没排回去」，静默不响（冷启动 / 回前台 / 开机重排都走这条路）。时间没填：上班没填按当天（不瞎挪一天）、下班没填退回 ②③。（0.11.1 起「次日」这一档已经能做 —— 见上。）**`endMinute` 有两种存法，算值班窗口时别只按一种**：累计式（24 小时值班 480 → 1920）与**回绕式**（12 小时制夜班 20:30 → 08:30 存成 510 < 1230 —— 内置 12 小时制模板与编辑器产出的**都是这一种**）。`span` 直接相减在回绕式下**是负的**，窗口判据会静默失效（v0.9.2 就这么漏了一整类班次，v0.9.3 才修掉；当时我的用例全用累计式，所以没照出来）。`shift_rotation_test.dart` 里「回绕式存法的跨午夜班」与「两种存法同解」两条是护栏 —— 以后若再引入第三种存法，把它加进那条同解用例。
- **班次闹钟的数量上限是 id 空间算出来的，不是产品口味**：原生 id = `序号 × 天数窗口 + 天数偏移`，天数窗口就是 `AlarmService._shiftDaysHorizon`（**同时**是 `reschedule(days:)` 的缺省值），序号 = 闹钟在 `ShiftClass.alarms` 里的下标。6 × 60 = 360 ≤ 400 —— 400 是 Kotlin 侧 `cancelAllNativeAlarms` 的扫描上界（`MainActivity.kt:550`）。**改上限、改天数窗口、改扫描范围，三个一起改。** 另一条：**重排绝不能重新编号**（否则每次打开 App 都换一批 id，用户设过的响铃记录会错位），但**用户在编辑页里调整闹钟顺序会换号** —— 那是可接受的（编辑之后必然重排、`cancelAll` 先跑）。算式与上界由 `shift_alarm_decision_test.dart` 的「原生 id 的算式」用例钉住。
- 闹钟页 = **未来 30 天**班次闹钟（每条可单独开关、响过自动隐藏）+ 自定义闹钟分区；`Timer.periodic(1min)` + 回到前台重建；响过的一次性自定义闹钟自动删除。
- **小米机型锁屏弹不出响铃界面 = 少开了一项系统权限，不是「OS 限制」**：MIUI 的「后台弹出界面」（系统里显示为 `Open new windows while running in the background`，与「显示悬浮窗」是两项）不开时，`ActivityStarterImpl` 会**静默**拒绝从后台拉起 Activity（logcat 里只有 `MIUILOG- Permission Denied Activity`），系统把它降级成 "invisible launch"——Activity 起来了但不显示、`onNewIntent` 都不走，**连通知那条 fullScreenIntent 的 PendingIntent 也一起被拒**。表现就是闹钟只响、不弹界面。两项都开之后实测：退后台 → 自动拉前台弹出响铃界面；退后台 + 锁屏 → 点亮屏幕并顶掉 keyguard（`mKeyguardOccluded=true`）。这项权限**读不到状态**、也没法用 adb 授予（MIUI 的 op 常量是 `OP_BACKGROUND_START_ACTIVITY`，但没进 `AppOpsManager` 的名字表），只能引导用户去开：`am start -a miui.intent.action.APP_PERM_EDITOR --es extra_pkgname <包名>`。**再遇到「锁屏不弹」先查这项权限，别当 OS 限制记档。**
- **响铃结束必须撤掉 `setShowWhenLocked`**：它是只进不出的，不显式关掉，这个 Activity 会一直能盖在锁屏上——用户关掉响铃界面后露出来的是 App 主界面（锁屏下能直接操作 App 内容，真人反馈的隐患）。`MainActivity.exitLockScreenMode()` 在 `stopAlarm` 里调用。
- **`SYSTEM_ALERT_WINDOW` 不能删**：代码里没有 `WindowManager.addView`，但「显示悬浮窗」权限卡（`AlarmService.checkOverlayPermission`→`Settings.canDrawOverlays`）依赖它在 manifest 声明——删了 App 就从系统「显示悬浮窗」列表消失、小米/华为锁屏全屏闹钟可能弹不出（AOSP 层那次后台启动豁免走的就是它，`BAL_ALLOW_SAW_PERMISSION`）。grep 判"未使用"是误判，勿再删。
- **响铃界面要用的设置，只能直接读 `SharedPreferences`，不能读 provider**（v0.11.8 的贪睡时长）。那个界面是原生闹钟的 intent 拉起来的，**不 watch 任何 provider**；而 `appSettings` 那一套的值要等 `_load()` 才落到模块级标志上（v0.10.13 的 `47_ringing_liquid` 出图与标准档**逐字节相同**，就是同一个坑的现场）。所以「响铃那一刻才用的设置」——贪睡时长、铃声——一律直接读 prefs，两处共用一个真源。⚠️ 读到**不在档位里**的值要**退回默认**、不要照排：照排的话 `0` 会变成「按下就再响」、负数会排到过去，两者都比没有这一项更糟。
- **「仅震动」这一档铃声存的是哨兵值，不是新字段**：`AlarmSound.VIBRATE_ONLY = "vibrateOnly"`，与铃声 URI **共用** `ringtoneUri` 这一个键（Dart 侧同一个值在 `AlarmService.vibrateOnlyRingtone`）。理由：整条链路本来就是一路字符串（prefs → `MainActivity.scheduleNativeAlarm` → Intent extra → `AlarmReceiver` → `AlarmRingService` → `AlarmSound`），另加布尔开关要同时改这五处、还要改 `AlarmStore` 的开机重排记录。**两个必须记住的点**：① **不能拿空串 / `null` 表示静音** —— `AlarmSound.start` 里那两值的含义是「没配 → 用内置铃声」，拿它们当静音会**静静地响一声**，比不响更糟；哨兵因此判在 `start` 的最前面，且显式返回 null、**不记错误日志**（这是用户选的正常状态，不是失败）。② Dart 与 Kotlin 各持一份常量、没有共享通道，**写歪一个的后果是静默的**（回落内置）；由 `test/ringtone_vibrate_only_test.dart` 扫两边源码比对（同 `widget_fixed_cards_guard_test.dart` 的套路）。哨兵不可能与真实音源撞上：系统铃声 `content://`、自选 `file://`、内置**根本不存**这个键。另注：`AlarmService.startAlarmSound()` 全仓无调用点，`MainActivity.startAlarm` 是条死路（真在跑的是 `AlarmReceiver → AlarmRingService`），改音源时别只改那一条。
